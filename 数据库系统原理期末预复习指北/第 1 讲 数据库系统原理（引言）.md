# 第一讲 数据库系统原理（引言）

## `1.1` 数据库系统概述

- `1.1.1` 数据

    描述事物的符号记录称为数据

    - 表现形式：数字、字符、图形、图像、视频、声音等；所有形式都可以数字化存入计算机
    - **数据是数据库中存储的基本对象**

- `1.1.2` 数据库

    数据库是按一定的组织形式存储在一起的**相互关联的数据的集合**

    > 不是零散文件堆砌，数据之间是有联系的

- `1.1.3` 数据库管理系统

    数据库管理系统 `DataBase Management System (DBMS)` 是数据库系统的核心软件，由相互关联的数据集合和一组访问数据的程序组成

    - 能够提供方便、高效存取数据库信息的途径
    - 常见例子：MySQL、PostgreSQL、SQL Server、Oracle

    ```mermaid
    flowchart LR
        App1[数据库应用系统1] <--> DBMS
        ... <--> DBMS
        AppN[数据库应用系统n] <--> DBMS
        DBMS <--> DB[(数据库)]
    ```

- `1.1.4` 数据库系统 `DataBase System (DBS)`

    数据库系统 `DataBase System (DBS)` 是一些相互关联的数据和一组（使得用户可以）访问、修改数据的程序的集合

    数据库系统由数据库、数据库管理系统（及其应用开发工具）、应用系统、和数据库管理人员组成的存储、管理、处理和维护数据的系统

    ```mermaid
    flowchart TD
        U[用户] --> App[应用系统]
        App --> DevTool[应用开发工具]
        DevTool --> DBMS[数据库管理系统]
        DBA[数据库管理员] --> DBMS
        DBMS --> OS[操作系统]
        OS --> DB[(数据库)]
    ```

## `1.2` 数据库系统应用

只要需要持久存储、管理数据的场景，就可以使用数据库

- `1.2.1` 应用领域：政府、教育、工业、金融、服务业等几乎所有行业
- `1.2.2` 应用平台：业务管理系统、网站 / Web 应用、嵌入式控制系统、移动端系统

## `1.3` 数据视图

- `1.3.1` 数据模型

    一个描述数据、数据联系、数据语义、以及一致性约束的概念工具的集合称为数据模型（用来抽象现实世界的数据库 “描述语言”）

    - **关系模型**：用**表（关系）**集合表达数据和数据之间联系；一行为一条记录，一列为一个属性，列名唯一
    - **E-R（实体 - 联系）模型**：用来描述实体对象，以及实体之间的联系，一般用来做数据库前期需求设计
    - **半结构化数据模型**：同一类型数据，可以拥有不一样的属性集合，典型例子：JSON、XML
    - **基于对象的数据模型**：把面向对象思想融入数据库，支持对象、继承等面向对象特性（面向对象数据库）

- `1.3.2` 关系数据模型

    这是使用最广泛的数据模型

    - 组织形式：数据存储在多张二维表里，表 = 关系
    - 表结构：多行多列，列名唯一；一行 = 一条记录（元组），一列 = 属性

- `1.3.3` 数据抽象

    三层抽象由高到低：视图层 $\rightarrow$ 逻辑层 $\rightarrow$ 物理层

    ```mermaid
    graph TD
    V[视图层 view level<br/>子模式：只展示数据库的一部分，面向用户]
    L[逻辑层 logical level<br/>逻辑模式：有哪些表、表之间什么关系]
    P[物理层 physical level<br/>物理模式：数据在磁盘上如何存储]
    V --> L
    L --> P
    ```

    - **物理层**：物理模式，描述底层存储细节：文件、磁盘块、索引怎么存，用户不需要关心
    - **逻辑层**：逻辑模式，描述整个数据库里有哪些表、字段、表之间的关联、完整性约束，是 DBA、开发人员主要关心的一层
    - **视图层**：子模式，只给用户展示数据库里**他需要的一小部分**，屏蔽无关数据；一个数据库可以有很多视图

## `1.4` 数据库语言

- `1.4.1` 数据定义语言 `Data-Definition Language (DDL)`

    **定义、修改数据库的结构 / 模式**，管 “表长什么样、库怎么建”，可用于：

    - 创建、修改数据库，数据库备份管理
    - 创建、修改数据表结构
    - 定义域约束、用户权限

    ```sql
    create table instructor (
        ID        char(5),
        name      varchar(20),
        dept_name varchar(20),
        salary    numeric(8,2)
    );
    ```

    > 常用 DDL 关键字：`CREATE`、`ALTER`、`DROP`

- `1.4.2` 数据操纵语言 `Data-Manipulation Language (DML)`

    **对表里的数据进行查询、增删改，管表里的行数据**，可用于插入、修改、删除、查询数据

    ```sql
    select name
    from instructor
    where dept_name = 'Comp. Sci.';
    ```

    > 常用 DML 关键字：`SELECT`、`INSERT`、`UPDATE`、`DELETE`

## `1.5` 数据库设计

数据库设计是指针对给定应用环境，设计最优数据库模式，建立数据库系统，高效存储数据、满足用户需求，核心工作是数据库模式设计

- `1.5.1` 三大核心设计阶段

    1. **概念设计**：确定要存哪些数据、数据怎么组织到实体；使用 E-R（实体联系）模型，输出 E-R 图

        此时只关心业务含义，不关心用什么数据库

    2. **逻辑设计**：把高层的概念模式（E-R 图）转换成目标数据库支持的数据模型（一般是关系表），得到逻辑模式

    3. **物理设计**：设计底层物理特性，包括文件组织形式、磁盘存储结构、索引等，关心数据在硬盘怎么放

- `1.5.2` 数据库设计的过程

    ```mermaid
    flowchart TD
        A[需求搜集和分析]:::step -->|需求分析阶段| B[设计概念结构]:::step
        B -->|概念设计阶段| C[设计逻辑结构]:::step
        C <--> D[数据模型优化]:::step
        D -->|逻辑设计阶段| E[设计物理结构]:::step
        E --> F[评价设计、性能预测]:::step
        F -.->|方案不达标，回流迭代| C
        F -.->|方案不达标，回流迭代| E
        F -->|物理设计阶段| G[物理实现]:::step
        G --> H[试运行]:::step
        H -.->|发现问题回流修改| C
        H -.->|发现问题回流修改| E
        H -->|数据库实施阶段| I[使用、维护数据库]:::step
        I -->|数据库运行维护阶段| I
    ```

    

- ` 1.5.3` 数据库各级模式的形成过程

    ```mermaid
    graph LR
    D[多个应用需求] -->|综合| C[概念模式]
    C -->|转换| L[逻辑模式]
    L -->|映像| N[内模式（物理模式）]
    L -->|映像| W1[外模式1]
    L -->|映像| W2[外模式2]
    L -->|映像| W3[外模式3]
    ```

    - 外模式：面向单个应用 / 用户视图，一个数据库可以有很多个外模式
    - 概念模式：综合全部业务需求，全局概念 E-R 模型
    - 逻辑模式：全局关系表结构（模式）
    - 内模式：物理存储（物理模式）

- `1.5.4` 概念 / 逻辑 / 物理结构设计

    1. 概念结构设计

        - 输入：需求分析得到的业务需求，拆分为多个子需求 
        - 工作：对数据分类聚集，抽取出：**实体、实体属性、实体的码（主键）、实体间联系（1:1 / 1:n / m:n）** 
        - 流程： 局部子需求 → 局部概念模式 → 合并、消除冲突 → **全局概念模式** 
        - 输出：**E-R 图**

        ```mermaid
        flowchart TD
            R1[子需求] --> E1[局部概念模式]
            R2[子需求] --> E2[局部概念模式]
            R3[子需求] --> E3[局部概念模式]
            E1 & E2 & E3 --> Merge[合并集成]
            Merge --> G[全局概念模式]
        ```

        > 概念结构设计是独立于数据库、独立于硬件的，只描述业务语义

    2. 逻辑结构设计

        - 输入：E-R 图（概念模型） 
        - 三步流程：
            1. 根据转换规则，把 E-R 图转换成**通用数据模型**（关系模型）
            2. 适配为选定 DBMS 支持的数据模型
            3. 使用范式规范化理论做模型优化 
        - 输出：**逻辑模型（表、字段、主键、外键、约束）**

        ```mermaid
        flowchart LR
            ER[基本E-R图] --> T1[转换为<br>一般数据模型]
            T1 --> T2[转化为特定DBMS<br>支持的数据模型]
            T2 --> T3[优化模型<br>（规范化理论）]
            T3 --> LM[逻辑模型]
        ```

        > 逻辑结构设计负责承接概念结构设计的结构，将其转换为适合数据库的结构

    3. 物理结构设计

        - 输入：逻辑模型（已经设计好的表结构）
        - 两步流程：
            1. 确定数据库的物理结构：文件组织、存储方式、索引、分区
            2. 评价物理方案：存取效率、存储开销、维护代价，不合适则回退修改 
        - 输出：**物理模型**，交付数据库实施阶段落地

        ```mermaid
        flowchart LR
            LM[逻辑模型] --> P1[确定数据库的物理结构]
            P1 --> P2[评价数据库物理结构]
            P2 --> PM[物理模型]
        ```

## `1.6` 数据库引擎

三大模块：**存储管理器、查询处理器、事务管理**

- `1.6.1` 存储管理器：负责数据存储、检索、更新

    下属子模块：

    - 权限及完整性管理器：检查权限、约束（主键、外键）
    - 事务管理器：事务相关调度
    - 文件管理器：管理磁盘上的数据文件
    - 缓冲区管理器：管理内存缓冲区，磁盘 $\leftrightarrow$ 内存的数据交换

- `1.6.2` 查询处理器：负责 SQL 解析、执行、检索数据

    下属子模块：

    - DDL 解释器：解析建库建表等 DDL 语句
    - DML 编译器：对查询 DML 语句做语法解析、查询优化，生成执行计划
    - 查询执行引擎：执行查询计划，取出数据

- `1.6.3` 事务管理（保证原子性、一致性、隔离性、持久性 ACID）

    下属子模块：

    - 并发控制管理器：控制多用户并发访问，防止冲突（脏读、不可重复读）
    - 恢复管理器：故障之后，恢复数据到一致状态

## `1.7` 数据库和应用体系结构

- `1.7.1` 数据库系统各个部分及之间的联系

    - 四类用户
        - **初学者用户（出纳员、代理商、Web 用户）**：使用应用界面，不会直接写 SQL
        - **应用程序员**：编写应用程序
        - **老练用户（分析员）**：直接使用查询工具，手写 SQL
        - **数据库管理员 DBA**：使用管理工具，负责数据库运维、权限、备份
    - 自上而下数据流链路
        1. 应用系统（用户入口）：应用界面 / 应用程序 / 查询工具 / 管理工具
        2. 查询处理器
            - 编译器和预处理器、DDL 解释器、DML 编译器、查询执行引擎
            - 作用：接收 SQL，语法检查、优化，生成执行计划
        3. 存储管理器（对接磁盘）
            - 缓冲区管理器、文件管理器、授权和完整性管理器、事务管理器
            - 作用：内存缓冲、磁盘文件读写、权限校验、完整性约束、事务并发与恢复
        4. 磁盘存储：**数据、索引、数据字典、统计数据**
            - 数据字典：元数据（表结构、字段、约束、权限等）

- `1.7.2` 数据库应用系统的结构

    1. 两层架构（Client-Server 两层 C/S）

        ```mermaid
        flowchart LR
            U[user] --> APP[application]
            APP --network--> DB[database system]
        ```

        - Client 端：user + application，业务逻辑放在客户端程序里
        - Server 端：database system（DBMS）
        - 特点：
            - 客户端比较 “重”，应用、业务逻辑都在本地
            - 客户端直接和数据库通信

    2. 三层架构

        ```mermaid
        flowchart LR
            U[user] --> AC[application client]
            AC --network--> AS[application server]
            AS --> DB[database system]
        ```

        **客户端 → 应用服务器（中间层）→ 数据库系统**

        - Client：application client，只做页面展示、简单交互，很轻
        - 中间层 application server：**集中存放业务逻辑**
        - Server 底层：database system
        - 特点：业务逻辑统一在中间服务器，更新时只改服务端，不用批量更新客户端

## `1.8` 数据管理

- `1.8.1` 数据管理技术的发展

    | 对比维度       | 人工管理阶段<br/>(20 世纪 40-50 年代) | 文件系统阶段<br/>(20 世纪 50-60 年代) | 数据库系统阶段<br/>(20 世纪 70 年代至今)    |
    | -------------- | ------------------------------------- | ------------------------------------- | ------------------------------------------- |
    | 核心应用场景   | 计算机主要用于科学计算                | 科学计算 + 业务管理                   | 全行业、大规模数据管理                      |
    | 存储介质       | 磁带、卡片、纸带                      | 磁盘、磁鼓、软盘                      | 磁盘、固态硬盘等大容量存储                  |
    | 数据留存       | 数据不保存在机器中                    | 数据可长期保存在外存                  | 数据持久化存储，面向全组织                  |
    | 管理方式       | 无专门软件，程序自带<br/>数据处理逻辑 | 操作系统文件系统管理                  | DBMS 数据库<br/>管理系统统一管理            |
    | 数据与程序关系 | 一组数据对应一个程序，完全绑定        | 数据可被多个程序复用，<br/>但耦合度高 | 数据与程序高度独立<br/>（物理 + 逻辑独立）  |
    | 数据冗余与共享 | 无共享，冗余极大                      | 共享性差，冗余度高                    | 共享性高，冗余度可控、易扩充                |
    | 数据联系       | 数据之间无关联                        | 数据间联系弱，文件独立                | 支持复杂数据结构与数据关联                  |
    | 控制能力       | 无统一控制                            | 无统一安全、并发、完整性控制          | 统一的安全、完整性、<br/>并发、故障恢复控制 |
    | 最小存取单位   | 程序自定义，无统一标准                | 以文件 / 记录为单位                   | 最小存取单位是数据项                        |

- `1.8.2` 数据库系统的地位

    - 数据库技术产生于 20 世纪 60 年代末，是数据管理的最新技术，是计算机科学的重要分支
    - 数据库系统与操作系统同属计算机系统的**基础软件**，也称为系统软件、平台软件，是信息化系统的底层支撑
    - 数据库技术是信息系统的核心和基础，是信息化建设的基础设施
    - 数据库的建设规模、数据信息量大小和使用频度，已成为衡量一个国家信息化程度的重要标志

- `1.8.3` 数据库技术的发展回顾

    - **技术三代演变**：层次 / 网状数据库系统 → 关系数据库系统 → 新一代数据库系统家族（分布式、NoSQL、NewSQL、HTAP 等）
    - **学术领域成就**：造就了五位图灵奖得主，分别是 C. W. Bachman、E. F. Codd、James Gray、M. Stonebraker、D. DeWitt
    - **学科建设**：发展成为一门成熟的计算机基础学科，以数据模型和 DBMS 核心技术为主，覆盖理论、系统、应用多个方向，内容丰富、领域宽广
    - **产业价值**：形成了规模庞大的软件产业，包含 DBMS 内核产品、周边工具、行业应用解决方案等完整生态

- `1.8.4` 三位核心图灵奖得主及其贡献

    1. Charles W. Bachman —— 网状数据库之父

        - 1960 年为通用电气公司打造了世界上第一个网状数据库系统 IDS

        - 推动并促成了数据库行业标准 DBTG 报告（DataBase Task Group）的制定，奠定了网状数据库的规范基础

        - 在数据库技术的产生、发展与推广应用中发挥了巨大作用

        - 1973 年获得图灵奖；1983 年创立 Bachman Information System 公司

    2. Edgar F. Codd —— 关系数据库之父

        - 英国牛津大学数学专业本硕毕业，早年在 IBM 从事操作系统与自动机理论研究；40 岁后进修计算机专业，1965 年获博士学位

        - 20 世纪 60 年代后期转向数据库研究，**1970 年提出关系模型概念**，是关系数据库的理论基石

        - 1981 年获得图灵奖，1984 年从 IBM 退休

        - 其提出的关系模型是当今绝大多数商用数据库的理论基础

    3. James (Jim) Gray —— 数据库技术与事务处理专家

        - 1944 年出生，加州大学伯克利分校计算机科学博士，先后任职于贝尔实验室、IBM、Tandem、DEC 等企业

        - 在数据库事务处理领域做出开创性贡献，在学术原型到商业产品的工程落地方面具备领袖地位

        - 1998 年获得图灵奖，其研究成果是数据库 ACID 特性、并发控制、故障恢复的重要理论与工程基础

## `1.9` 我国数据库软件卡脖子问题

- `1.9.1` 市场现状

    - 全球主流商用数据库以美国厂商为主：Oracle、MySQL 均隶属于甲骨文公司；此外 IBM、微软、Teradata 等美国厂商占据了全球大部分市场份额
    - 国内数据库市场长期被海外厂商主导，国产数据库早期市场份额占比极低，且主要集中在非核心场景
    - 国产数据库的痛点：早期产品在稳定性、性能、生态完善度上与海外头部产品存在差距，银行、电力等对稳定性要求极高的核心业务场景，长期优先选择海外商用数据库
    - 课件数据显示：国产数据库阵营包含达梦、人大金仓、神舟通用、南大通用等厂商，整体处于逐步追赶、替代的过程中

- `1.9.2` 主流国产数据库产品

    1. OceanBase

        - 定位：蚂蚁集团完全自主研发的原生分布式关系数据库，深耕金融级场景

        - 落地：支撑多家银行、保险等金融客户核心系统，通过 TPC-C 基准测试，经受支付宝双 11 高并发场景验证
        - 核心优势：
            - 数据分区存储，基线数据落盘、增量数据存内存，数据压缩率高，存储成本低
            - 基于普通服务器集群构建，硬件成本低
            - 多副本 Paxos 协议同步，高可用，少数节点故障不影响服务
            - 节点可弹性扩容，算力接近线性增长
            - 支持多地部署，无单点瓶颈

        - 局限：对 MySQL/Oracle 语法做兼容，但仍存在迁移成本

    2. TiDB

        - 定位：PingCAP 研发的开源分布式 HTAP 数据库，融合关系型数据库与 NoSQL 的特性
        - 核心优势：
            - 高度兼容 MySQL 协议，业务从 MySQL 迁移改造成本低
            - 支持水平弹性扩缩容，通过增减节点调整算力
            - 支持分布式事务，满足 ACID 强一致性
            - 云原生架构，支持 Kubernetes 容器化部署，同时支持 OLTP 在线事务与 OLAP 分析处理

        - 局限：存储引擎、优化器仍在迭代，单一方案难以同时满足极致 OLTP 性能与极致 OLAP 性能

    3. openGauss

        - 定位：华为开源的企业级关系型数据库，内核基于 PostgreSQL 深度改造，融合华为多年数据库技术积累
        - 核心优势：
            - 高性能：面向多核架构的并发控制、全链路智能优化
            - 高可用：支持主备同步 / 异步 / 级联部署，秒级故障切换，数据一致性强
            - 高安全：全密态计算、访问控制、数据加密、审计等全链路安全能力
            - 易运维：内置 AI 参数调优、慢 SQL 诊断等智能运维特性
            - 开源开放，依托社区生态持续迭代

        - 局限：部分编译版本部署复杂，依赖项多且版本偏旧

    4. GaussDB

        - 定位：华为推出的企业级商用分布式数据库，是华为数据库技术的商业化产品，内核与 openGauss 同源

        - 核心优势：
            - 支持行存、列存，适配混合负载场景
            - 高可用、高安全、高性能，适配国产鲲鹏芯片与信创生态
            - 覆盖政企、金融等核心业务场景，提供商业级技术支持

    5. 达梦数据库

        - 定位：达梦公司自主研发的国产数据库，拥有完全自主知识产权
        - 核心优势：
            - 高通用性：兼容 Windows、Linux、Unix 等多类操作系统，支持主流开发语言
            - 高可靠：自带数据守护组件，主备切换快，服务可用性高
            - 高兼容：高度兼容 Oracle 语法，存储过程、函数迁移成本低
            - 全生态适配：支持 x86、ARM、鲲鹏等国产 CPU，适配国产操作系统
            - 操作友好：中文界面与文档，符合国内用户使用习惯

        - 应用场景：广泛应用于公安、政务、司法、审计、住建、国土、应急等政企领域
