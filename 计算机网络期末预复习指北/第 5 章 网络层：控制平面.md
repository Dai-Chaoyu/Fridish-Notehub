# 第 5 章 网络层：控制平面

## `5.1` 导论

- `5.1.1` 每 - 路由器 `Per-router` 控制平面

    1. 架构特点：在每一个路由器中的单独路由器算法元件，在控制平面进行交互

        - **控制平面完全分布式**：每一台路由器都自带完整的 “路由算法 `Routing Algorithm` ”，独立运行路由协议（如 OSPF、BGP）

        - **路由器间直接交互**：所有路由器的控制平面之间，通过路由协议直接交换信息，共同计算全网路由

        - **数据平面仅执行转发**：每台路由器的本地转发表 `local forwarding table` 由自身的路由算法生成，数据平面只负责查表转发

    2. 优缺点

    | 优点                           | 缺点                                   |
    | ------------------------------ | -------------------------------------- |
    | 无单点故障，网络健壮性高       | 配置复杂，全网策略统一管理困难         |
    | 分布式计算，早期网络扩展性尚可 | 设备厂商强绑定，依赖硬件实现，灵活性差 |
    | 无需额外控制器，架构简单       | 路由协议复杂，大规模网络收敛慢         |

- `5.1.2`  SDN 方式

    1. 架构特点：一个集中的（通常是远程的）控制器与本地控制代理（CAs） 交互

        - **控制平面集中化**：全网的路由计算、策略管理，都由一台（或集群）远程控制器 `Remote Controller` 统一完成

        - **路由器仅保留数据平面 + 轻量代理**：传统路由器的路由算法被移除，只保留控制代理  `Control Agent (CA)` ，负责与控制器通信、接收转发表并执行转发

        - **控制与数据完全分离**：控制平面的所有决策都由控制器下发，数据平面的设备只负责 “无脑转发”，不参与路由计算

    2. 优缺点

    | 优点                                     | 缺点                                                         |
    | ---------------------------------------- | ------------------------------------------------------------ |
    | 全网策略统一管理，配置灵活，支持自动化   | 控制器可能成为单点故障，需集群保障高可用                     |
    | 设备与控制解耦，可使用白盒设备，降低成本 | 控制器与设备间的通信延迟可能影响网络收敛                     |
    | 支持自定义网络功能，适合云数据中心等场景 | 依赖 OpenFlow 等南向协议（平台 / 网关 $\rightarrow$ 终端 / 下位设备），<br />早期兼容性问题较多 |

## `5.2` 路由选择算法

### `5.2.0` 路由与路由选择算法

- `5.2.0.1` 路由与路由协议

    1. 路由的核心设计思想：以 “子网” 为计算单位

        - **网络 - 网络的路由 = 路由器 - 路由器之间的路由**

            路由器的路由计算目标，是**子网到子网的路径**，而不是 “主机到主机” 的路径，有效减少了路由计算的规模

        - 路由的输入：网络的图抽象的拓扑、边的代价、源节点

        - 路由的输出：源节点的汇集树（此节点到所有其它节点的最优路径形成的树，最优化原则 `Optimality Principle`）

    2. 路由协议

        路由协议的本质任务是：**在由路由器组成的网络中，为数据包从发送方到接收方找到一条 “好的路径”**

        - 路径 `Path`：数据包从给定的初始源主机遍历到最终目的主机的路由器序列
        - 好 `good`：最少的“成本” ， 最快的“速度” ， 最少的“拥堵”

    3. 不同层级的转发分工（网络层 vs 链路层）

        - **路由器 ↔ 主机之间的通信：由链路层解决（MAC 地址）**

            同一个局域网内，主机和网关路由器的通信，靠 MAC 地址完成二层转发，不属于路由协议的工作范畴

        - **路由器 ↔ 路由器之间的通信：由网络层（路由协议）解决（IP 地址）**

            **跨网络的路径选择，是路由协议的核心任务**

        - 一个关键结论：**到达某个子网的网关路由器，就等同于到达了这个网络**；后续子网内的转发，由链路层完成，不需要路由协议操心

- `5.2.0.2` 路由选择算法

    1. 路由选择算法是**网络层软件的核心部分**，负责实现路由功能：

        - 收集网络拓扑、链路状态信息
        - 计算不同子网之间的最优路径
        - 生成并维护路由表，指导路由器转发数据包

    2. 路由选择算法的原则

        - **正确性 `correctness`**：算法必须是正确的和完整的

            - 正确：使分组一站一站接力，正确发向目标站
            - 完整：目标所有的站地址，在路由表中都能找到相应的表项（没有处理不了的目标站地）

        - **简单性 `simplicity`**：算法在计算机上应简单

            最优但复杂的算法，时间上延迟很大，不实用，不应为了获取路由信息增加很多的通信量

        - **健壮性 `robustness`**：算法应能适应通信量和网络拓扑的变化

            - 通信量变化，网络拓扑的变化算法能很快适应
            - 不向很拥挤的链路发数据，不向断了的链路发送数据

        - **稳定性 `stability`**：产生的路由不应该摇摆

            网络拓扑或负载轻微波动时，路由路径不会来回切换，避免转发路径忽变、丢包、时延抖动

        - **公平性 `fairness`**：对每一个站点都公平

            网络中**每个站点 / 用户 / 业务**都能合理分配带宽、路由资源、转发机会，不会出现部分站点抢占资源、另一部分被挤占饿死

        - **最优性 `optimality`**：

            - 某一个指标的最优（如时间上，费用上等指标），或综合指标
            - 实际上，获取最优的结果代价较高，可以是次优的

    3. 路由算法分类

        - 按是否读取全局路由信息分类
            - 全局路由算法：所有的路由器拥有完整的拓扑和边的代价信息 $\rightarrow$ 链路状态 `link state` 算法
            - 分布式路由算法：路由器只知道与它 `有物理连接关系的邻居路由器` 和 `到相应邻居路由器的代价值`，迭代地与邻居交换和计算路由信息 $\rightarrow$ 距离向量 `distance vector` 算法
        - 按路线变化速度的快慢分类
            - 静态算法（非适应算法 `non-adaptive algorithm`），路由随时间变化缓慢，事先计算好路由表，不能适应网络拓扑和通信量的变化
            - 动态算法（自适应路由选择 `adaptive algorithm`），路由周期性更新或根据链路代价进行更新，能够适应网络拓扑和痛心凉的变化

### `5.2.1` 链路状态 (LS) 路由选择算法

- `5.2.1.1` 链路状态路由选择算法的工作过程

    1. 配置链路状态路由选择算法**路由的工作过程**
        1. 各点通过各种渠道获得整个网络拓扑、网络中所有链路的代价等信息（这部分与算法无关，属于协议实现的部分）
        2. 使用 LS 路由算法，计算本站点到其他站点的最优路径（汇集树），得到路由表
        3. 按照路由表，以数据报 `datagram` 方式转发数据包（路由算法的使用结果，由网络层完成）
    2. 链路状态路由选择算法的基本工作过程
        1. 发现邻居节点，获取对方地址
        2. 测量到邻居节点的链路代价（如延迟、开销等）
        3. 组装一个链路状态分组，描述它到相邻节点的代价情况
        4. 将分组通过泛洪 `flooding` 的方法把链路状态转发给除了接收端口之外的所有接口，让所有路由器收到一样的链路状态分组
            - 泛洪的问题：广播风暴与环路，可能在环路中无限转发，浪费网络带宽
            - 解决方法：`Age` 字段（每经过一次转发就递减（或按时间递减），当 Age 变为 0 时，分组被丢弃）与 `Seq` 字段（每个路由器为自己发出的链路状态分组分配递增的序列号，如果收到重复序列号的分组，直接丢弃）
        5. 通过 `Dijkstra 算法` 找出最短路径
    3. 链路状态路由的典型应用协议
        1. 开放最短路径优先 `OSPF` ：是互联网中最主流的内部网关协议（IGP）
        2. 中间系统到中间系统 `IS-IS` ：最初为 OSI 网络体系设计，后来被改造支持 TCP/IP

- `5.2.1.2` 核心思想：Dijkstra 算法

    | 符号     | 含义                                        |
    | -------- | ------------------------------------------- |
    | $c_{ij}$ | 节点i到节点j的链路代价（初始非相邻节点为∞） |
    | $D(v)$   | 源节点到节点v的当前路径代价                 |
    | $p(v)$   | 源节点到节点v的路径前序节点（上一跳）       |
    | $N′$     | 已确定最优路径的 “永久节点” 集合            |

    1. `Dijkstra` 算法的执行步骤
        1. 初始化
            - 源节点加入永久集合，其余节点为 “临时节点”
            - 源节点的直接邻居，节点代价 $D(v)$ 设为链路代价 $c(s,v)$ ，其余节点代价设为 ∞
        2. 迭代循环
            1. **选永久节点**：从所有临时节点中，选出节点代价 $D(w)$ 最小的节点 $w$ ，将其标记为永久节点
            2. **更新邻居代价**：对 $w$ 的所有临时邻居节点 $v$：
                - 若 $D(v)>D(w)+c(w,v)$，则更新：$D(v)=D(w)+c(w,v)，p(v)=w$
                - 否则不更新
            3. 重复上述过程，直到所有节点都成为永久节点
    2. 关于 Dijkstra 算法的讨论
        1. 算法复杂度 `algorithm complexity` 方面，每一次迭代需要检查所有不在永久集合 $N'$ 中的节点，时间复杂度 $O(n^2)$，利用最小堆（优先队列）来快速获取代价最小的节点可以优化到 $O(m\log n)$ （$n$ 个节点、$m$ 条链路）
        2. 消息复杂度 `message complexity` 方面，每个路由器必须广播它的链路状态信息给其他 $n$ 个路由器，每个路由器的消息经过 $O(n)$ 条链路：总体消息复杂度 $O(n^2)$

### `5.2.2` 距离向量 (DV) 路由选择算法

- `5.2.2.1` 距离向量路由选择算法的工作过程

    1. 距离向量路由选择算法**路由的工作过程**

        1. 各路由器通过直连检测，获取自身直连网络信息，初始化本地路由表（包含**目标节点、途径的邻居节点、代价**等信息，这部分与算法无关，属于协议实现的部分）
        2. 使用 DV 路由算法，结合邻居传递的路由信息，计算本路由器到其他所有目的网络的最优路径，完善本地路由表
        3. 按照路由表，以数据报 `datagram` 方式转发数据包（路由算法的使用结果，由网络层完成）

    2. 距离向量状态路由选择算法的基本工作过程

        1. 识别直连邻居节点，建立邻居关系并获取对方路由器地址

        2. 更新路由信息

            1. 对于相邻节点，**实测**到每个邻居节点的链路代价（如跳数 `hops` 、延迟 `delay` 、队列长度等）

                $\rightarrow$ 定期测量到相邻节点的代价

            2. 对于不相邻节点，**根据相邻站点声明的到目标节点的代价**，找到经过一个相邻节点到达目标节点的**最小代价**

                $\rightarrow$ 定期与相邻节点交换路由表

        3. 整理本地路由表信息，形成包含目的节点、下一跳的路由条目（途径的邻居节点）、代价的集合

        4. 将本地完整路由表，发送给所有直连邻居，确保邻居能获取自身的路由信息

- `5.2.2.2` 核心思想：贝尔曼 - 福特方程 `Bellman-Ford Equation`

    1. 方程定义

        - 设：\( D_x(y) \)：节点 \( x \) 到目标节点 \( y \) 的**最小路径代价**（距离），\( c_{x,v} \)：节点 \( x \) 到它的邻居节点 \( v \) 的直接链路代价

            则方程为：
            \[
            D_x(y) = \min_{v} \{ \, c_{x,v} + D_v(y) \, \}
            \]

            - \( c_{x,v} \)：当前节点 \( x \) 走到邻居 \( v \) 的直接代价
            - \( D_v(y) \)：邻居 \( v \) 已经算好的、到目标 \( y \) 的最小代价

        - 对所有邻居 \( v \)，计算“从 \( x \) 走到 \( v \)，再走 \( v \) 到目标的最短路径”的总代价，取其中最小的那个，就是 \( x \) 到目标的新最短路径代价

    2. 核心思路

        1. **邻居间的信息交换**：每个节点会把自己的「距离向量（到所有目标节点的距离估计值）」，定时或在自己的距离向量变化时，发送给所有邻居
        2. **本地更新逻辑**：节点收到邻居的距离向量后，用 `Bellman-Ford` 方程更新自己的距离向量

        3. **收敛特性**：节点的距离向量估计值，会随着迭代更新，最终收敛到实际的最短路径代价

    3. 执行流程

        这是一个**异步、事件驱动的迭代过程**，节点的行为由两个事件触发：
        1.  **等待触发事件**：两种情况会唤醒节点
            - 本地链路的代价发生了变化（比如链路断了、延迟变了）
            - 收到邻居发来的新的距离向量更新报文
        2.  **重新计算距离向量**：用 `Bellman-Ford` 方程，更新到所有目标节点的距离估计值
        3.  **判断并通告邻居**：如果自己的距离向量发生了变化，就把更新后的向量发送给所有邻居；如果没变化，就不主动发消息

- `5.2.2.3` 距离向量路由的特性

    1. `好消息传得快`

        每一轮路由信息交换，“好消息” 就能向前推进一个路由器

    2. `坏消息传得慢`

        - 当目标节点失效时，路由器会错误地依赖彼此的路由信息，形成 “互相抬价” 的循环，距离值只能一轮轮缓慢增加，直到达到无穷大才确认目标不可达

            具体地讲，对于 `A - B - C - ...` 这样的链路：

            - **故障发生，直连失效**

                A 与 B 的链路断开，B 的直连路由失效，它失去了到 A 的直接路径

            - **错误依赖，循环误导**

                B 向邻居 C 询问，C 的路由表中写着 “到 A 的距离是 2（下一跳是 B）”，于是回复 B：“我到 A 的距离是 2”

                B 不知道这个路径的下一跳就是自己，于是错误更新：$2+1=3$，认为可以通过 C 到达 A

            - **距离递增，缓慢收敛**（计数到无穷问题 `Count-to-Infinity`）

                下一轮交换中，C 收到 B 的更新 “到 A 的距离是 3”，于是 C 也错误更新：$3+1=4$

                之后 `B - C - B ...` 每一轮交换，距离都会 $+ 1$，直到达到预设的无穷大阈值，才会判定 A 不可达

        - 解决方法

            1. 水平分裂 `split horizon` 算法

                路由器**绝不把 “从某个邻居学到的路由” 再发回给这个邻居**，避免给对方造成误导

                - 逻辑：我从你这学到的路，绝不 “回传” 给你，防止你误以为能通过我绕路走
                - 作用：切断了 “互相抬价” 的直接环路，解决两节点间的计数到无穷问题

            2. 毒性逆转 `poisoned reverse` 算法

                它是水平分裂的**强化版**：不仅不回传路由，还会向 “给你路由的邻居”**谎称该路由已失效（距离设为无穷大）**，直接打破对方的错误幻想

                - 逻辑：我知道你是我到目标的下一跳，所以我直接告诉你：“我到目标的距离是无穷大”，断了你 “绕路通过我到达目标” 的念头
                - 作用：比单纯水平分裂更决绝，能更快让对方确认目标不可达，收敛更快

            | 算法     | 核心动作                               | 效果                                 |
            | -------- | -------------------------------------- | ------------------------------------ |
            | 水平分裂 | 从你那学的路，我就不发给你             | 避免回传，减少误导                   |
            | 毒性逆转 | 从你那学的路，我**故意发成无穷大**给你 | 主动 “毒杀” 可能的错误路径，收敛更快 |

| 对比维度 | **LS（链路状态算法）** | **DV（距离向量算法）** | 优势方 |
| :--- | :--- | :--- | :--- |
| **消息复杂度** | 复杂度为 $O(N\times E)$<br/>每个节点向全网泛洪自身链路状态，消息量大 | 仅与邻居交换完整路由表<br/>传播范围小，消息开销低 | DV 胜出 |
| **收敛时间** | 时间复杂度 $O(n^2)$，收敛速度快<br/>但可能出现路由震荡 | 收敛较慢<br/>存在路由环路、计数到无穷问题 | LS 胜出 |
| **健壮性** | 错误信息仅影响局部，影响范围小<br/>（节点仅通告自身链路状态，独立计算路由） | 错误路由信息会随路由表扩散至全网<br/>更新延迟高，影响范围大 | LS 胜出 |
| **信息传播逻辑** | 局部的链路信息，向**全局泛洪传播** | 全局的路由信息，仅在**邻居间局部传播** | - |
| **典型应用协议** | OSPF | RIP | - |

## `5.3` 因特网中自治系统内部的路由选择

- `5.3.1` 平面路由与层次路由

    1. 平面路由

        **一个网络中所有的路由器的地位一样**，所有路由器都要参与全网的路由计算和信息交换

        - **规模问题：路由信息的存储、传输和计算代价巨大**
            - DV 算法：距离矢量会变得极其庞大，还容易出现不收敛的问题
            - LS 算法：数百万节点的链路状态泛洪、存储和最短路径计算，对路由器和链路都是灾难
        - **管理问题：无法满足多组织的需求**
            - 不同网络所有者想按自己的规则管理内部网络
            - 不想对外暴露自己的拓扑细节
            - 同时又要和其他网络互联

    2. 层次路由与自治系统 `Autonomous Systems(AS)`

        将整个互联网分成多个区域的自治系统 AS，每个 AS 用 `AS Number (ASN)` 唯一标识，路由因此变成了两个层次路由

        - **AS 内部路由 `intra-AS routing`**：在同一个 AS 内部，用内部网关协议 `IGP` 计算路由，来决定 **AS 内部**目的地的转发路径（当数据包的目标地址在同一个 AS 内时，路由器用内部路由计算出的路径来转发），只关心内部网络

            | 常见的 IGP | 核心算法       | 关键特点                                                     |
            | ---------- | -------------- | ------------------------------------------------------------ |
            | **RIP**    | 距离矢量（DV） | 经典 DV 协议，每 30 秒交换一次路由信息；现在基本不再大规模使用 |
            | **EIGRP**  | 距离矢量（DV） | Cisco 私有协议，2013 年公开标准；优化了 DV 的收敛速度和开销  |
            | **OSPF**   | 链路状态（LS） | 开放标准，基于链路状态算法；是目前最主流的 IGP，支持大型网络 |
            | **IS-IS**  | 链路状态（LS） | 和 OSPF 原理几乎一样，是 ISO 标准而非 RFC 标准，运营商网络用得较多 |

        - **AS 之间路由 `inter-AS routing`**：在不同 AS 之间，用外部网关协议（EGP，比如 BGP）交换路由，由网关路由器 `Gateway Router` （内部路由的边缘路由器）负责，只关心如何到达其他 AS，不关心对方内部细节

            对于涉及 AS 外部目的地的转发，需要先通过 inter-AS 路由，找到到达目标 AS 的出口网关路由器；再通过 intra-AS 路由，把数据包转发到这个出口网关

        $\rightarrow$ 解决了规模问题和管理问题

        - 解决「规模问题」
            - 对于**AS 内部**，每个 AS 内部只需要处理有限数量的路由器 / 子网，路由计算、存储和交换的成本可控；如果节点太多，还可以进一步分割 AS，保持内部规模可控
            - 对于**AS 之间**，每个 AS 在整个互联网里只被当作**一个 “节点” 来对待**，新增一个 AS 对其他 AS 来说，只是路由表里多了一个 “如何到达这个 AS” 的表项，让网络规模扩大时路由性能不会明显下降，带来了极强的可扩展性
        - 解决「管理问题」
            - 各 AS 可以自主选择内部路由协议、配置路由策略，互不干涉
            - AS 的内部拓扑、地址规划等细节，不会对外暴露，满足了组织的管理自治和安全需求

- `5.3.2` 开放最短路径优先协议 `OSPF` 

    1. 一种链路状态 `LS` 路由协议，用于**同一个自治系统内的路由计算**

    2. 通告信息包含每个邻居路由器的链路状态表项，报文**直接封装在 IP 数据报中**，不依赖 UDP/TCP 协议

    3. 核心优势

        - **安全性**：所有 OSPF 报文都支持身份验证，可防止恶意攻击

        - **支持等价路由**：允许多条代价相同的路径同时存在，实现流量负载均衡（RIP 只能用一条路径）

        - **多播支持**：对单播和多播路由都有良好支持，新增了专门的链路状态通告类型

        - **支持层次化网络**：大型网络可划分为多个区域，降低路由计算开销

    4. 层次性的 OSPF 路由

        为了适配大型网络，OSPF 引入了 **区域 `Area`** 的概念，将网络分为两层

        - **骨干区域**：所有非骨干区域都必须连接到骨干区域，负责区域间路由的传递

        - **非骨干区域：负责本区域内的路由计算和数据转发

        | 角色                          | 作用                                                     |
        | ----------------------------- | -------------------------------------------------------- |
        | **内部路由器**                | 所有接口都在同一个区域内，只维护本区域的拓扑信息         |
        | **骨干路由器**                | 接口位于骨干区域内，负责骨干区域内的路由计算             |
        | **区域边界路由器 (ABR)**      | 连接骨干区域和非骨干区域，汇总本区域路由并发布到其他区域 |
        | **自治系统边界路由器 (ASBR)** | 连接不同的 AS，引入外部路由信息                          |

        $\rightarrow$ 链路状态通告仅在本区域内泛洪，大幅减少全网路由信息交互量；非骨干区域内的路由器无需维护全网拓扑，只需知道通过 ABR 就能到达其他区域，降低设备负担

## `5.4` 边际网关协议 `Border Gateway Protocol (BGP)`

边际网关协议 BGP 是目前**互联网上唯一的域间路由协议**，让不同的 AS 互相通告 “我这里有哪些网段”，从而实现全网互通

- `5.4.1` BGP 给每个 AS 提供两种方式获取 / 传递路由：

    1. **eBGP（外部 BGP）**：从别的 AS 那里获取可达信息
    2. **iBGP（内部 BGP）**：把外部学到的路由，传递给 AS 内部的所有路由器

    特别地，AS 的网关路由器，会同时运行 eBGP 和 iBGP 协议，一边和外部 AS 通信，一边把信息同步给内部

- `5.4.2` BGP 的路由算法

    BGP 采用基于改进的距离向量路由算法（额外包括到达各个目标网络的详细路径，如 AS 序号的列表）能够避免简单 DV 算法的路由环路问题

    - 例如，当 AS3 的网关路由器，向 AS2 的网关路由器通告 “我能到网段 X” 时，会带上路径信息 `AS3,X`

        语义上，这表示：

        1. AS3 向 AS2 承诺，它可以向子网 X 转发数据报
        2. 如果 AS3 要向 X 发送数据报，AS2 的网关路由器是 AS3 网关路由器关于 X 的下一跳

    - 这个路径信息，会一直传递下去，最终让全网的路由器都知道 “去 X 网段要走哪条路”

- `5.4.3` BGP 会话（路径通告）

    两个 BGP 路由器会先建立一个 **TCP 连接（端口 179）**，然后交换 BGP 报文，通告向不同目标子网前缀的 “路径”

    - 目标子网前缀 `Prefix` + 这条路由的各种属性 `Attributes` = `"Router"`

    - 两个核心路径属性

        1. AS 路径 `AS-PATH`：这条路由从源到当前 AS，所经过的所有 AS 号列表，比如 `AS2 - AS3 - AS5`

            - 核心作用
                1. **防环**：路由器收到路由时，如果发现自己的 AS 号在 AS-PATH 里，就知道出现了环路，直接丢弃这条路由
                2. **选路参考**：BGP 会优先选择 AS-PATH 更短的路径（经过的 AS 更少）

            - **规则**：当你把路由转发给其他 AS 时，必须把自己的 AS 号加到 AS-PATH 的最前面

        2. 下一跳 `NEXT-HOP`：告诉接收方，到这个目标前缀，下一跳应该通过哪个链路转发

            - 核心作用：当两个 AS 之间有多条链路时，NEXT-HOP 会明确指定用哪条链路转发，避免路由混乱

        3. 其他属性

            还有比如路由偏好指标（Local Pref）等，用来控制 BGP 的选路优先级，让管理员可以人为干预路由选择

- `5.4.4` **基于（商业）策略的路由**（路径选择）

    BGP 和传统路由协议最大的区别，就是它不是只看 “跳数 / 距离”，而是**基于策略做路由决策**

    1. 输入策略（接收 / 过滤路由）

        当网关路由器收到一条路由通告时，可以自己决定要不要接收它

        - 比如：不想让流量经过某个 AS，就直接过滤掉来自这个 AS 的路由
        - 或者：已经有了一条更优的路由，就拒绝接收新的同目标前缀的路由

    2. 输出策略（向邻居通告路由）

        路由器也可以决定，要不要把收到的路由再发给其他邻居

        - 比如：只把某些客户的路由发给特定的合作运营商，不发给竞争对手

    3. 策略的底层逻辑

        这些策略，本质上是运营商根据**经济、商业、政治**等因素制定的规则，比如：

        - 不想给竞争对手免费中转流量
        - 优先把流量发给付费更高的合作方
        - 拒绝某些地区的路由，避免合规风险

    4. 示例

        1. 热土豆路由 `Hot Potato Routing`

            核心思想是，**AS 内的路由器选择「到出口网关的内部路径代价最小」的路径，尽快将流量 “扔出” 本 AS**，就像手里的热土豆，越快脱手越好，完全不关心流量离开本 AS 后，在外部网络的路径是否最优

        2. ISP 流量中转控制

            互联网服务提供商 `ISP` 通常**只愿意承载 “自己客户的流量”**，不愿意成为其他 ISP 之间的 “免费中转节点”

            因此，ISP 会通过 BGP 的路径通告策略，**不向非客户对等体通告中转路径**

        3. 多宿主网络的策略控制

            - 概念补充：

                桩网络 / 存根网络 `Stub Network`：仅连接到一个 ISP 的终端网络，无中转流量需求

                多宿主网络 `Multi-homed Network`：同时连接到多个 ISP 的网络，这类网络通常也不想成为 ISP 之间的中转节点

            多宿主网络 X 会通过 BGP 的路径通告控制，**不向连接的 ISP 通告可作为中转的路径**

- `5.4.5` 内部网关协议（IGP）与外部网关协议（EGP）的对比 

    | 对比维度     | 内部网关协议（IGP，如 OSPF/RIP）                          | 外部网关协议（EGP，如 BGP）                                  |
    | ------------ | --------------------------------------------------------- | ------------------------------------------------------------ |
    | **核心目标** | 单一管理域内的**最优路径转发**，以性能为核心              | 不同管理域间的**策略可控通信**，以策略和稳定性为核心         |
    | **策略控制** | 无商业策略需求，仅关注技术层面的最优路径                  | 强策略驱动，支持基于商业 / 运营需求的路由过滤、路径选择      |
    | **规模考量** | 路由表规模可控，可通过区域划分（如 OSPF 区域）优化        | 需支撑全网路由转发，路由表规模大，依赖路由聚合、汇总控制规模 |
    | **性能需求** | 要求快速收敛（秒级甚至毫秒级），适应拓扑变化              | 收敛速度慢（分钟级），牺牲速度换取稳定性，避免全网路由震荡   |
    | **环路防止** | 基于拓扑（如最短路径优先算法 SPF 算法）或距离向量机制防环 | 依赖 AS_PATH 属性防环（丢弃包含自身 AS 号的路由）            |

## `5.5` SDN 控制平面

- `5.5.1` 传统互联网网络层的实现与局限

    传统网络设备（如路由器）采用**垂直集成**的封闭架构，存在明显局限：

    - **设备内部紧耦合**：单个路由器同时包含三类组件，且三者绑定：
        - 专用交换硬件（仅支持特定厂商的转发逻辑）
        - 私有操作系统（如思科 IOS，与硬件深度绑定）
        - 标准协议的私有实现（IP、OSPF、BGP 等协议的厂商定制版本，兼容性差）
    - **额外功能依赖 “中间盒”**：防火墙、负载均衡、NAT 等功能需要单独部署硬件设备，网络架构复杂，管理和维护成本高
    - **控制平面僵化**：控制逻辑与转发逻辑紧耦合，无法根据业务需求灵活调整，催生了 2005 年后对 “重新思考互联网控制平面” 的探索

- `5.5.2` 传统路由在流量工程中的局限

    1. 场景 1：按源地址区分不同流量的转发路径

        - **业务需求**：希望自定义节点 u 到 z 的流量走路径 `u→v→w→z`，x 到 z 的流量走路径 `x→w→y→z`

        - **传统路由的问题**：

            传统 IP 路由是 **“面向目标” 的转发 **—— 路由器仅根据目的 IP 地址决定转发端口，不考虑源 IP 或流量类型

            若通过调整链路代价（权重）实现，会影响所有去往同一目标的流量，无法针对不同源的流量单独控制

        - 本质问题：**控制平面的策略无法灵活定义，仅靠链路权重无法实现精细化调度**

    2. 场景 2：同一源目对的流量负载均衡（多路径转发）

        - **业务需求**：节点 u 到 z 的流量需要负载均衡，分为 `u→v→w→z` 和 `u→x→y→z` 两条路径

        - **传统路由的问题**：

            传统路由协议（如 OSPF）仅支持 “等价路由 `ECMP`”，但需要链路代价完全相等，且转发是基于哈希的随机分配，无法精确控制流量比例

            若要实现非等价负载均衡，需要修改路由算法并在全网所有路由器部署，成本极高，几乎不可行

        - 本质问题：**分布式路由算法无法支持全局统一的精细化流量调度**

    3. 场景 3：同一节点对不同类型流量的差异化转发

        - **业务需求**：节点 w 需要对不同流量采用不同的转发路径（如有的走 `w→y→z`，有的走 `w→z`）

        - **传统路由的问题**：

            传统路由（链路状态 / 距离矢量算法）仅基于目的地址转发，路由器无法根据流量的类型（如端口号、协议类型、业务优先级）区分转发路径

        - 本质问题：**数据平面的转发规则由分布式算法决定，无法根据全局业务需求灵活编程**

- `5.5.3` SDN 架构的特点

    1. **流表驱动的数据平面**

        交换机 / 转发设备基于 “流 `flow`” 进行转发，遵循 “匹配 + 行动  `match + action` ” 模型（典型实现为 OpenFlow）

        - 匹配：按数据包的源 / 目的 IP、端口、协议类型等字段匹配流表条目
        - 行动：匹配成功后执行转发、丢弃、修改字段等操作

    2. **控制平面与数据平面分离**

        - 数据平面：仅负责按流表转发数据包，无路由计算、策略决策能力，是 “哑转发设备”
        - 控制平面：集中部署的控制器，负责计算转发路径、生成流表、下发策略，是网络的 “大脑”

    3. **控制平面功能集中化**

        路由计算、流量调度、安全策略等所有控制逻辑，都由控制器实现，而非分散在每台交换机上

    4. **可编程控制平面**

        用户 / 应用可通过控制器提供的北向接口（API），以编程方式自定义网络功能（如动态调整流量路径、定义安全规则），无需修改硬件设备

    | 维度             | 传统网络设备                      | SDN 架构                           |
    | ---------------- | --------------------------------- | ---------------------------------- |
    | 架构模式         | 垂直集成（封闭、私有）            | 水平集成（开放、标准）             |
    | 硬件与软件的关系 | 专用硬件 + 专用操作系统，深度绑定 | 通用硬件 + 开放接口 + 通用控制软件 |
    | 创新速度         | 缓慢，厂商主导                    | 快速，生态开放，可自定义开发       |
    | 产业规模与成本   | 规模小、成本高                    | 规模大、成本低                     |

- `5.5.4` SDN 控制器的三层架构

    控制器是 SDN 的核心，内部采用分层设计，实现 “底层通信 - 状态管理 - 上层应用” 的解耦

    | 层级                     | 核心功能                                                     | 关键组件 / 接口                                              |
    | ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **网络控制应用界面层**   | 为网络应用提供抽象 API，支持开发者实现自定义网络功能（北向接口层） | 拓扑 API、路由 API、状态统计 API 等，支持路由、访问控制、负载均衡等应用 |
    | **网络范围的状态管理层** | 维护全网的拓扑、链路状态、设备信息，提供全局统一的网络视图   | 链路状态 `link-state info`、主机信息 `host info`、交换机信息 `switch info`、流表管理 `flow table` |
    | **通信层**               | 实现控制器与交换机之间的通信，下发流表、收集设备状态（南向接口层） | OpenFlow 协议、SNMP 等                                       |

- `5.5.5` `OpenFlow` 协议

    `OpenFlow` 是 SDN 中控制器与交换机通信的主流协议（南向），是实现 “控制与转发分离” 的关键

    - **核心定位**：定义控制器如何向交换机下发流表、交换机如何向控制器上报状态
    - **传输层**：采用 TCP 协议承载报文，加密（TLS）可选，保障通信可靠性
    - **报文类型**：分为三类，覆盖控制器与交换机的双向交互：
        1. 控制器 $\rightarrow$ 交换机：下发流表、修改转发规则、查询设备状态
        2. 交换机 $\rightarrow$ 控制器：上报数据包、设备故障、状态变更
        3. 对称报文：双方均可主动发送，如 Hello 握手、错误报告

    - **核心 API**：定义了通用转发动作的编程接口，如转发到指定端口、修改数据包字段、丢弃数据包等，让控制器可灵活定义转发逻辑

- `5.5.6` SDN 面临的主要挑战

    1. **控制平面的可靠性与扩展性**：

        - 集中式控制器是单点故障风险点，需构建高可用、可扩展的分布式控制器集群
        - 需解决海量设备状态同步、流表下发延迟、控制器负载均衡等问题

    2. **网络与协议的特定需求适配**：

        不同场景对网络特性有严格要求，如数据中心的低延迟、运营商网络的超高可靠性、工业网络的高安全性，SDN 需针对性优化

    3. **全网部署的扩展性问题**：

        传统 SDN 多在单个自治域（AS）内部署，如何实现跨 AS、跨运营商的全网 SDN 部署，仍是行业难题

    4. **5G 等新兴场景的适配**：

        5G 蜂窝网络对低时延、高可靠、切片隔离有极高要求，SDN 需与 NFV（网络功能虚拟化）结合，实现灵活的网络切片与资源调度

## `5.6` ICMP 因特网控制报文协议

- `5.6.1` ICMP 协议基础

    1. 定义与核心功能

        互联网控制报文协议 `Internet Control Message Protocol (ICMP)` 是 TCP/IP 协议簇的核心辅助协议，由**主机、路由器、网关**用于传递网络层控制信息，核心功能分为两类：

        - **错误报告**：当 IP 数据报传输出现异常（如主机 / 网络 / 端口不可达、TTL 过期等），由中间设备或目的主机发送 ICMP 错误报文，通知源主机定位问题
        - **网络诊断与控制**：典型应用为`Ping`命令（Echo 请求 / 回复），用于测试端到端的连通性；此外还支持拥塞控制（源端抑制，目前已废弃）、路由发现等功能

    2. 协议层级与封装方式

        ICMP 在 TCP/IP 模型中属于**网络层协议**，但它**承载在 IP 协议之上**：

        - ICMP 报文并非独立传输，而是作为 IP 数据报的**数据部分**，由 IP 协议封装后转发
        - IP 首部的`协议`字段值为`1`，用于标识该 IP 数据报的数据部分是 ICMP 报文

    3. **ICMP 报文结构**

        | 字段         | 长度     | 作用                                                         |
        | ------------ | -------- | ------------------------------------------------------------ |
        | 类型（Type） | 1 字节   | 标识 ICMP 报文的大类（如 Echo 请求、目的不可达、TTL 过期）   |
        | 编码（Code） | 1 字节   | 对 Type 类型的细分，提供更具体的错误 / 控制信息              |
        | 校验和       | 2 字节   | 检测 ICMP 报文在传输过程中是否发生比特错误                   |
        | 数据部分     | 可变长度 | 错误报告类报文必须携带**导致错误的原始 IP 数据报的前 8 字节（IP 首部 + 传输层首部前 4 字节）**，方便源主机定位出错的传输层会话 |

        *附常见 ICMP 报文类型与编码*

        | Type | Code | 描述                     | 典型应用场景                                                 |
        | ---- | ---- | ------------------------ | ------------------------------------------------------------ |
        | 0    | 0    | Echo Reply（回显回复）   | `Ping`命令的响应报文，回复 Echo 请求                         |
        | 3    | 0    | 目的网络不可达           | 路由器无目标网络路由时发送                                   |
        | 3    | 1    | 目的主机不可达           | 路由可达但目标主机无响应 / 不存在                            |
        | 3    | 2    | 目的协议不可达           | 目标主机不支持 IP 数据报中的传输层协议                       |
        | 3    | 3    | 目的端口不可达           | 目标主机的传输层端口未开放（Traceroute 停止条件）            |
        | 4    | 0    | 源端抑制（已废弃）       | 拥塞控制，通知源主机降低发送速率                             |
        | 8    | 0    | Echo Request（回显请求） | `Ping`命令的探测报文，测试连通性                             |
        | 11   | 0    | TTL 过期                 | IP 数据报 TTL 减为 0 时，路由器发送此报文（Traceroute 核心） |
        | 12   | 0    | 错误 IP 首部             | IP 数据报首部格式错误，无法解析                              |

- `5.6.2` Traceroute 工具与 ICMP

    Traceroute（Linux/macOS）/Tracert（Windows）是探测 IP 数据报从源主机到目标主机所经路由路径的工具，核心依赖**IP 的 TTL 字段**和**ICMP 报文**实现

    1. 核心机制：TTL 探测法

        生存时间 `Time To Live (TTL)` 是 IP 数据报首部的字段，每经过一个路由器，TTL 值减 1；当 TTL 减为 0 时，路由器会丢弃该数据报，并向源主机发送**ICMP TTL 过期报文（Type=11，Code=0）**

        Traceroute 利用这一特性，发送 TTL 从 1 开始递增的探测报文，**逐个获取路径上的路由器信息**

    2. 工作流程

        1. **准备探测报文**：Linux 系统默认使用 UDP 报文，目标端口号选择一个**不可达的高端口（如 33434）**，方便后续触发端口不可达报文；同时设置 TTL 值：
            - 第 1 个探测报文：$TTL=1$
            - 第 2 个探测报文：$TTL=2$
            - 以此类推，第 n 个探测报文的 $TTL=n$
        2. **获取中间路由器信息**：
            - $TTL=1$ 的报文到达第 1 跳路由器时，TTL 减为 0，路由器丢弃报文并发送 ICMP TTL 过期报文，源主机由此记录第 1 跳路由器的 IP 地址和往返时间（RTT）
            - $TTL=2$ 的报文到达第 2 跳路由器时，TTL 减为 0，路由器同样回复 TTL 过期报文，源主机记录第 2 跳信息
            - 重复此过程，每一跳路由器都会在探测报文 TTL 到期时回复报文，源主机记录所有跳数的路径信息
        3. **重复探测**：图片中显示，Traceroute 会对每一跳发送 3 次探测报文（3 probes），计算平均往返时延 `Round-Trip Time (RTT)`，避免单次探测的偶然性误差

    3. **探测停止的判断依据**

        当探测报文最终到达目标主机时，触发停止条件：

        1. 目标主机收到 $TTL=n$ 的 UDP 探测报文，此时 TTL 未过期，报文被正常交给传输层处理
        2. 由于 Traceroute 使用的目标端口是不可达的，目标主机的 UDP 协议会发现端口未开放，因此向源主机发送**ICMP 目的端口不可达报文（Type=3，Code=3）**
        3. 源主机收到该 ICMP 报文后，确认探测报文已到达目标主机，停止后续 TTL 递增的探测流程

- `5.6.3` ICMP 的现实问题

    1. Ping 不通 ≠ 主机不存在

        Ping 是基于 **回显请求 / 应答 `ICMP Echo Request/Reply`** 实现的连通性检测工具，它的 “不通” 仅代表**ICMP 报文未收到回复**，不代表主机离线或网络不可用，核心原因有两类：

        1. 防火墙 / 安全设备默认屏蔽 ICMP 报文

            - 几乎所有企业防火墙、云服务器安全组，都会默认拒绝外部的 ICMP Echo 请求（Ping 请求），目的是防止攻击者通过 Ping 扫描存活主机，避免暴露网络拓扑

            - 举个例子：你 Ping 百度的服务器，有时会超时，但用浏览器打开百度网页完全正常 —— 这就是百度服务器的防火墙屏蔽了 ICMP 请求，但正常转发 HTTP/HTTPS 流量

        2. traceroute 显示的路径可能严重失真

            traceroute（Linux/macOS 工具）/tracert（Windows 工具）的原理是：通过发送 TTL（生存时间）字段依次为 1、2、3… 的数据包，让中间路由器返回 ICMP 超时报文，从而 “探测” 数据包经过的路径

            但以下 3 种情况会导致路径信息完全失真：

            | 影响因素                           | 原理说明                                                     |
            | ---------------------------------- | ------------------------------------------------------------ |
            | 防火墙丢弃 ICMP 报文但转发数据流量 | 防火墙会丢弃 traceroute 触发的 ICMP 超时报文，但正常转发业务数据，导致 traceroute 无法看到这一跳的设备，路径出现 “断层” |
            | MPLS 隧道使中间路由器不可见        | MPLS（多协议标签交换）会在数据包外层封装标签，中间的标签交换路由器只处理标签，不处理 IP 层的 TTL，也不会返回 ICMP 超时报文，导致这些设备在 traceroute 中 “隐身” |
            | 多路径负载均衡                     | 路由器会把不同数据包分发到多条链路传输，导致 traceroute 每次探测的路径都不一样，显示的跳数、IP 地址混乱，无法反映真实的传输路径 |

    2. ICMP 重定向报文的安全风险

        1. 原理：正常场景下的 “路径优化”

            ICMP 重定向报文的设计目的是：当主机向非最优网关发送数据包时，网关会向主机发送 ICMP 重定向报文，告知主机 “去往目标地址的数据包，应该发给另一个下一跳设备”，从而让主机更新路由表，选择更优路径

        2. 安全风险：伪造报文实施流量劫持

            攻击者可以伪造合法的 ICMP 重定向报文，欺骗主机将流量转发到攻击者控制的恶意主机

            例如：攻击者伪造网关发送重定向报文，让主机把访问银行网站的流量转发到钓鱼服务器，从而窃取账号密码

        3. 现状：防护措施与残留风险

        - 现代操作系统（Windows、Linux、macOS）默认会忽略 ICMP 重定向报文，避免被攻击
        - 部分老旧的嵌入式设备（如工业路由器、IoT 设备）为了兼容早期协议，仍默认开启 ICMP 重定向功能，存在被劫持的风险




## `5.7` 网络管理（了解）

### `5.7.0` 网络管理导论

- `5.7.0.1` 网络管理的概念

    网络管理是指对网络中的硬件、软件和人力资源进行**规划、配置、监测、分析、评价和控制**，以确保网络系统连续、稳定、高效运行，并以合理成本满足用户的服务质量（QoS）、实时性和可用性要求的一系列活动

    关键要素拆解：

    - 管理对象：硬件（路由器、交换机）、软件（操作系统、协议栈）、人类元素（管理员、用户）$\rightarrow$ 自治系统 AS
    - 核心动作：监测、配置、分析、控制
    - 目标：低成本、高服务质量、高可靠性

- `5.7.0.2` 网络管理的功能

    | 功能分类                          | 核心定义                                                     | 关键动作 / 场景                                              | 与其他功能的区别                                             |
    | --------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **性能管理（Performance）**       | 量化、测量、报告、分析和控制网络部件的性能，保障网络运行效率 | 监测网卡利用率、端口吞吐量、端到端延迟、丢包率；生成性能报告；基于阈值进行预警 | 关注**长期趋势**和**整体效率**，是预防性管理                 |
    | **故障管理（Fault）**             | 记录、检测、定位和响应网络故障，快速恢复服务                 | 设备宕机告警、链路中断检测、故障根因分析、自动故障切换       | 关注**突发故障**和**快速响应**，是应急性管理                 |
    | **配置管理（Configuration）**     | 跟踪、管理和控制网络设备的配置信息，确保配置的一致性和合规性 | 备份设备配置文件、批量下发配置、版本回滚、配置合规检查       | 是所有管理功能的基础，保障网络拓扑和参数的正确性             |
    | **账户 / 计费管理（Accounting）** | 定义、记录和控制用户 / 设备对网络资源的访问，实现资源使用的可追溯与计费 | 用户权限分配、流量限额控制、资源使用统计、计费报表生成       | 关注资源的**分配与使用审计**，保障资源公平性                 |
    | **安全管理（Security）**          | 定义和执行安全策略，控制对网络资源的访问，防范安全威胁       | 访问控制列表（ACL）配置、防火墙策略管理、日志审计、漏洞扫描  | 关注网络的**保密性、完整性、可用性**，防范外部攻击与内部违规 |

- `5.7.0.3` 网络管理架构与组件 —— 以管理者 - 代理 `Manager-Agent` 架构为例

    | 组件                                            | 定义与角色                                                   | 示例                                     |
    | ----------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------- |
    | **管理服务器（Managing Server/Manager）**       | 网络管理的核心，运行管理应用程序，接收管理员指令，向被管理设备发送管理请求，并处理设备返回的数据 | Zabbix、Nagios、SolarWinds 等网管平台    |
    | **被管理设备（Managed Device）**                | 网络中需要被管理的硬件 / 软件实体，具备可管理、可配置的接口  | 路由器、交换机、服务器、防火墙           |
    | **代理（Agent）**                               | 运行在被管理设备上的进程，负责接收管理服务器的请求，采集设备数据，执行配置操作，并将结果返回给管理服务器 | SNMP Agent、NETCONF Agent                |
    | **网络管理协议（Network Management Protocol）** | 管理服务器与代理之间通信的标准，定义了请求 / 响应的格式、数据交互规则 | SNMP、NETCONF、RESTCONF                  |
    | **管理数据（Data）**                            | 被管理设备的状态信息，包括配置数据、运行数据、统计数据、告警信息等 | 路由器的端口状态、CPU 利用率、路由表信息 |

    - 架构的工作流程

    ```mermaid
    flowchart LR
        管理员 --> 管理服务器
        管理服务器 -->|管理协议| 代理(Agent)
        代理 --> 操作被管理设备
        被管理设备 -->|返回结果| 代理
        代理 -->|管理协议| 管理服务器
        管理服务器 --> 展示给管理员
    ```

    1. 管理员在管理服务器上发起管理请求（如查询端口状态、修改 VLAN 配置）
    2. 管理服务器通过网络管理协议，将请求发送给被管理设备上的代理
    3. 代理接收请求后，在设备上执行对应的操作（如采集数据、修改配置）
    4. 代理将操作结果（如端口状态数据、配置执行结果）返回给管理服务器
    5. 管理服务器将结果展示给管理员，或根据数据自动触发告警 / 自动化操作

### `5.7.1` SNMP/MIB

- `5.7.1.1` 核心概念

    遵循简单网络管理协议 / 管理信息库 `Simple Network Management Protocol / Management Information Base (SNMP/MIB)` 进行网络管理，是指基于管理者 - 代理模型，管理服务器通过 SNMP 协议向设备代理发送请求，查询 / 设置设备的管理数据（存储在 MIB 中）

- `5.7.1.2` 特点

    - 优点：标准化、支持批量监控、成熟稳定，广泛应用于传统网络监控
    - 缺点：配置管理能力较弱，不适合复杂的批量配置操作；MIB 定义复杂，扩展性差

    **典型场景**：网络设备性能监控、故障告警

### `5.7.2` NETCONF/YANG

- `5.7.2.1` 核心概念

    面向大规模网络的配置管理协议，NETCONF 是通信协议，YANG 是数据建模语言，实现多设备的统一、自动化配置管理

- `5.7.2.2` 特点

    - 优点：支持自动化、批量配置，配置可回滚、可验证，适合大规模网络；标准化程度高，支持多厂商设备
    - 缺点：实现复杂度高，对设备性能有一定要求，部分老旧设备不支持

    **典型场景**：运营商大规模网络配置管理、数据中心网络自动化运维

### `5.7.3` CLI

- `5.7.3.1` 核心概念

    利用命令行接口 `Command Line Interface (CLI)` 进行网络管理，是指管理员通过 SSH、Telnet 等方式直接登录到单个设备，通过命令行手动配置和管理设备

- `5.7.3.2` 特点

    - 优点：直接、灵活，适合设备调试和故障排查
    - 缺点：无法批量管理多设备，效率低，易出错，不适合大规模网络

    **典型场景**：设备首次配置、紧急故障处理、个性化调试

| 管理方法     | 适用场景             | 核心优势               | 局限性                   |
| ------------ | -------------------- | ---------------------- | ------------------------ |
| CLI          | 单设备调试、故障排查 | 直接灵活               | 无法批量管理，效率低     |
| SNMP/MIB     | 设备监控、故障告警   | 标准化、成熟稳定       | 配置管理能力弱，扩展性差 |
| NETCONF/YANG | 大规模网络自动化配置 | 自动化、标准化、可回滚 | 实现复杂，对设备要求高   |
