# 第 4 章 网络层：数据平面

## `4.1` 网络层概述

### `4.1.0` 网络层服务与协议

- `4.1.0.1` 网络层的基本定位

    网络层是 OSI 参考模型的第三层，其核心任务是在**发送主机和接收主机之间传送"段"** `Segment`，具体来说：

    - **发送端**：将传输层交付的段 `Segment` 封装到数据报 `Datagram` 中
    - **接收端**：将数据报解封装后，将段上交给传输层实体

    > 网络层协议存在于**每一个主机和路由器**中，这是与传输层的重要区别——传输层协议只存在于端系统（主机）中

- `4.1.0.2` 路由器

    路由器是网络层的核心设备，执行两项关键操作：

    - **检查**：检查每一个经过它的 IP 数据报的头部
    - **移动**：将数据报从输入端口移动到输出端口，以沿端到端路径传输数据报

- `4.1.0.3` 关键功能：转发 & 路由选择

    | 维度         | 转发 `Forwarding`                            | 路由选择 `Routing`                             |
    | :----------- | :------------------------------------------- | :--------------------------------------------- |
    | **定义**     | 将分组从路由器的输入接口转发到合适的输出接口 | 使用路由算法决定分组从发送主机到目标主机的路径 |
    | **范围**     | **本地**（单个路由器内部）                   | **全局**（端到端路径规划）                     |
    | **时间尺度** | 纳秒级（硬件实现）                           | 毫秒/秒级（软件实现）                          |
    | **类比**     | 通过**单个路口**的过程                       | 从源到目的的**路径规划**过程                   |
    | **依赖**     | 转发表 `Forwarding Table`                    | 路由表 `Routing Table`                         |
    | **实现位置** | 数据平面                                     | 控制平面                                       |

    > 路由选择算法生成**路由表**，路由表经过优化后生成**转发表**
    >
    > 转发表是路由表的"本地执行版本"，存储在每个输入端口的内存中，用于高速查找

- `4.1.0.4` 数据平面与控制平面

    | 平面                         | 作用范围             | 核心功能                               |
    | ---------------------------- | -------------------- | -------------------------------------- |
    | **数据平面** `Data plane`    | 本地、单个路由器内部 | 决定从某个端口进入的分组从哪个端口输出 |
    | **控制平面** `Control plane` | 整个网络范围         | 决定数据报如何沿着端到端路径传输       |

### `4.1.1` 数据平面

- `4.1.1.1` 网络层连接的建立

    在分组传输之前，两个主机之间，在通过**一些路由器**所构成的路径上建立一个网络层连接

    | 对比项           | 传输层连接（TCP 连接）         | 网络层连接（虚电路 VC）        |
    | ---------------- | ------------------------------ | ------------------------------ |
    | **通信对象**     | 两台主机上**应用进程（端口）** | 两台**主机（IP 地址）**        |
    | **途经设备**     | 只在**两端主机**，路由器无感知 | 源主机→沿途所有路由器→目的主机 |
    | **典型代表**     | TCP（面向连接）                | ATM 虚电路、帧中继虚电路       |
    | **连接建立位置** | 端系统内部                     | 端系统 + 整条路径所有路由器    |
    | **无连接代表**   | UDP（无连接）                  | IP 数据报（无连接、尽力交付）  |
    | **故障影响**     | 链路断：仅断开两端进程连接     | 链路断：整条虚电路全部失效     |

- `4.1.1.2` 网络服务模型

    网络服务模型定义了网络为传输的数据报提供什么样的服务质量 `Quality of Service (QoS)` 保证

    1. 服务分类

        - **针对单个数据报的服务**：
            - 可靠传送：保证数据报一定到达目的地
            - 延迟保证：保证数据报的传输延迟不超过某个阈值（如延迟少于 40ms）
        - **针对数据流的服务**：
            - 保序数据报传送：保证数据报按发送顺序到达
            - 保证流的最小带宽：为数据流预留一定的带宽
            - 分组之间的延迟差：保证同一数据流中分组之间的延迟波动在一定范围内

    2. 典型网络服务模型对比

        | 网络架构 | 服务模型                  | 带宽保证 | 丢失保证 | 保序保证 | 延迟保证 | 拥塞反馈           |
        | -------- | ------------------------- | -------- | -------- | -------- | -------- | ------------------ |
        | Internet | 尽最大努力（Best effort） | 无       | 无       | 无       | 无       | 无（通过丢包推断） |
        | ATM      | CBR（恒定比特率）         | 恒定     | 是       | 是       | 是       | 拥塞               |
        | ATM      | VBR（可变比特率）         | 保证速率 | 是       | 是       | 是       | 拥塞               |
        | ATM      | ABR（可用比特率）         | 保证最小 | 否       | 是       | 否       | 是                 |
        | ATM      | UBR（不指明比特率）       | 无       | 否       | 是       | 否       | 否                 |

    3. 尽最大努力 `Best Effort` 服务

        互联网不提供任何服务质量保证，只是尽最大努力将数据报传送到目的地

        > **不保证**成功将数据报传递到目的地（可能丢失）
        >
        > **不保证**交货的时间或顺序（可能延迟、乱序）
        >
        > **不保证**端到端可用的带宽

        - 设计哲学：将复杂性推向网络边缘（端系统），网络核心保持简单
            - **简单的机制**使互联网得以广泛部署
            - **充足的带宽**供应使实时应用程序（如交互式语音、视频）的性能在"大部分时间"内"足够好"
            - **"弹性"服务**的拥塞控制有助于防止网络崩溃、尽可能利用网络资源、同时保障基本传输服务

### `4.1.2` 控制平面

- `4.1.2.1` 传统方式：单个路由器 `Per-router` 控制平面

    每一个路由器都包含独立的路由算法元件，路由器之间通过路由协议交互路由信息

    - 每个路由器独立运行路由算法，与其他路由器交换路由信息
    - 每个路由器根据收集到的路由信息，计算并维护自己的本地转发表
    - 数据平面根据本地转发表，对到达的 IP 数据报进行转发
    - 控制平面和数据平面**紧密耦合**在同一设备中
    - **优缺点**：可靠性高（分布式架构），但配置复杂，难以实现全局统一的网络策略

- `4.1.2.2` SDN 方式：逻辑集中的控制平面

    将控制平面从路由器中分离出来，由一个**远程的、逻辑集中的控制器**统一管理

    - 一个**远程控制器** `Remote Controller` 与本地控制代理 `Control Agents (CAs)` 交互
    - 控制器维护全网视图，计算转发规则，通过**南向接口**（如 OpenFlow 协议）将流表下发
    - 路由器的数据平面根据流表对数据报进行转发
    - **优缺点**：配置简单，支持灵活的网络编程，但存在单点故障风险

## `4.2` 路由器工作原理

- `4.2.1` 路由器体系架构

    路由器的核心功能可以抽象为两个独立的平面，这是理解路由器工作原理的基础

    | 平面类型      | 核心功能                                               | 实现方式              | 时间尺度    |
    | ------------- | ------------------------------------------------------ | --------------------- | ----------- |
    | **控制平面 ** | 运行路由协议（RIP/OSPF/BGP），计算最优路径，生成路由表 | 软件实现 (路由处理器) | 毫秒级 (慢) |
    | **数据平面**  | 根据转发表将分组从输入端口转发到输出端口               | 硬件实现 (交换结构)   | 纳秒级 (快) |

    ```mermaid

                RP[路由处理器<br/>Routing Processor]
    ```

- `4.2.2` 输入端口功能

    输入端口处理分为三个层次，最终目标是实现**"线速处理"**（处理速度与物理链路传输速率保持同步）：

    1. **物理层**：线路终端，完成比特级的信号接收和同步

    2. **数据链路层**：处理链路层协议（如 Ethernet），完成帧的解封装和差错检测

    3. **网络层**：**（匹配+行动）**

        - 提取目的 IP 地址，查找转发表，确定分组的输出端口

            > **分布式交换**：现代路由器将转发决策下放到每个输入端口本地完成，目标是实现 "线速处理"—— 处理速度与物理链路的传输速率保持同步

        - 执行转发操作

            - 基于目标的转发：仅依赖 IP 分组的目标 IP 地址（传统路由器）

            - 通用转发：基于 IP 头部任意字段的组合进行转发（现代 SDN 路由器）

        - 当交换结构忙，或数据报到达速度超过交换结构转发速度时，将分组放入输入端口（缓存中）排队

- `4.2.3` 最长前缀匹配 LPM

    转发表中存储的不是完整 IP 地址，而是**地址前缀/网络前缀**（如 `11001000 00010111 00010000 00000000`），这导致了一个目的 IP 可能匹配多条表项，如何决策？

    $\rightarrow$ **最长前缀匹配** `Longest Prefix Match (LPM)` ：当给定目的地址查找转发表时，采用与目的地址**匹配的最长地址前缀**对应的表项进行转发

    依据：IP 地址采用层次编址，最长前缀匹配能保证路由的准确性和路由聚合的有效性

    | 目的地址前缀                               | 前缀长度 | 链路接口 |
    | ------------------------------------------ | -------- | -------- |
    | `11001000 00010111 00010` `***` `********` | /21      | 0        |
    | `11001000 00010111 00011000` `********`    | /24      | 1        |
    | `11001000 00010111 00011` `***` `********` | /21      | 2        |
    | `otherwise`                                | —        | 3        |

    - 假设转发表如上所示，对于目的地址 = `11001000 00010111 00011000 10101010` 的情况：
        - 与表项 0 匹配：前 21 位 `11001000 00010111 00010` ❌（第 21 位是 0 不是 1）
        - 与表项 1 匹配：前 24 位 `11001000 00010111 00011000` ✅
        - 与表项 2 匹配：前 21 位 `11001000 00010111 00011` ✅
        - **比较**：表项 1 匹配长度 24 位 > 表项 2 匹配长度 21 位
        - **结果**：选择表项 1，接口 **1**
    - 在路由器中经常采用**三态内容可寻址存储器** `Ternary Content Addressable Memory (TCAM)` 来实现 LPM 
        - **内容可寻址**：将目的 IP 地址作为"钥匙"交给 TCAM，所有表项**并行比对**，在一个时钟周期内返回结果，与表大小无关
        - **三态**：每个比特可存储 0、1 或 *（通配符，表示"不关心"）
        - **性能**：Cisco Catalyst 系列路由器可在 TCAM 中存储约 **100 万条**路由表项

- `4.2.4` 交换结构 `Switching Fabrics`

    交换结构负责将分组从输入端口传输到正确的输出端口，是路由器实现高速多端口并发转发的关键硬件架构

    - 核心指标：交换速率，即分组可以按照怎样的速率从输入传输到输出

        理想情况下，交换速率 = N × 输入线路速率（N 为端口数），此时称为**无阻塞交换机**

    - 经典的交换结构

        1. 通过内存交换：分组被拷贝到系统内存，CPU 从分组的头部提取出目标地址，查找转发表，找到对应的输出端口，拷贝到输出端口

        2. 通过总线交换：数据报通过共享总线，从输入端口转发到输出端口

        3. 通过互联网络交换：通过榕树 `Banyan` 网络、纵横 `Crossbar` 网络和其他互联网络，路由器可以同时并行转发多个分组，克服总线带宽的限制

            - 并行传输的优化：输入端口将变长的 IP 分组切割成固定长度的信元，信元在交换网络中独立传输，输出端口将信元重新组装成原始 IP 分组

            - 从单个交换机，到多级交换机、多平面交换网络

                - Crossbar 纵横网格交换：由 n 行 n 列的交叉点开关组成，形成一个 n×n 的矩阵
                    $$
                    \begin{array}c
                    A&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}\\
                    &&\Updownarrow&&\Updownarrow&&\Updownarrow\\
                    B&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}\\
                    &&\Updownarrow&&\Updownarrow&&\Updownarrow\\
                    C&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}&\Leftrightarrow&\boldsymbol{\bullet}\\
                    &&\Updownarrow&&\Updownarrow&&\Updownarrow\\
                    &&X&&Y&&Z
                    \end{array}
                    $$
                    当输入端口 A 需要向输出端口 Y 发送分组时，控制器闭合 A 行 Y 列的交叉点开关，建立一条专用的物理路径

                    > 只要不同输入不向同一个输出发送，就可以同时建立多条路径
                    >
                    > 如果想同一个输出同时发送，仍然会造成阻塞

                - 多级交换网络：纯 Crossbar 无法扩展到大规模端口，因此将大的交换矩阵分解为**多个级联的小型交换单元**

                - 多平面交换架构：当单个交换平面的容量达到物理极限时，通过**多个并行的交换平面**实现容量的线性扩展

        | 交换类型         | 优点                  | 缺点                                                 | 代表产品                                           |
        | ---------------- | --------------------- | ---------------------------------------------------- | -------------------------------------------------- |
        | **内存交换**     | 简单，成本低          | 带宽受限 (数据两次经过总线)<br/>一次只能转发一个分组 | 第一代传统计算机路由器                             |
        | **总线交换**     | 实现简单              | 总线竞争，带宽有限<br/>一次只能转发一个分组          | Cisco 1900 (1Gbps总线)<br/>Cisco 5600 (32Gbps总线) |
        | **互联网络交换** | 高带宽<br/>无总线瓶颈 | 复杂度高，成本高                                     | Cisco CRS (8个交换平面，100Tbps容量)               |

- `4.2.5` 排队与缓存管理

    - 输入端口排队：当交换结构的速率**小于**输入端口的汇聚速率时，分组在输入端口需要排队

        $\rightarrow$ 队头阻塞 `Head-of-the-Line Blocking (HOL)`：排在队列**队头**的数据报因目标输出端口被占用而无法前进，导致其后方的数据报（即使目标输出端口空闲）也被阻塞

    - 输出端口排队：当**多个输入端口同时向同一个输出端口发送分组**时，（考虑到交换结构的理想速率）分组到达输出端口的瞬时速率会远超过物理链路的传输速率，分组在输出端口需要排队

        $\rightarrow$ 缓存溢出：当持续的突发流量超过缓存容量时，路由器必须执行丢弃策略删除数据报

        - 缓存大小的经验性确定（平衡性能与成本）
            - 缓存大小的两面性：缓存不足会导致丢包；缓存过大则增加排队延迟
            - **RFC 3439 经验规则（拇指规则）**：平均缓存大小 = 典型的 RTT $\times$ 链路容量 C
            - 对于有 N 个流的多流情况（另外一种经验计算）：平均缓存大小 = $\text{RTT}\times C\div\sqrt{N}$

        - 分组调度 `Buffert Mannagement`

            - 丢弃策略：缓存满时，丢弃哪些数据报？

                | 策略                  | 说明                                                    |
                | --------------------- | ------------------------------------------------------- |
                | 尾丢弃 `Tail Drop`    | 缓存满时，丢弃新到达的分组                              |
                | 优先权丢弃 `Priority` | 根据优先权丢弃/移除分组（如优先丢弃低优先级分组）       |
                | 随机丢弃 `Random`     | 随机丢弃分组，避免全局同步                              |
                | ECN/RED 标记          | 在队列满之前主动标记/丢弃分组，向发送端提供早期拥塞信号 |

            - 调度算法：多个分组等待时，按什么顺序发送？

                1. FCFS / FIFO（先进先出）：按分组到达输出端口的顺序发送

                    - **特点**：实现最简单，所有分组同等对待
                    - **缺点**：无法区分流量类型，高优先级流量可能被阻塞

                2. 优先权调度 `Priority Scheduling`

                    将到达流量分类到不同优先级队列，**总是优先发送高优先级队列**中的分组，同优先级队列内按 FIFO 顺序发送

                    - **分类依据**：IP 首部标记、源/目的 IP、端口号、DSCP 字段等
                    - **风险**：若高优先级队列持续有分组，低优先级队列可能**饿死（starvation）**

                3. 循环调度 `Round Robin (RR)`

                    将流量分类到不同队列，调度器**轮流扫描**各队列，每次从每个非空队列发送一个分组

                    - **特点**：避免了低优先级饿死问题，各队列获得均等机会
                    - **局限**：未考虑各队列的流量大小差异，大分组占用更多带宽

                4. 加权公平排队 `Weighted Fair Queuing (WFQ)`

                    - RR 的一般化，每个队列分配权重 $w_i$ ，在循环中按权重比例获得服务量
                    - **服务时间分配**：队列 $i$  获得的服务时间比例 = $W_i/\sum W_i$
                    - **特点**：保证每个流量等级的**最低带宽**，实现公平共享
                    - **应用**：现代QoS（服务质量）保障的核心算法

## `4.3` 网际协议 IP

- `4.3.1` 数据报格式

    IP 数据报是网络层的核心传输单元，整体分为**首部**和**数据**两部分：

    - 首部：固定 20 字节（所有 IP 数据报必须包含） + 可选字段（0-40 字节，用于扩展功能）

        | 固定字段名称                 | 长度  | 核心作用与说明                                               |
        | ---------------------------- | ----- | ------------------------------------------------------------ |
        | 版本 `Version`               | 4 位  | 标识 IP 协议版本<br/>IPv4 为 `0100`（十进制 4），IPv6 为 `0110`（十进制 6） |
        | 首部长度 `IHL`               | 4 位  | **单位为 4 字节**，表示整个 IP 首部的长度<br/>最小值为 5（5×4=20 字节，无选项）<br/>最大值为 15（15×4=60 字节，满选项） |
        | 服务类型 `Type of Service`   | 8 位  | 用于指定数据报的服务质量需求，如优先级、延迟、吞吐量、可靠性 |
        | 总长度 `Total Length`        | 16 位 | **单位为 1 字节**，表示整个 IP 数据报（首部 + 数据）的总长度<br/>最大值为 2^16^-1=65535 字节（64KB） |
        | 标识 `Identification`        | 16 位 | 用于唯一标识一个数据报<br/>同一个原始数据报的所有分片具有相同的标识号 |
        | 标志 `Flags`                 | 3 位  | 仅 2 位有效：最高位（第 1 位）为保留位，必须为 0<br/>- DF 位（第 2 位）：1 = 禁止分片，0 = 允许分片<br/>- MF 位（第 3 位）：1 = 后面还有分片，0 = 最后一个分片 |
        | 片偏移 `Fragment Offset`     | 13 位 | **单位为 8 字节**，表示本分片数据相对于原始数据报数据部分的偏移量<br/>片偏移值 = 该分片数据在原始数据报中的起始字节位置 $\div$ 8 |
        | 生存时间 `TTL`               | 8 位  | 数据报在网络中的最大跳数；**每经过一个路由器 TTL 减 1**<br/>当 TTL = 0 时，路由器丢弃该数据报并向源主机发送 ICMP 超时报文 |
        | 协议 `Protocol`              | 8 位  | 指示数据部分承载的上层协议类型<br/>常见值：ICMP = 1，TCP = 6，UDP = 17 |
        | 首部检验和 `Header Checksum` | 16 位 | 仅检验 IP 首部，不检验数据部分<br/>采用反码求和算法，每经过一个路由器必须重新计算 |
        | 源 IP 地址                   | 32 位 | 发送方主机的 IPv4 地址                                       |
        | 目的 IP 地址                 | 32 位 | 接收方主机的 IPv4 地址                                       |

    - 数据部分：可变长度，通常承载 TCP 段、UDP 段或 ICMP 报文等上层协议数据

    - 总长度字段为 16 位，因此数据报的理论最大长度为 $2^{16}-1=65535$ 字节

- `4.3.2` IP 分片与重组

    虽然 IP 数据报理论最大长度为 65535 字节，但是受限于链路层最大传输单元 `Maximum Transmission Unit (MTU)`（例如以太网标准的 MTU = 1500 字节），当一个 IP 数据报的总长度大于其要经过的某条链路的 MTU 时，转发该数据报的路由器必须将其分割成多个更小的数据报（分片）后再转发

    - IP 分片的核心机制

        | 字段             | 长度  | 核心作用                                                     |
        | ---------------- | ----- | ------------------------------------------------------------ |
        | 标识（ID）       | 16 位 | 用于唯一标识一个数据报<br/>同一个原始数据报的所有分片具有相同的标识号 |
        | 标志（flag）     | 3 位  | 仅 2 位有效：最高位（第 1 位）为保留位，必须为 0<br/>- DF 位 `Don't Fragment`（第 2 位）：1 = 禁止分片，0 = 允许分片<br/>- MF 位 `More Fragment` （第 3 位）：1 = 后面还有分片，0 = 最后一个分片 |
        | 片偏移（offset） | 13 位 | **单位为 8 字节**，表示本分片数据相对于原始数据报数据部分的偏移量<br/>片偏移值 = 该分片数据在原始数据报中的起始字节位置 $\div$ 8 |

        1. 每个分片都有独立的 IP 首部（除 MF 位和 offset 字段外，其他字段与原始数据报基本一致）

        2. 除最后一个分片外，所有分片的数据部分长度必须是 8 字节的整数倍（由 offset 的单位决定）

        3. 分片可以在传输路径上的任何路由器上进行，且可以被再次分片

        4. 例如，对于 4000 字节的 IP 数据报，MTU = 1500 字节的情况中

            1. 4000 字节的数据报 = 20 字节的 IP 头部 + 3980 字节数据
            2. MTU = 20 字节 IP 头部 + 1480 字节数据
            3. 3980 字节数据 = 1480 字节数据 $\times$ 2 + 1020 字节数据（按数据拆分，不管 IP 头部） $\rightarrow$ 分成三片

            | 分片序号   | 总长度（字节） | ID   | MF 位 | 片偏移          | 数据部分长度（字节） |
            | ---------- | -------------- | ---- | ----- | --------------- | -------------------- |
            | 原始数据报 | 4000           | x    | 0     | 0               | 3980                 |
            | 分片 1     | 1500           | x    | 1     | 0               | 1480                 |
            | 分片 2     | 1500           | x    | 1     | $1480\div8=185$ | 1480                 |
            | 分片 3     | 1040           | x    | 0     | $2960\div8=370$ | 1020                 |

    - IP 重组的核心机制

        - **重组位置**：**仅在最终的目标主机上进行**，中间路由器不执行任何重组操作

            > 中间路由器无法保证收到同一个数据报的所有分片（分片可能走不同路径），因此只能由最终目标主机完成重组

        - 重组过程：目标主机收集所有具有相同 ID 的分片，根据**片偏移从小到大排序**，最后拼接成完整的原始数据报

        - 超时机制：如果目标主机在规定时间内未收到某个数据报的所有分片，将丢弃已收到的所有分片，并向源主机发送 ICMP 超时差错报文

- `4.3.3` IPv4 地址

    - IP 编址基础

        - IP 地址：一个**32 位（4 字节）的二进制数**，用于唯一标识互联网中的主机或路由器接口

            通常采用**点分十进制**表示：将 32 位二进制数分为 4 个 8 位组，每个组转换为 0-255 的十进制数，用点分隔

        - 接口 `Interface` ：主机 / 路由器与物理链路的连接点

            - 路由器必须**拥有 2 个及以上接口**，每个接口对应一个不同的 IP 地址，否则无法在网络中转发数据
            - 主机可以有 1 个或多个接口（如同时连接有线网卡和无线网卡），每个接口对应一个 IP 地址

            > **一个 IP 地址唯一对应一个接口**

    - 子网 `Subnets` 

        - 子网与 IP 地址

            - IP 地址结构：分为**子网部分（高位比特）**和**主机部分（低位比特）**

            - 子网：IP 地址高位部分（前缀）相同的节点（主机 / 路由器）构成的网络片段

                > 将每一个接口从主机或路由器上分开，构成一个个"网络孤岛"，**每一个孤岛就是一个子网**

            - 关键特性：**子网内的主机无需路由器介入，可直接物理通信（通过交换机一跳可达）**

        - 子网掩码 `Subnet Mask` ：用于区分 IP 地址中的子网部分和主机部分的数字，用 32 位二进制数表示

            其中：**1 表示子网位，0 表示主机位**，常用 `/x` 简化表示，其中 x 表示子网位的长度

            > 例如 `\24` 表示子网掩码为 `255.255.255.0`（即前 24 位为 1，后 8 位 0），说明前 24 位都是子网位

    - IP 地址及其传统分类

        | 地址类别 | 前缀特征 | 网络号长度 | 主机号长度 | 可用网络数 | 每个网络可用主机数 | 地址范围                    |
        | -------- | -------- | ---------- | ---------- | ---------- | ------------------ | --------------------------- |
        | A 类     | 0        | 8 位       | 24 位      | 126        | 16,777,214         | 1.0.0.0 ~ 126.255.255.255   |
        | B 类     | 10       | 16 位      | 16 位      | 16,384     | 65,534             | 128.0.0.0 ~ 191.255.255.255 |
        | C 类     | 110      | 24 位      | 8 位       | 2,097,152  | 254                | 192.0.0.0 ~ 223.255.255.255 |
        | D 类     | 1110     | -          | -          | -          | -                  | 224.0.0.0 ~ 239.255.255.255 |
        | E 类     | 1111     | -          | -          | -          | -                  | 240.0.0.0 ~ 255.255.255.255 |

        - 特殊的 IP 地址

            | 规则           | 含义                           |
            | :------------- | :----------------------------- |
            | 子网部分全为 0 | 表示"本网络"                   |
            | 主机部分全为 0 | 表示"本主机"                   |
            | 主机部分全为 1 | 表示广播地址，该网络的所有主机 |

            | 地址              | 名称                 | 用途                                   |
            | :---------------- | :------------------- | :------------------------------------- |
            | `127.0.0.1`       | 环回地址 ` Loopback` | 测试本地 TCP/IP 协议栈，数据不离开本机 |
            | `0.0.0.0`         | 本主机/默认路由      | 表示本机或作为默认路由的匹配地址       |
            | `255.255.255.255` | 有限广播地址         | 向本地网络所有主机广播                 |
            | `169.254.x.x`     | APIPA 地址           | DHCP 失效时自动分配的链路本地地址      |

            以家庭网络为例：

            - **子网掩码**：`255.255.255.0`（/24）
            - **网段**：`192.168.0.0`（网络地址，主机位全为 0）
            - **广播地址**：`192.168.0.255`（主机位全为1）
            - **可用IP地址**：`192.168.0.1` - `192.168.0.254`（共 254 个可用地址）

        - 内网专用 IP 地址：地址空间中专门保留给内部网络使用的地址，**永远不会被公网分配**

            | 类别     | 地址范围                      | CIDR表示       | 子网掩码    | 地址数量 | 典型场景           |
            | :------- | :---------------------------- | :------------- | :---------- | :------: | :----------------- |
            | A 类私有 | 10.0.0.0 - 10.255.255.255     | 10.0.0.0/8     | 255.0.0.0   | 1677 万  | 大型企业、数据中心 |
            | B 类私有 | 172.16.0.0 - 172.31.255.255   | 172.16.0.0/12  | 255.240.0.0 |  104 万  | 中型企业           |
            | C 类私有 | 192.168.0.0 - 192.168.255.255 | 192.168.0.0/16 | 255.255.0.0 |  6.5 万  | 家庭、小型办公室   |

            1. **路由器不转发**：目标地址为私有地址的分组不会被路由器转发到公网
            2. **NAT 转换**：私有地址主机通过网络地址转换 `NAT` 技术访问互联网
            3. **可重复使用**：不同局域网可以使用相同的私有地址段，不会冲突

        - 无类域间路由 `Classless Inter Domain Routing (CIDR)`

            子网部分可以在任意位置，不再受传统分类中 A/B/C 类固定网络位的约束，仍然用 `a.b.c.d/x` 来表示 IP 地址

            - 解决了传统分类地址的浪费问题

            - 支持路由聚合 `Route Aggregation` ，将内部多个小网络合并为一个大的地址前缀，向外部只宣告**聚合后的超网路由**，隐藏内部细节，大幅减少路由表的规模

    - 路由的转发表与转发算法

        - 转发表 `Forwarding Table` 的基本结构

            | 目的网络 `Destination` | 子网掩码 `Mask` | 下一跳 `Next Hop` | 接口 `Interface` |
            | :--------------------- | :-------------- | :---------------- | :--------------- |
            | 202.38.73.0            | 255.255.255.192 | IP~x~             | Lan1             |
            | 202.38.64.0            | 255.255.255.192 | IP~y~             | Lan2             |
            | Default                | -               | IP~z~             | Lan0             |
            | ……                     | ……              | ……                | ……               |

        - 转发算法

            1. **提取目的地址**：从收到的 IP 数据报首部提取目的 IP 地址 `D`
            2. **逐条匹配**：对转发表中的每个表项，执行 `(D & Mask) == Destination`
            3. **最长前缀匹配**：若多个表项匹配，选择匹配**前缀最长**的表项
            4. **默认路由**：若都没有找到，使用默认表项 `0.0.0.0/0` 转发数据报

    - IP 地址的获取与 DHCP 协议

        | 获取 IP 地址的方式 | 特点                       | 适用场景                    |
        | :----------------- | :------------------------- | :-------------------------- |
        | **手动配置**       | 管理员在系统文件中静态配置 | 服务器、网络设备、固定主机  |
        | **DHCP 动态配置**  | 自动从服务器获取，即插即用 | 普通 PC、移动设备、访客网络 |

        - DHCP 协议概论

            动态主机配置协议 `Dynamic Host Configuration Protocol (DHCP)` 是一种**客户端-服务器模型**的应用层协议，基于**UDP**传输，是目前应用最广泛的 IP 地址分配协议，协议实现的核心功能如下：

            1. 允许主机加入网络时自动获得 IP 地址
            2. 支持地址租期管理：到期可续租，不用时自动回收
            3. 支持移动用户无缝接入和离开网络
            4. 集中管理 IP 地址，避免手动配置导致的地址冲突

            > 通常，整个网络会有一个专用 DHCP 服务器，或将该服务集成于于路由器中，服务路由器所连接的所有子网

        - DHCP 四步握手

            ```mermaid
            sequenceDiagram
                participant C as DHCP客户端<br/>(0.0.0.0:68)
                participant S as DHCP服务器<br/>(223.1.2.5:67)
                
                Note over C: 新主机接入网络<br/>无IP地址
                
                C->>S: ① DHCP Discover<br/>广播 255.255.255.255<br/>"有DHCP服务器吗？"
                
                S->>C: ② DHCP Offer<br/>广播/单播<br/>"我是服务器，提供IP 223.1.2.4"
                
                C->>S: ③ DHCP Request<br/>广播<br/>"我要使用这个IP地址"
                
                S->>C: ④ DHCP ACK<br/>广播/单播<br/>"确认！地址归你了"
                
                Note over C: 获得IP地址<br/>可进行通信
            ```

            | 步骤           | 报文类型 | 源地址       | 目的地址             | 核心作用                               |
            | :------------- | :------- | :----------- | :------------------- | :------------------------------------- |
            | **① Discover** | 发现     | `0.0.0.0:68` | `255.255.255.255:67` | 客户端广播寻找可用 DHCP 服务器         |
            | **② Offer**    | 提供     | 服务器 IP:67 | `255.255.255.255:68` | 服务器从地址池选 IP，回应租约信息      |
            | **③ Request**  | 请求     | `0.0.0.0:68` | `255.255.255.255:67` | 客户端选择第一个收到的 Offer，广播确认 |
            | **④ ACK**      | 确认     | 服务器 IP:67 | `255.255.255.255:68` | 服务器正式分配地址，客户端可用         |

            - **为什么用广播 ？** 客户端初始阶段没有 IP 地址，无法定向发送单播，必须通过广播（`255.255.255.255`）或以太网广播（`FF:FF:FF:FF:FF:FF`）进行通信
            - **为什么用 UDP 而非 TCP ？** TCP 需要三次握手建立连接，但客户端此时无 IP 地址，无法进行连接建立；UDP 无连接、可广播的特性完美契合此场景
            - **端口分配**：服务器监听 **UDP 67 端口**，客户端使用 **UDP 68 端口**

            > 优化机制：如果客户端之前使用过某个 IP 且租期未过期，可以跳过前两步，直接发送 `DHCP Request` 请求续租

        - DHCP 的返回值

            | 参数                     | 作用                               | 示例值                |
            | :----------------------- | :--------------------------------- | :-------------------- |
            | IP 地址                  | 主机在网络中的唯一标识             | `192.168.1.101`       |
            | 子网掩码 `Subnet Mask`   | 区分网络号和主机号                 | `255.255.255.0`       |
            | 默认网关 Default Gateway | 第一跳路由器 IP 地址，用于访问外网 | `192.168.1.1`         |
            | DNS 服务器地址           | 域名解析服务地址                   | `68.87.71.226`        |
            | 域名 `Domain Name`       | 本地域名后缀                       | `hst1.ma.comcast.net` |
            | 租期 `Lease Time`        | IP地址有效使用时长                 | 3600 秒               |

        - DHCP 的运行过程

            1. 联网笔记本需要获取自己的 IP 地址、第一跳路由器地址（网关地址）和 DNS 服务器地址：采用 DHCP 协议
            2. DHCP 请求被首先封装在 UDP 段中，然后封装在 IP 数据报中，最后封装在以太网的帧中
            3. 以太网帧在局域网范围内广播（目的 MAC：`FFFFFFFFFFFF`），被运行 DHCP 服务的路由器收到
            4. 以太网帧解封装成 IP，IP 解封装成 UDP，解封装成 DHCP
            5. DHCP 服务器生成**DHCP ACK 报文**，报文内容：客户端 IP 地址、第一跳路由器 IP 地址、DNS 域名服务器 IP 地址
            6. 服务器将 ACK 报文逐层封装后，把数据帧转发至客户端
            7. 客户端对收到的数据逐层解封装，最终得到 DHCP 报文
            8. 客户端完成配置：获得本机 IP、DNS 服务器信息、第一跳路由器 IP

            1. **NAT（网络地址转换）**：通过私有地址复用，缓解IPv4地址空间压力
            2. **IPv6**：采用128位地址空间，提供约3.4×10³⁸个地址，从根本上解决地址不足
            3. **CIDR 路由聚合**：提高地址分配效率，减少路由表膨胀

- `4.3.4` NAT：网络地址转换

    - NAT 基本概念

        网络地址转换 `Network Address Translation (NAT)` 是一种将内网私有 IP 地址转换为公网 IP 地址的技术，使得本地网络中的所有设备对外共享一个或少量公网 IPv4 地址

        | 使用 NAT 的动机      | 具体解释                                                     |
        | -------------------- | ------------------------------------------------------------ |
        | **节省公网IP地址**   | 不需要从 ISP 分配一块地址，可用一个 IP 地址用于所有局域网设备，大幅节省 IPv4 地址资源 |
        | **内网地址灵活变更** | 可以在局域网内随意改变设备的地址，而**无需通知外界**（外部只看到 NAT 公网 IP） |
        | **便于更换ISP**      | 可以改变 ISP（公网地址变化）而不需要改变内部网络设备的 IP 地址配置 |
        | **增强地址隐蔽性**   | 局域网内部设备没有明确的公网地址，对外不可见，形成天然的地址隔离 |

        - NAT 常见误区

            - **NAT 不允许外部直接访问内网主机，因此内网主机不能作为服务器**

                > 通过静态端口映射、UPnP 或 STUN/TURN/ICE 等 NAT 穿越技术，外网主机可以直接连接到 NAT 后的内网服务器，P2P 应用、VoIP、视频会议等都广泛使用这些技术

            - **NAT 被视作安全的特征，提供了安全防护**

                > NAT 只是隐藏了内网主机的真实 IP 地址，提供了一定的 “隐蔽性”，但不是真正的安全机制，它无法阻止恶意流量（如病毒、木马）从内网向外传播，也无法防御针对公网 IP 的攻击
                >
                > 真正的安全需要依赖防火墙、入侵检测系统（IDS）、入侵防御系统（IPS）等专门的安全设备

    - NAT 的实现机制

        1. 出方向数据包处理（内网 → 外网）
            - **替换源 IP 地址和源端口号**为 NAT 路由器的公网 IP 地址和一个**新的端口号**
            - **目标 IP 和端口保持不变**
            - 远端服务器看到的"发送者"就是 NAT 公网 IP，完全不知道内网主机的真实存在
        2. 建立 NAT 转换表
            - NAT 路由器必须**记住每个转换替换对**，存储在 **NAT 转换表** `Translation Table` 中
            - 表项格式：`(源IP, 源端口)`  $\Leftrightarrow$​  `(NAT IP, 新端口)` + **传输层协议号（TCP=6、UDP=17、ICMP=1）**
        3. 入方向数据包处理（外网 → 内网）
            - 根据返回数据包的**目的 IP 地址和目的端口号**，检索 NAT 转换表
            - 找到对应的映射记录后，**替换目的 IP 和目的端口**为内网主机的原始地址
            - 将数据报转发到内部网络

    - NAT 的局限性与争议

        | 争议点                     | 详细说明                                                     |
        | -------------------------- | ------------------------------------------------------------ |
        | **① 路由器"越层"操作**     | 传统路由器应只处理网络层信息<br/>但 NAT 需要查看并修改传输层的端口号，这违背了分层原则 |
        | **② 违反端到端原则**       | "端到端原则"——网络只负责尽力传输，复杂性应放在网络边缘（主机端）<br/>NAT 引入了中间节点的状态维护，增加了网络复杂性 |
        | **③ 外网无法主动连接内网** | NAT 表项由内网主动访问外网时动态建立<br/>除非预先配置映射，外部主机无法主动发起连接到内网主机 |
        | **④ P2P 应用受阻**         | P2P 应用需要双方直接通信，NAT 打破了这种直连可能性<br/>应用设计者必须额外考虑 NAT 穿透 |
        | **⑤ 地址短缺另有解决**     | NAT 被视为 IPv4 地址不足的"权宜之计"，根本解决方案是 IPv6 的庞大地址空间 |

    - NAT 穿越问题 `NAT Traversal` 及其解决

        NAT 穿越问题：外网客户端无法主动连接到 NAT 后的内网服务器，且 NAT 路由器会主动拒绝未由内网发起的连接请求

        1. 静态端口映射
            - **原理**：手动配置 NAT 路由器，将公网 IP 的某个固定端口永久映射到内网某台服务器的 IP 和端口
            - **示例**：将 138.76.29.7:25000 固定转发到 10.0.0.1:25000
            - **优点**：配置简单，稳定可靠
            - **缺点**：需要手动配置，不适合动态变化的网络，且每个服务需要占用一个公网端口
        2. 通用即插即用互联网网关设备 `Universal Plug and Play Internet Gateway Device (UPnP IGD)`
            - **原理**：允许内网主机自动向 NAT 路由器请求端口映射，无需手动配置
            - **功能**：获取网络的公网 IP 地址；列举已存在的端口映射；动态增 / 删端口映射（有租用时间限制）
            - **优点**：自动化配置，适合家庭网络和普通用户
            - **缺点**：存在安全风险，可能被恶意程序利用开放端口
        3. 中继方案（如 Skype 早期使用）
            - **原理**：通过第三方中继服务器中转所有数据
            - **流程**：
                1. NAT 后的内网服务器主动连接到中继服务器
                2. 外网客户端也连接到中继服务器
                3. 中继服务器在两个连接之间桥接转发数据
            - **优点**：可以穿越任何类型的 NAT
            - **缺点**：延迟高、带宽消耗大、成本高，存在单点故障风险
        4. 主流 NAT 穿越协议
            - **STUN**：简单穿越 UDP 的中继，允许内网主机发现自己的公网地址和端口，然后直接建立 P2P 连接
            - **TURN**：中继穿越 NAT，当 STUN 无法直接建立连接时使用，通过中继服务器转发数据
            - **ICE**：交互式连接建立，结合 STUN 和 TURN，自动尝试所有可能的连接方式，选择最佳路径

- `4.3.5` IPv6

    - 从 IPv4 到 IPv6

        - 核心动机：IPv4 采用 32 位地址空间，理论上仅能提供约 43 亿个唯一地址，随着互联网普及和物联网设备爆发式增长，地址空间早已面临枯竭危机

        | 其他动机           | 相比 IPv4 的变化                                             |
        | ------------------ | ------------------------------------------------------------ |
        | **加速路由处理**   | 固定长度头部（40 字节），无需解析变长选项，路由器可用 ASIC 硬件线速转发 |
        | **移除头部校验和** | 每跳无需重新计算校验和，降低路由器 CPU 负担                  |
        | **移除分片机制**   | 路由器不再分片，仅由源主机分片，简化路由器处理逻辑           |
        | **支持 QoS**       | 引入 Flow Label 字段，便于流分类和负载均衡                   |
        | **内置安全性**     | IPsec 作为推荐扩展（SHOULD），支持端到端加密认证             |

        - 过渡手段

            互联网规模庞大，无法在某一个 日子保证所有设备全部升级为 IPv6，因此必须支持 IPv4 和 IPv6 网络长期共存

            \[\rightarrow\] 需要过渡手段来支持：隧道技术 `Tunneling`

            将 **IPv6 数据报完整封装** `Encapsulation`  **在 IPv4 数据报的有效载荷中**，通过现有的 IPv4 骨干网传输

            - **隧道入口**：双栈路由器为 IPv6 数据报添加 IPv4 头部，外层 IPv4 源地址为入口路由器的 IPv4 地址，目的地址为出口路由器的 IPv4 地址

            - **隧道传输**：中间的纯 IPv4 路由器将其当作普通 IPv4 数据报转发，完全不知道内部封装的 IPv6 数据

            - **隧道出口**：双栈路由器剥去外层 IPv4 头部，还原出原始 IPv6 数据报，继续在 IPv6 网络中转发

            ```mermaid

                    A[("IPv6 主机 A")] -->|IPv6 数据报| B[("双栈路由器 B<br/>IPv6/v4 隧道入口")]
                    B -.->|"隧道（IPv4 网络）"| E[("双栈路由器 E<br/>IPv6/v4 隧道出口")]
                    E -->|IPv6 数据报| F[("IPv6 主机 F")]
                end

                    A2[("A")] --> B2[("B")]
                    B2 --> C2[("C<br/>纯 IPv4 路由器")]

                end
            ```

    - IPv6 数据报格式

        IPv6 采用**固定 40 字节的基本头部**，且传输过程中路由器不允许对数据报进行分片，大幅提升了转发效率

        | 字段                            | 长度   | 作用                                                         |
        | ------------------------------- | ------ | ------------------------------------------------------------ |
        | 版本 `Version`                  | 4 位   | 固定值为 6，标识 IPv6 协议                                   |
        | 优先级 `Priority`               | 8 位   | 标示数据流的优先级，用于 QoS 调度                            |
        | 流标签`Flow Label`              | 20 位  | 标识属于同一个 "流" 的数据报，使路由器能对同一流的数据包进行相同处理<br/>**注意：目前 "流" 的概念尚未被严格统一定义** |
        | 有效载荷长度<br/> `Payload Len` | 16 位  | 表示 IPv6 基本头部之后所有数据的长度（包括扩展头部和上层协议数据） |
        | 下一个头部<br/>`Next Header`    | 8 位   | 标识紧跟在基本头部之后的下一个头部类型<br/>可指向 TCP/UDP 等上层协议，也可指向 IPv6 扩展头部 |
        | 跳数限制`Hop Limit`             | 8 位   | 对应 IPv4 的 TTL 字段，每经过一个路由器值减 1，减至 0 时丢弃数据报<br/>改名是因为该字段实际记录跳数而非时间 |
        | 源 / 目的地址                   | 128 位 | IPv6 的源和目的 IP 地址，地址空间是 IPv4 的 2^96^ 倍         |

        | 被移除的字段                       | IPv4 中的作用                            | IPv6 的处理方式                                              |
        | ---------------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
        | 头部校验和<br/>`Header Checksum`   | 每跳路由器验证并重新计算（TTL 的变化）   | 完全移除，依赖链路层 CRC（如以太网 FCS）和传输层校验和（TCP/UDP） |
        | 分片字段 `Fragmentation` ` Fields` | Identification / Flags / Fragment Offset | 路由器不再分片<br/>需要分片时由源主机使用**分片扩展头部**<br/>（Fragment Header, Next Header=44） |
        | 选项字段 `Options`                 | 变长选项嵌入头部                         | 移至扩展头部 `Extension Headers`<br/>通过 Next Header 链式串联<br/>仅在需要时由目的节点处理 |

        其他关键变化：

        1. **选项字段重构**：选项不再是基本头部的一部分，而是作为独立的扩展头部存在

            常见扩展头部包括逐跳选项头、路由头、分片头、认证头等，支持灵活扩展且不影响基本头部处理

        2. **ICMPv6 协议升级**

            - 保留了 ICMPv4 的基本功能（如 ping、traceroute）
            - 新增报文类型：如 "Packet Too Big"（类型 2，代码 0），用于路径 MTU 发现
            - 集成多播组管理功能：用 MLD（多播监听发现）协议替代 IPv4 的 IGMP
            - 集成邻居发现协议 (NDP)：替代 IPv4 的 ARP、路由器发现和重定向功能，全部通过 ICMPv6 报文实现，更加安全高效

        3. **支持的最小 MTU 变大**：RFC 8200 强制要求每条 IPv6 链路支持的最小 MTU 为 **1280 字节**（远高于 IPv4 的 576 字节），确保基本报文无需分片即可传输

    - IPv6 现状

        - **全球部署情况**
            - Google 统计数据显示，截至 2025 年，约 41% 的用户通过 IPv6 访问 Google 服务
            - 截至 2026 年 4 月，全球 IPv6 用户占比已达到 45%-50%，且周末 IPv6 使用率通常高于工作日

        - **中国部署特点**：以移动网络和内网流量为主，大量 IPv6 流量发生在国内网络内部；三大运营商的移动网络已基本全面支持 IPv6，家庭宽带 IPv6 普及率也在快速提升

        - **IPv6 迁移困境**：NAT 技术通过地址共享大幅延长了 IPv4 的寿命，加上 IPv4 地址租赁和交易市场的存在，企业缺乏迁移到 IPv6 的紧迫感，因为 IPv6 带来的短期商业收益极为有限

## `4.4` 通用转发与 SDN

### `4.4.1` 通用转发：“匹配 + 动作” 抽象

- `4.4.1.1` 传统转发

    传统路由器采用**基于目的转发** `Destination-Based Forwarding` ，仅根据目的 IP 地址查转发表决定输出端口

    这种方式功能单一，难以满足现代网络对安全、QoS、负载均衡的复杂需求

- `4.4.1.2` 广义转发（通用转发）

    - **匹配**：可以匹配数据包任意层的任意头部字段
        - 链路层：源/目的 MAC 地址、以太网类型、VLAN ID
        - 网络层：源/目的 IP 地址、IP 协议类型、IP ToS
        - 传输层：TCP/UDP 源端口、目的端口
    - **动作**：支持转发、丢弃、修改头部、复制、日志、上报控制器等多种操作，具体来说可能包括：
        - 将分组转发到指定端口
        - 丢弃分组（Drop）
        - 修改报头中的字段（如重写MAC/IP/端口）
        - 封装并转发给控制器（Packet-In）
        - 复制/泛洪/日志记录

    - 核心价值：用统一的 "匹配 + 动作" 模型描述所有网络设备的功能，包括路由器、交换机、防火墙、NAT 等

- `4.4.1.3` 软件定义网络 `Software Defined Networking (SDN)`

    - 数据平面：由大量简单的 SDN 交换机组成，仅执行控制器下发的流表规则，不做任何路由计算
    - 控制平面：由一个或多个远程控制器组成，集中计算全网路由逻辑，将结果以流表形式下发给交换机
    - 通信接口：控制器与交换机之间通过标准协议（如 OpenFlow）通信
    - 核心特点
        - **通用 Flow-based**：基于流的匹配+行动（如OpenFlow协议）
        - **控制与数据平面分离**：物理或逻辑上解耦
        - **控制平面外置**：控制功能在数据交换设备之外实现（远程控制器）
        - **可编程控制应用**：在控制器之上以网络应用形式实现各种网络功能（如路由、访问控制、负载均衡）

### `4.4.2` OpenFlow 有关 “匹配+行动” 的运行实例

OpenFlow 是目前最主流的 SDN 南向协议，定义了控制器与交换机之间的通信标准，其核心是**流表**

- `4.4.2.1` 流表的表项结构

    1. **匹配域（Match）**：用于匹配数据包的头部字段，覆盖三层：
        - 链路层：入端口、源 MAC、目的 MAC、VLAN ID、VLAN 优先级
        - 网络层：源 IP、目的 IP、IP 协议类型、TOS
        - 传输层：TCP/UDP 源端口、目的端口
    2. **动作域（Action）**：匹配成功后执行的操作，常见动作：
        - 转发到指定端口
        - 丢弃数据包
        - 修改数据包头部字段
        - 封装并转发给控制器
    3. **统计域（Stats）**：记录该流表项的匹配次数、数据包数、字节数等统计信息

- `4.4.2.2` OpenFlow "匹配 + 动作" 的典型应用

    几乎所有传统网络设备的功能都可以用 OpenFlow 的 "匹配 + 动作" 模型来描述

    - **匹配范围**：在**任意层**匹配到达分组的**任意层**头部信息（跨层匹配）
    - **本地动作**：丢弃、转发、修改头部、或将匹配的报文发送到控制器
    - **可编程性**：网络管理员/应用可以通过编程方式动态修改流表，实现灵活的网络策略

    | 网络设备   | 匹配条件                     | 执行动作             |
    | ---------- | ---------------------------- | -------------------- |
    | 路由器     | 目的 IP 地址（最长前缀匹配） | 转发到下一跳端口     |
    | 二层交换机 | 目的 MAC 地址                | 转发到对应端口或泛洪 |
    | 防火墙     | 源 IP + 目的 IP + 端口号     | 允许或禁止（丢弃）   |
    | NAT 设备   | 源 IP + 源端口               | 重写为公有 IP 和端口 |

    运行实例：

    - **基于目的 IP 的转发**：匹配 `IP Dst=51.6.0.8`，动作 `forward(6)`，即所有发往 51.6.0.8 的数据包从端口 6 转发

    - **防火墙功能**：匹配 `TCP Dst Port=22`，动作`drop`，即禁止所有 SSH 访问

    - **基于 MAC 地址的转发**：匹配 `MAC Dst=22:A7:23:11:E1:02`，动作 `forward(3)`，即链路层的转发

## `4.5` 中间盒

- `4.5.1` 中间盒的基本概念

    中间盒 `Middleboxes` 是指在源主机和目标主机之间的数据路径上，执行除 IP 路由器的正常标准功能**（根据目的 IP 地址进行数据包转发）**外的其他功能的任何中间设备

    | 常见的中间盒类型         | 中文                | 部署场景         | 核心功能                                                   |
    | ------------------------ | ------------------- | ---------------- | ---------------------------------------------------------- |
    | **NAT**                  | 网络地址转换        | 家庭、手机、机构 | 私有 IP $\leftrightarrow$ 公网 IP 转换，缓解 IPv4 地址枯竭 |
    | **Firewalls/IDS**        | 防火墙/入侵检测系统 | 企业、ISP、IDC   | 安全策略过滤、流量监控、威胁检测                           |
    | **Load Balancers**       | 负载均衡器          | 数据中心、企业   | 流量分发、服务器健康检查、高可用                           |
    | **Caches**               | 缓存服务器          | CDN、移动网络    | 内容缓存、加速访问、减少回源                               |
    | **Application-specific** | 应用特定中间盒      | 服务提供商、CDN  | 协议优化、内容压缩、转码、SSL 卸载                         |

    中间盒与路由器的本质区别：

    | 特性         | 标准 IP 路由器               | 中间盒                               |
    | ------------ | ---------------------------- | ------------------------------------ |
    | **功能**     | 基于目的 IP 查表转发         | 修改/过滤/转换/监控分组              |
    | **状态性**   | 通常无状态（或仅有路由状态） | **有状态**（记住连接、会话、流信息） |
    | **透明度**   | 对 IP 分组透明               | 可能终止并重创流、修改首部/载荷      |
    | **操作对象** | 主要检查 IP 首部             | 可深入检查传输层甚至应用层           |
    | **部署位置** | 网络核心                     | 网络边缘（接入点、边界）             |

- `4.5.2` IP 沙漏模型

    互联网的协议体系结构呈现出独特的**沙漏形状**，IP 协议位于最细的 “腰部”，是整个互联网的**核心统一协议**

    - **上下层多样性**：物理层、链路层、传输层、应用层可以有多种协议
    - **单一网络层协议**：IP是唯一的网络层协议，必须在**数十亿**联网设备上实现

    > **"Everything over IP, IP over Everything"**：所有应用都运行在IP之上，IP可以运行在所有链路技术之上

    - 现实演变：细腰上移

        由于中间盒（尤其是NAT和防火墙）的广泛部署，原始的 "IP 沙漏" 正在发生演变

        > 根据IETF草案研究，**UDP 和 TCP 正在成为新的"细腰"**
