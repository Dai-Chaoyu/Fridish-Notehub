# 第 2 章 应用层

## `2.1` 应用层协议原理

- `2.1.1` 网络应用体系结构

    网络应用的核心在于**端系统运行程序**，通过网络基础设施实现通信；网络核心（路由器、交换机等）只负责数据转发，**不处理应用层数据**

    1. 客户-服务器体系结构 `Client-Server Paradigm` 

        | 角色       | 特征                                                         |
        | ---------- | ------------------------------------------------------------ |
        | **服务器** | 永久在线 `Always-on` 、固定 IP 地址与端口号、通常位于数据中心，支持大规模扩展 |
        | **客户端** | 间歇性连接、动态 IP、主动与服务器通信、**不直接与其他客户端通信** |

        **典型应用**：HTTP (Web 浏览)、FTP (文件传输)、SMTP (电子邮件发送)、IMAP (电子邮件接收)

    2. P2P 体系结构 `Peer-to-Peer Paradigm` 

        | 特征         | 说明                                         |
        | ------------ | -------------------------------------------- |
        | 无中心服务器 | （几乎）没有一直运行的服务器                 |
        | 对等通信     | 任意端系统之间可直接通信                     |
        | 双重角色     | 每个节点**既是客户端又是服务器**             |
        | 自扩展性     | 新节点加入带来新服务能力，但也增加管理复杂度 |
        | 动态性       | 节点间歇性连接且可改变 IP 地址               |

        **典型应用**：BitTorrent 文件共享、Windows 更新的 P2P 分发

    3. C/S 与 P2P 混合体系结构

        这是当前绝大多数主流应用采用的模式，结合了两者的优点：

        - **Napster**：文件搜索使用 C/S 模式（集中式索引服务器），文件传输使用 P2P 模式。
        - **即时通信**：在线检测和用户定位使用 C/S 模式（用户向中心服务器注册 IP 地址），用户之间聊天使用 P2P 模式。
        - **视频会议 (Zoom)**：信令控制使用 C/S 模式，媒体流传输使用 P2P 或混合模式。

    | 特性        | 客户 - 服务器 (C/S)          | P2P 对等模式                 |
    | ----------- | ---------------------------- | ---------------------------- |
    | 服务器角色  | 专用、一直运行               | 无专用服务器，节点双重身份   |
    | 通信方式    | 客户端 - 服务器单向发起      | 任意节点之间直接通信         |
    | IP 地址要求 | 服务器必须固定 IP            | 节点可以使用动态 IP          |
    | 可扩展性    | 受服务器性能限制，需集群扩展 | 自扩展性好，节点越多能力越强 |
    | 管理复杂度  | 低，集中式管理               | 高，分布式管理               |
    | 典型应用    | Web、电子邮件、FTP           | BitTorrent、早期 Skype       |

- `2.1.2` 进程通信与套接字

    - 进程 `Process`

        进程是**在主机上运行的应用程序**，不同主机上的进程通过**应用层协议**交换报文 `Message` 进行通信

        - **客户端进程**：发起通信的进程
        - **服务器进程**：等待连接的进程
        - **注意**：P2P 中每个节点同时包含客户端进程和服务器进程 —— **发起通信的是客户端进程，等待连接的是服务器进程**

    - 套接字 `Socket`

        Socket 是**应用层与传输层之间的接口** `API` ，是应用程序与传输层协议交互的端点

        ```mermaid
        sequenceDiagram
            participant A as 发送进程
            participant S as Socket API
            participant T as 传输层
            participant N as 网络层
            participant I as 链路层 Internet
            participant R as 接收进程
            
            A->>S: 将报文推入门户
            S->>T: 由操作系统控制
            T->>N: 封装为报文段
            N->>I: 路由传输
            I->>N: 到达目的主机
            N->>T: 交付给传输层
            T->>S: 由操作系统控制
            S->>R: 从门户接收报文
        ```

        发送方通过 Socket 将报文发出，接收方从 Socket 接收报文，无需关心底层传输细节

    - 进程寻址

        进程间跨网络的通信，必须要有唯一的标识符来确定一个进程：IP + 端口号 `Port Number`

        - **IP 地址**：32 位 (IPv4)，唯一标识互联网上的一台主机。

        - **端口号**：16 位 (0-65535)，唯一标识主机上的一个应用进程。

            | 服务     | 对应的知名端口号 |
            | -------- | ---------------- |
            | HTTP     | 80               |
            | HTTPS    | 443              |
            | SMTP     | 25               |
            | FTP 控制 | 21               |
            | FTP 数据 | 20               |
            | DNS      | 53               |
            | Telnet   | 23               |

- `2.1.3` 应用层协议

    应用层协议定义了运行在不同端系统上的应用进程如何相互交换报文

    | 要素             | 含义                                     |
    | ---------------- | ---------------------------------------- |
    | 交换的信息类型   | 请求报文 `Request` 、响应报文 `Response` |
    | 语法 `Syntax`    | 报文中各字段的格式与结构                 |
    | 语义 `Semantics` | 字段中信息的含义                         |
    | 规则 `Rules`     | 进程何时发送/响应报文、如何响应          |

    - **公开协议**：由 RFC 文档定义，任何人都可以使用和实现，如 HTTP、SMTP、DNS。
    - **专用 (私有) 协议**：由公司自行定义，不对外公开，如微信、QQ、Zoom 的内部协议。

- `2.1.4` 应用对网络传输的需求

    | 需求类型     | 说明                                                   | 典型应用             |
    | ------------ | ------------------------------------------------------ | -------------------- |
    | **可靠性**   | 100%可靠传输（如文件）或容忍一定丢失（如音频）         | 文件传输、电子邮件   |
    | **吞吐量**   | 最小吞吐量保证（多媒体）或弹性应用（充分利用可用带宽） | 视频流、文件传输     |
    | **定时保证** | 严格的时间限制，对数据传输有时效性要求                 | 实时音视频、在线游戏 |
    | **安全性**   | 加密、数据完整性、可认证性                             | 网银、VPN            |

    $\rightarrow$ 传输层协议 TCP & UDP

    | TCP 服务特性     | 说明                                           |
    | ---------------- | ---------------------------------------------- |
    | **可靠传输**     | 通过确认、重传机制保证数据无差错、按序到达     |
    | **流量控制**     | 防止发送方淹没接收方（滑动窗口机制）           |
    | **拥塞控制**     | 网络拥塞时抑制发送方（慢启动、拥塞避免等算法） |
    | **面向连接**     | 数据传输前需三次握手建立连接                   |
    | **不提供的服务** | 不保证定时、最小吞吐量和安全性                 |

    | UDP 服务特性   | 说明                                         |
    | -------------- | -------------------------------------------- |
    | **不可靠传输** | "尽力而为"，不保证到达、不保证顺序           |
    | **无连接**     | 无需建立连接，直接发送数据                   |
    | **无流量控制** | 发送方不感知接收方状态                       |
    | **无拥塞控制** | 发送速率由应用层决定，网络拥塞时不会自动降速 |
    | **低开销**     | 头部仅 8 字节（TCP 为 20 字节）              |

    | 常见应用        | 应用层协议                     | 传输层协议/端口                         |
    | --------------- | ------------------------------ | --------------------------------------- |
    | 电子邮件        | SMTP (RFC 5321)                | TCP 25 / 587 / 993                      |
    | 远程终端访问    | Telnet (RFC 854)               | TCP 23                                  |
    | Web             | HTTP (RFC 7230) / HTTPS        | TCP 80 / 443                            |
    | 文件传输        | FTP (RFC 959)                  | TCP 20（数据）/ 21（控制）              |
    | 流媒体          | HTTP / DASH                    | TCP 80                                  |
    | VoIP / 网络电话 | SIP (RFC 3261), RTP (RFC 3550) | UDP/TCP                                 |
    | 域名解析        | DNS (RFC 1035)                 | **UDP 53**（查询）/  TCP 53（区域传输） |

- `2.1.5` 安全 TCP：TLS/SSL

    TCP 和 UDP Socket 本身**不提供加密**，明文传输（包括账号、密码）存在安全风险，**应用层**在其之上额外实现了一些加密协议作用于传输层以保障数据传输安全 $\rightarrow$ `Transport Layer Security (TLS)` 

    - **功能**：提供加密的 TCP 连接、数据完整性校验、端到端认证
    - **机制**：应用程序使用 SSL / TLS 库，发送的明文经过加密后在互联网传输
    - **应用**：HTTPS（HTTP over TLS）、SMTPS、IMAPS等

## `2.2` Web and HTTP

- `2.2.1` Web 与 HTTP 概述

    - **Web 网页组成**

        - Web 网页由多个**对象**组成，常见对象包括 HTML 文件、JPEG 图像、Java 小程序、声音文件等

        - 每个网页包含一个**基本 HTML 文件**，该文件通过**链接（引用）** 指向其他对象

        - 所有对象都通过 **URL（统一资源定位符）** 进行唯一标识和访问

            ```
            URL（统一资源定位符）结构：
            http://www.someschool.edu:80/someDept/pic.gif
            \___/ \_________________/\_/ \______________/
             协议         主机名       端口      路径名
            ```

    - HTTP 协议概述

        超文本传输协议 `Hypertext Transfer Protocol (HTTP)` 是 Web 的应用层协议，采用客户/服务器模式

        - HTTP 与 TCP ：HTTP 是**应用层协议**，使用 **TCP** 作为传输层协议

            1. 客户端发起与服务器的 TCP 连接（建立套接字），目标端口为 80
            2. 服务器接受 TCP 连接请求
            3. 浏览器（HTTP 客户端）与 Web 服务器（HTTP 服务器）交换 HTTP 报文
            4. TCP 连接关闭

        - **HTTP 无状态特性**：服务器**不维护任何关于客户端的历史信息**，每次请求都是独立的

            - 服务器设计简单，无需存储客户端状态
            - 无状态服务器能够支持更多的并发客户端

            > 如果在协议层维护状态，服务器需要处理状态同步、故障恢复等问题
            >
            > 因此 HTTP 选择无状态设计，而通过 **Cookie 机制**在应用层实现状态管理

- `2.2.2` HTTP 连接类型

    - 非持久 HTTP 连接（HTTP/1.0 默认）

        - **核心规则**：一个 TCP 连接最多只能传输一个对象，下载多个对象需要建立多个 TCP 连接

        - **工作示例**：

            假设访问一个包含 1 个 HTML 文件和 10 个 JPEG 图像的网页：

            ```mermaid
            sequenceDiagram
                participant C as 客户端
                participant S as 服务器
                
                Note over C,S: 获取基础HTML文件
                C->>S: 1. 建立TCP连接 (SYN)
                S->>C: 2. 确认连接 (SYN-ACK)
                C->>S: 3. 确认并发送HTTP请求 (ACK + GET)
                S->>C: 4. 返回HTTP响应 (HTML文件)
                S->>C: 5. 关闭TCP连接
                
                Note over C,S: 获取10个JPEG图像（重复10次）
                loop 10个JPEG对象
                    C->>S: 建立TCP连接
                    C->>S: 发送HTTP请求
                    S->>C: 返回JPEG图像
                    S->>C: 关闭连接
                end
            ```

            $\rightarrow$ 总共需要建立 **11 个 TCP 连接**

        - **响应时间模型**

            - 往返时间 `Round-Trip Time (RTT)` ：一个小分组从客户端到服务器再返回客户端的时间（忽略传输时间）

            - 单个对象的响应时间 = 2 `RTT` + 文件传输时间

                - 1 个 RTT：建立 TCP 连接（三次握手前两次）
                - 1 个 RTT：发送 HTTP 请求并等待响应
                - 文件传输时间：服务器将文件传输到客户端的时间

                > 在 TCP 三次握手的第三个 ACK 报文中，客户端可以同时携带 HTTP 请求报文，因此建立连接和发送请求可以部分重叠，但总体估算仍为 2 `RTT`

        - **缺点**：

            - 每个对象都需要 2 `RTT` 的开销
            - 操作系统需要为每个 TCP 连接分配资源
            - 即使浏览器使用并行 TCP 连接，仍会产生大量连接开销

    - 持久 HTTP 连接（HTTP / 1.1 默认）

        - **核心规则**：多个对象可以在同一个 TCP 连接上传输，服务器发送响应后仍保持连接

        - 标识：请求 / 响应首部包含 `Connection: keep-alive` 字段

        - 两种工作模式：

            | 特性           | 非流水方式 `Without Pipeline`  | 流水方式 `With Pipeline`    |
            | -------------- | ------------------------------ | --------------------------- |
            | **请求时机**   | 收到前一个响应后才能发新请求   | 遇到引用对象立即发送请求    |
            | **RTT 开销**   | 每个对象 1 个 `RTT`            | 所有对象可能只需 1 个 `RTT` |
            | **服务器空闲** | 发送完一个对象后等待下一个请求 | 可以连续发送多个响应        |
            | **HTTP 版本**  | 可选模式                       | **HTTP/1.1 默认模式**       |

            > HTTP/1.1 默认使用**带流水线的持久连接**，这是目前 Web 的主流工作方式
            >
            > 与非持久连接相比，持久连接不仅减少了 RTT 开销，还降低了 TCP **缓启动**带来的延迟，因为后续对象复用已建立好的 TCP 连接，不需要重新经历慢启动阶段

- `2.2.3` HTTP 报文结构

    HTTP 报文分为**请求报文**（客户端→服务器）和**响应报文**（服务器→客户端）两类，均采用 ASCII 编码

    - HTTP 请求报文

        基本结构：请求行 `Request Line` $\rightarrow$ 首部行 `Header Lines` $\rightarrow$ 空行 `CRLF` $\rightarrow$ 实体体 `Entity Body`（可选）

        ```http
        GET /index.html HTTP/1.1 \r\n
        <方法>  <URL>   <HTTP版本> CRLF
        Host: www.net.cs.umass.edu\r\n
        User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15; rv:80.0)\r\n
        Accept: text/html,application/xhtml+xml\r\n
        Accept-Language: en-us,en;q=0.5\r\n
        Accept-Encoding: gzip,deflate\r\n
        Connection: keep-alive\r\n
        \r\n
        ```

        > **注意**：`\r\n`（回车换行符）是 HTTP 报文的分隔符，首部行结束后必须有一个空行（即连续两个 CRLF），表示首部结束、实体体开始

        - 常见的请求方法

            | 方法   | 用途                       | 特点                                     |
            | ------ | -------------------------- | ---------------------------------------- |
            | GET    | 向服务器请求指定资源       | 数据放在 URL 中，长度有限制，可被缓存    |
            | POST   | 向服务器提交数据（如表单） | 数据放在实体体中，无长度限制，不可被缓存 |
            | HEAD   | 只请求资源的首部信息       | 不返回实体体，用于故障跟踪和搜索引擎索引 |
            | PUT    | 上传文件到服务器指定位置   | 用请求体中的内容替换指定 URL 的资源      |
            | DELETE | 删除服务器上指定的资源     | 用于删除 URL 指定的文件                  |

            GET Vs. POST：

            | 对比维度         | GET                                   | POST                            |
            | ---------------- | ------------------------------------- | ------------------------------- |
            | **数据传输位置** | URL查询参数（ `?key=value` ）         | 请求实体体（Body）              |
            | **数据可见性**   | 参数暴露在 URL 中，可见               | 参数在 Body 中，不可直接见      |
            | **数据长度限制** | 受 URL 长度限制（浏览器约 2 - 4KB）   | 无限制（取决于服务器配置）      |
            | **安全性**       | 较低（参数在历史记录、日志中留存）    | 较高（但需配合 HTTPS）          |
            | **缓存**         | 可被浏览器缓存                        | 默认不被缓存                    |
            | **书签/历史**    | URL 可被收藏、回溯                    | 不可直接收藏                    |
            | **幂等性**       | 幂等（多次请求结果相同）              | 非幂等（可能重复创建资源）      |
            | **编码支持**     | 仅 ASCII 字符（需 Percent Encoding ） | 支持多种编码（JSON 、二进制等） |

    - HTTP 响应报文

        基本结构：状态行 `Status Line` $\rightarrow$ 首部行 `Header Lines` $\rightarrow$ 空行 `CRLF` $\rightarrow$ 实体体 `Entity Body`（可选）

        ```http
        HTTP/1.1 200 OK \r\n
        <HTTP版本> <状态码> <状态短语> CRLF
        Date: Tue, 08 Sep 2020 00:53:20 GMT\r\n
        Server: Apache/2.4.6 (CentOS)\r\n
        Last-Modified: Tue, 01 Mar 2016 18:57:50 GMT\r\n
        ETag: "a5b-52d015789e9ee"\r\n
        Accept-Ranges: bytes\r\n
        Content-Length: 2651\r\n
        Content-Type: text/html; charset=UTF-8\r\n
        \r\n
        <html>...</html>
        ```

        - 常见响应状态码

            | 状态码 | 状态短语              | 含义                                                        |
            | ------ | --------------------- | ----------------------------------------------------------- |
            | `200`  | OK                    | 请求成功，请求的对象包含在响应报文中                        |
            | `301`  | Moved Permanently     | 资源永久移动，新 URL 在 Location 首部中指定，客户端自动跳转 |
            | `304`  | Not Modified          | 资源未修改，客户端可使用本地缓存                            |
            | `400`  | Bad Request           | 请求语法错误，服务器无法理解                                |
            | `403`  | Forbidden             | 服务器拒绝访问                                              |
            | `404`  | Not Found             | 请求的资源在服务器上不存在                                  |
            | `500`  | Internal Server Error | 服务器内部错误                                              |
            | `503`  | Service Unavailable   | 服务不可用                                                  |

- `2.2.4` 用户 - 服务器状态维护与 Cookie

    HTTP 协议**不维护客户端与服务器之间的会话状态**，每个请求都是独立的，服务器无法识别多次请求是否来自同一个用户

    - 这意味着：无需客户端 / 服务器跟踪多步交互的 “状态”，服务器不会保存 “未完成事务” 的中间状态，无法从断点恢复交互

    - Cookie 的组成与工作流程

        Cookie 是 Web 应用实现 “状态维护” 的核心技术，包含 4 个关键组成部分

        | 组成部分                  | 说明                                                         |
        | ------------------------- | ------------------------------------------------------------ |
        | **1. HTTP 响应首部**      | 服务器通过 `Set-Cookie: ID=XX` 将标识发送给客户端            |
        | **2. HTTP 请求首部**      | 后续客户端通过 `Cookie: ID=XX` 将标识回传给服务器            |
        | **3. 客户端 Cookie 文件** | 浏览器在本地维护一个 Cookie 文件，存储多个站点的 Cookie      |
        | **4. 服务器后端数据库**   | 网站后端数据库以 Cookie 值为索引，记录用户的会话状态与历史数据 |

        ```mermaid
        sequenceDiagram
            participant C as 客户端浏览器
            participant S as Web服务器
            participant DB as 后端数据库
            
            Note over C,DB: 第一次访问（无Cookie）
            C->>S: HTTP请求（无Cookie首部）
            S->>DB: 创建新条目，生成唯一ID（如1678）
            S->>C: HTTP响应 + Set-Cookie: 1678
            C->>C: 本地Cookie文件保存
            
            Note over C,DB: 一周后再次访问
            C->>S: HTTP请求 + Cookie: 1678
            S->>DB: 查询ID=1678的用户记录
            S->>C: 返回个性化页面（推荐商品等）
        ```

    - Cookie 的作用与隐私问题

        - 应用场景：

            - **用户验证** `Authorization` ：保持登录状态
            - **购物车** `Shopping carts` ：跨页面保存选购商品
            - **推荐系统** `Recommendations` ：如"猜你喜欢"等功能的实现就依赖 Cookie
            - **会话状态** `User session state` ：如 Web 邮箱保持登录

        - 隐私风险：

            - **第一方 Cookie**：用户访问的站点本身设置的 Cookie，相对可控
            - **第三方持久 Cookie（跟踪 Cookie）**：广告商等第三方通过嵌入内容跨站点追踪用户行为，形成用户画像，这是 Cookies 最主要的隐私争议点。

            > Cookies 不是程序，只是文本标识符；它弥补了 HTTP 无状态的缺陷，但引入了隐私泄露风险。

- `2.2.5` Web 缓存（代理服务器）

    Web 缓存能够在不访问原始服务器的情况下，直接满足客户端请求，提升响应速度

    - 工作流程

        - 浏览器配置通过缓存访问 Web ，使所有 HTTP 请求先发送到缓存服务器
        - 若请求对象已在缓存中（缓存命中），直接返回对象给客户端
        - 若对象不在缓存中（缓存未命中），缓存向原始服务器请求对象，再转发给客户端并保存副本

        ```mermaid
        graph LR
            subgraph 机构网络
                C1[客户端<br/>浏览器]
                C2[客户端<br/>浏览器]
                LAN[LAN]
                CACHE[本地Web缓存<br/>Proxy Server]
            end
            
            C1 --> LAN --> CACHE
            C2 --> LAN --> CACHE
            
            CACHE -->|接入链路| R[机构路由器]
            R -->|Internet| S[原始服务器<br/>Origin Server]
        ```

    - 缓存的核心优势

        - 降低客户端请求响应时间（缓存服务器离用户更近）
        - 减少机构内部网络与互联网接入链路的流量，降低带宽成本
        - 帮助中小内容提供商更高效交付内容，提升服务稳定性

    - 链路访问利用率的计算与缓存对端到端延迟的有效降低

        > 假设场景参数如下：
        >
        > | 参数                                 | 数值       |
        > | ------------------------------------ | ---------- |
        > | 接入链路带宽                         | 1.54 Mbps  |
        > | 机构路由器到服务器 RTT               | 2 sec      |
        > | 平均对象大小                         | 100 Kbits  |
        > | 机构内浏览器对原始服务器的平均请求率 | 15 req/sec |
        > | 局域网 LAN 带宽                      | 1 Gbps     |
        >
        > 流量强度 `Traffic Intensity` = 到达速率/服务速率；当强度接近 1 时排队延迟趋于无穷
        >
        > $\rightarrow$ 平均到浏览器的速率 = 平均对象大小 $\times$ 机构内浏览器的平均请求率 = 100 Kbits $\times$ 15 req/sec = 1.5 Mbps

        1. 无任何措施下的端到端延迟

            - 接入链路流量强度 = 1.50 / 1.54 $\approx$ 97% $\rightarrow$ **接入链路排队延迟（分钟级）**
            - LAN 流量强度 = 1.5 / 1000 = 0.0015 $\rightarrow$ LAN 延迟（毫秒级）

            $\rightarrow$ 总延时 = LAN 延迟（毫秒级） + **接入链路排队延迟（分钟级）** + Internet 延迟（2s）

            > 瓶颈在接入链路，排队延迟极高！

        2. 升级接入链路（1.54 Mbps $\rightarrow$ 154 Mbps）

            - 接入链路流量强度 = 1.50 / 154 $\approx$ 0.97% $\rightarrow$ **接入链路排队延迟（毫秒级）**
            - LAN 流量强度 = 1.5 / 1000 = 0.0015 $\rightarrow$ LAN 延迟（毫秒级）

            $\rightarrow$ 总延时 = LAN 延迟（毫秒级） + **接入链路排队延迟（毫秒级）** + Internet 延迟（2 s）$\approx$ 2 s

        3. 安装本地缓存（按缓存命中率 40% 计算）

            - 接入链路流量强度 = (1.50 $\times$ 0.6) / 1.54 $\approx$ 58% $\rightarrow$ **接入链路排队延迟（毫秒级）**
            - LAN 流量强度 = 1.5 / 1000 = 0.0015 $\rightarrow$ LAN 延迟（毫秒级）

            $\rightarrow$ 缓存未命中延时 = LAN 延迟（毫秒级） + **接入链路排队延迟（毫秒级）** + Internet 延迟（2 s）$\approx$ 2 s

            总延时 = 0.6 $\times$ 缓存未命中延时 + 0.4 $\times$ 从缓存获取对象的延时 $\approx$ 1.2 s

            > 延迟降低的效果显著，且成本显著低于升级接入电路

    - 条件 GET 方法与缓存更新机制

        为了避免缓存返回过期数据，HTTP 引入**条件 GET**实现缓存验证：

        ```mermaid
        sequenceDiagram
            participant C as 客户端/缓存
            participant S as 原始服务器
            
            Note over C,S: 首次请求
            C->>S: GET 请求
            S->>C: 200 OK + 对象数据 + Last-Modified: <date>
            C->>C: 缓存对象与修改日期
            
            Note over C,S: 后续请求（条件GET）
            C->>S: GET + If-Modified-Since: <date>
            
            alt 对象未修改
                S->>C: HTTP/1.0 304 Not Modified<br/>（无对象实体）
                C->>C: 使用本地缓存副本
            else 对象已修改
                S->>C: HTTP/1.0 200 OK + 新对象数据<br/>+ 新的 Last-Modified
                C->>C: 更新缓存
            end
        ```

        1. 客户端在请求中携带 `If-Modified-Since: <日期>` 首部，告诉服务器缓存副本的最后修改时间
        2. 服务器收到请求后，对比对象的实际修改时间：
            - 若对象未修改：返回 `304 Not Modified` 响应，不传输对象数据
            - 若对象已修改：返回 `200 OK` 响应，携带最新对象数据

        - 作用：在保证数据新鲜度的同时，减少不必要的数据传输，节省带宽

- `2.2.6` HTTP/2

    - HTTP/1.1 的瓶颈：队头阻塞 `HOL Blocking`

        HTTP/1.1 引入了流水线 `Pipelining` ，允许在单个 TCP 连接上连续发送多个 GET 请求，但服务器必须**按请求顺序返回响应**

        - 如果第一个请求对象很大（如视频文件），后续的小对象（如 CSS、JS）即使处理完毕，也必须等待大对象传输完成

            $\rightarrow$ 这就是 **Head-of-Line (HOL) Blocking —— 队头阻塞**，服务器按请求顺序响应，大对象会阻塞后续小对象的传输

        - 丢包恢复时，整个 TCP 连接暂停所有对象传输（TCP 的队头阻塞），影响多资源加载效率

    - HTTP/2 的关键优化

        | 特性                         | 说明                                                         |
        | ---------------------------- | ------------------------------------------------------------ |
        | **二进制分帧**               | 将请求/响应拆分为二进制帧（Frame），按优先级交错传输，从根本上缓解 HOL 阻塞 |
        | **多路复用** `Multiplexing`  | 单个 TCP 连接上并行交错传输多个请求/响应，通过 Stream ID 区分 |
        | **头部压缩** `HPACK`         | 使用静态表+动态表压缩冗余头部，显著减少传输量                |
        | **服务器推送** `Server Push` | 服务器可主动推送客户端可能需要的资源（如 CSS、JS）           |
        | **流优先级**                 | 客户端可指定请求优先级，服务器据此调度传输顺序               |

    - **HTTP/2 的局限性**：虽然解决了**应用层**的队头阻塞，但底层仍基于 **TCP**

        TCP 是面向字节流的可靠传输，一旦某个数据包丢失，整个 TCP 连接的所有流都必须等待重传，这就是 **TCP 层队头阻塞**

- `2.2.7` HTTP/3 与 QUIC 协议

    HTTP/2 仍存在 TCP 层的队头阻塞问题（单个丢包会阻塞整个连接），HTTP/3 通过 QUIC 协议解决

    - 传输层改用 UDP，避免 TCP 的连接建立延迟和队头阻塞
    - 每个请求 / 响应独立管理错误和拥塞控制，一个流丢包不影响其他流
    - 内置 TLS 1.3 加密，且连接建立更高效（0-RTT / 1-RTT 握手）

## `2.3` E-mail, SMPT, IMAP

- `2.3.1` 电子邮件系统及其三大组成部分

    一个完整的电子邮件系统由以下三个核心构件组成：

    | 组成部分         | 英文名称              | 核心功能                                                   |
    | ---------------- | --------------------- | ---------------------------------------------------------- |
    | **用户代理**     | User Agent (UA) / MUA | 用户与电子邮件系统的接口，负责撰写、编辑、显示、处理邮件   |
    | **邮件服务器**   | Mail Server           | 存储和管理邮件（邮箱），维护报文队列，向发信人报告传送情况 |
    | **邮件发送协议** | Mail Protocol         | **发送协议**（SMTP）+ **读取协议**（POP3/IMAP/HTTP）       |

    > 邮件服务器在传输过程中同时扮演**客户端**和**服务器**双重角色
    >
    > 当接收邮件时它是服务器；当向其他服务器转发邮件时它是客户端

    1. 用户代理 `User Agent` / 邮件阅读器 `Mail Reader`

        - 输入和输出的邮件**保存在服务器上**（而非仅本地）
        - 提供友好的图形界面（GUI）供用户撰写和阅读
        - 至少具备四大功能：**撰写、显示、处理、通信**

        > 用户代理不直接将邮件发送给收件人，而是先发送到自己的邮件服务器

    2. 邮件服务器 `Mail Server`

        邮件服务器是电子邮件系统的**基础设施**，每个 ISP 都部署有邮件服务器。

        - **邮箱** `Mailbox` ：管理和维护发送给用户的邮件，每个用户有独立的邮箱空间
        - **输出报文队列** `Outgoing Message Queue` ：保持待发送的邮件报文，若发送失败会定时重试
        - **双重角色**：既运行 SMTP 服务器端用于接收邮件，也运行 SMTP 客户端用于发送邮件

    3. 邮件发送协议

        作用范围：用户代理向发送方邮件服务器发送邮件，和发送方邮件服务器向接收方邮件服务器发送邮件

        > 邮件发送协议**不负责**从邮件服务器下载邮件到用户代理，这个功能由邮件访问协议完成

    ```mermaid
    sequenceDiagram
        participant A as Alice的用户代理
        participant S as Alice的邮件服务器
        participant R as Bob的邮件服务器
        participant B as Bob的用户代理
        
        A->>S: 1. 撰写邮件并发送到自己的邮件服务器
        Note over S: 2. 邮件放入输出报文队列
        S->>R: 3. 建立TCP连接，通过SMTP发送邮件
        Note over R: 5. 邮件放入Bob的邮箱
        B->>R: 6. 通过邮件访问协议读取邮件
    ```

    

- `2.3.2` 简单邮件传输协议 SMTP

    简单邮件传输协议 `Simple Mail Transfer Protocol (SMTP)` ，是目前使用最广泛的邮件发送标准

    - SMTP 基于 TCP 协议进行设计，默认端口号为 25（明文 SMTP 默认 25，加密 SMTP 常用 465、587。）

    - 传输模式：直接传输，即从发送方邮件服务器直接连接到接收方邮件服务器，中间不经过第三方服务器

    ```mermaid
    sequenceDiagram
        participant C as SMTP客户端<br/>(发送方服务器)
        participant S as SMTP服务器<br/>(接收方服务器)
        
        C->>S: 1. 建立TCP连接 (端口25)
        Note over C,S: 阶段一：SMTP握手 (Handshaking)
        S->>C: 220 Service ready
        C->>S: HELO/EHLO
        S->>C: 250 Hello
        
        Note over C,S: 阶段二：报文传输 (Transfer)
        C->>S: MAIL FROM:<alice@...>
        S->>C: 250 OK
        C->>S: RCPT TO:<bob@...>
        S->>C: 250 OK
        C->>S: DATA
        S->>C: 354 Start mail input
        C->>S: 报文内容 (以CRLF.CRLF结束)
        S->>C: 250 Message accepted
        
        Note over C,S: 阶段三：关闭 (Closure)
        C->>S: QUIT
        S->>C: 221 Closing connection
        C->>S: 断开TCP连接
    ```

    - SMTP 采用类似 HTTP 的**命令-响应**交互模式：

        | 类型                | 格式              | 说明                                              |
        | ------------------- | ----------------- | ------------------------------------------------- |
        | **命令** `Commands` | ASCII 文本        | 如 `HELO`, `MAIL FROM`, `RCPT TO`, `DATA`, `QUIT` |
        | **响应** `Response` | 状态码 + 状态信息 | 如 `220`, `250`, `354`, `221`                     |

        - **报文必须为 7 位 ASCII 码**：这是 SMTP 的严格限制，也是后来引入 MIME 扩展的根本原因
        - **报文结束标志**：`CRLF.CRLF`（回车换行 `\r\n` . 回车换行 `\r\n` ）

    - SMTP 与 HTTP

        | 对比维度     | SMTP                       | HTTP                         |
        | ------------ | -------------------------- | ---------------------------- |
        | **工作模式** | 客户端**推送** `Push` 数据 | 客户端**拉取 **`Pull` 数据   |
        | **传输方式** | 多个对象可在一个报文中     | 每个对象封装在独立响应报文中 |
        | **交互形式** | 命令 - 响应，状态码        | 命令 - 响应，状态码          |
        | **连接类型** | 持久连接                   | 既可持久也可非持久           |
        | **编码要求** | 7 位 ASCII 码              | 无此限制                     |

- `2.3.3` 邮件报文格式

    SMTP 是**传输/交换** E-mail报文的协议，而报文本身的格式由 **RFC 822** 定义

    ```
    首部 (Header)
    空行 (Blank Line)
    主体 (Body)
    ```

    - 首部 `Header` ：由多行 "关键字：值" 格式的行组成，包含邮件的元数据
        - 常见首部字段：To（收件人）、From（发件人）、Subject（主题）、Date（日期）等
        - **重要区分**：邮件首部的 From/To 字段与 SMTP 命令中的 MAIL FROM/RCPT TO 是完全不同的概念
            - SMTP 命令中的地址用于邮件路由
            - 邮件首部的地址只是显示给用户看的，不影响邮件的实际传输
    - 体部 `Body` ：邮件的实际内容，原始 RFC 822 规定只能是 ASCII 码文本
    - 空行：首部和体部之间用一个空行分隔

- `2.3.4` 多媒体扩展 MIME

    多用途互联网邮件扩展 `Multipurpose Internet Mail Extensions (MIME)` 在不改变SMTP的前提下，通过对邮件主体进行编码和声明，实现了多媒体内容的传输，解决了原始 SMTP 只能传输 ASCII 文本的局限

    - MIME 核心首部行：MIME 通过在报文首部**增加额外的行**来声明内容类型

        | 首部行                      | 作用             | 示例                                            |
        | --------------------------- | ---------------- | ----------------------------------------------- |
        | `MIME-Version: 1.0`         | 声明MIME版本     | `MIME-Version: 1.0`                             |
        | `Content-Type`              | 指定数据媒体类型 | `image/jpeg` , `text/plain` , `application/pdf` |
        | `Content-Transfer-Encoding` | 指定编码方式     | `base64` , `quoted-printable`                   |

    - Base64 编码

        每 3 个字节（24 位）拆分为 4 个 6 位组，每个 6 位组映射为一个 ASCII 字符，将二进制数据转换为 ASCII 字符序列

        - **特点**：编码后数据量增大约33%，但可确保通过 SMTP 传输

- `2.3.5` 邮件访问协议

    SMTP 只负责将邮件从发送方传输到接收方的邮件服务器，如果用户要从自己的邮件服务器下载邮件到本地用户代理，就需要使用**邮件访问协议** `Mail Access Protocol`

    - 邮局访问协议 `Post Office Protocol Version 3 (POP3)`
        - **两个阶段**：
            1. **用户确认阶段**：客户端向服务器发送用户名和密码进行认证
            2. **事务处理阶段**：客户端下载邮件，可选择删除或保留服务器副本
        - **两种配置模式**：
            - **下载并删除**：邮件下载到本地后从服务器删除（节省服务器空间，但无法多设备同步）
            - **下载并保留**：邮件下载后仍保留在服务器（支持多设备访问，但占用空间）
        - **关键特性**：**无状态**——会话结束后不保留用户信息，每次连接需重新认证
    - 因特网邮件访问协议 `Internet Mail Access Protocol (IMAP)`
        - 将每个邮件与服务器上的一个文件夹关联起来
        - 允许用户在服务器上创建、删除、重命名文件夹，组织邮件结构
        - 允许用户只读取邮件的部分内容（如只读取首部），适合低带宽环境
        - **有状态**协议，服务器会保留用户的会话状态（如文件夹结构、邮件已读 / 未读状态等）
        - 支持远程管理邮件，邮件默认保留在服务器上

    | 对比维度   | POP3                     | IMAP                         |
    | ---------- | ------------------------ | ---------------------------- |
    | 状态特性   | 无状态                   | 有状态                       |
    | 邮件存储   | 默认下载后删除           | 默认保留在服务器             |
    | 文件夹管理 | 不支持                   | 支持远程创建 / 管理文件夹    |
    | 部分读取   | 不支持，必须下载整个邮件 | 支持只读取邮件首部或部分内容 |
    | 多设备同步 | 较差（下载删除模式）     | 优秀（所有状态同步到服务器） |
    | 带宽使用   | 较高（必须下载整个邮件） | 较低（可按需下载）           |

    - 基于 Web 的 HTTP 访问
        - 在 SMTP 和 IMAP/POP3 的基础上，提供基于 Web 的用户界面
        - 用户通过浏览器使用 HTTP 协议访问邮件服务器，服务器将邮件以 HTML 页面的形式呈现给用户

- `2.3.6` 完整邮件发送过程示意

    ```mermaid
    sequenceDiagram
        participant A as Alice<br/>用户代理
        participant AS as Alice's<br/>邮件服务器
        participant BS as Bob's<br/>邮件服务器
        participant B as Bob<br/>用户代理
        
        Note over A,B: 发送阶段（使用SMTP）
    ```

## `2.4` 域名解析 DNS

- `2.4.1` DNS 的必要性

    域名解析 `Domain Name System (DNS)` 是互联网的**核心应用层基础设施**，它解决了人类与机器在标识符使用上的根本矛盾

    | 对比维度   | IP 地址                              | 域名                                 |
    | ---------- | ------------------------------------ | ------------------------------------ |
    | 形式       | 32 位二进制（IPv4）或 128 位（IPv6） | 有意义的字符串，如 `sse.sysu.edu.cn` |
    | 人类友好性 | 差，无实际意义，难以记忆             | 好，层次化、有意义                   |
    | 机器处理   | 网络层直接识别                       | 需通过 DNS 转换为 IP                 |

    DNS 的核心使命就是在这两种完全不同的标识符之间建立**高效、可靠、可扩展**的双向映射关系

- `2.4.2` DNS 的设计挑战与目标

    DNS 是世界上最大的分布式数据库系统之一，面临着独特的设计挑战：

    - **规模挑战**：存储约 10 亿条域名记录，每天处理数万亿次查询
    - **性能挑战**：几乎每个互联网请求都依赖 DNS，要求极低的查询延迟
    - **分布式挑战**：全球数百万个组织各自管理自己的域名记录
    - **可靠性挑战**：DNS 故障会导致整个互联网无法正常访问

    - 基于这些挑战，DNS 确立了三大设计目标：
        1. **解决命名问题**：采用层次化命名避免重名，便于人类使用
        2. **解决解析问题**：构建分布式数据库，不同节点维护不同层次的信息
        3. **解决维护问题**：支持域名记录的动态增加、删除和修改

- `2.4.3` DNS 历史：ARPANET  时代的集中式方案

    - 命名方式：无层次的平面命名（如 `host1`、`server`）
    - 维护方式：单个集中式文件 `Hosts.txt` 存储所有主机名 - IP 映射
    - 分发方式：每台主机定时从 SRI 国际的中央站点下载该文件

    - 集中式方案的致命缺陷

        - **单点故障**：中央服务器故障会导致整个网络无法解析域名

        - **性能瓶颈**：主机数量增多时，中央服务器无法承受查询压力

        - **命名冲突**：平面命名容易产生重名，无法扩展

        - **维护困难**：文件的更新、发布和分发变得极其复杂

- `2.4.4` DNS 核心架构：分层分布式数据库

    DNS 采用**树状的分层分布式架构**，将域名空间划分为不同层次，由不同的服务器负责管理

    ```mermaid
    graph LR
        A[Root DNS Servers<br/>根域名服务器] --> B[TLD DNS Servers<br/>顶级域服务器<br/>.com / .org / .edu / .cn]
        B --> C[Authoritative DNS Servers<br/>权威域名服务器<br/>yahoo.com / amazon.com / nyu.edu]
        C --> D[Local DNS Server<br/>本地DNS服务器<br/>ISP提供]
    ```

    - 域名解析流程示例（以 `www.amazon.com` 为例）

        ```mermaid
        sequenceDiagram
            participant C as Client
            participant L as Local DNS
            participant R as Root DNS
            participant T as .com TLD
            participant A as amazon.com<br/>Authoritative
            
            C->>L: 查询 www.amazon.com
            L->>R: 请求解析
            R-->>L: 返回 .com TLD服务器地址
            L->>T: 请求解析 amazon.com
            T-->>L: 返回 amazon.com权威服务器地址
            L->>A: 请求解析 www.amazon.com
            A-->>L: 返回 IP地址
            L-->>C: 返回最终结果
        ```

        1. 客户端向本地 DNS 服务器发送查询请求
        2. 本地 DNS 服务器向**根域名服务器**查询，获取`.com`顶级域名服务器的地址
        3. 本地 DNS 服务器向`.com`顶级域名服务器查询，获取`amazon.com`权威域名服务器的地址
        4. 本地 DNS 服务器向`amazon.com`权威域名服务器查询，获取`www.amazon.com`的 IP 地址
        5. 本地 DNS 服务器将 IP 地址返回给客户端并缓存

        > DNS 解析是一个**逐层委托**的过程，每一层服务器只知道自己下一层的信息，无需掌握全局。

- `2.4.5` DNS 命名空间

    - 核心概念区分

        | 概念                 | 定义                           | 示例                                      |
        | -------------------- | ------------------------------ | ----------------------------------------- |
        | **域** `Domain`      | 命名空间的一个分支，可包含子域 | `.com`、`.edu.cn`                         |
        | **子域** `Subdomain` | 从属于父域的域                 | `sse.sysu.edu.cn` 是 `sysu.edu.cn` 的子域 |
        | **主机** `Host`      | 域中的具体设备（服务器）       | `sse.sysu.edu.cn` 可对应一台具体服务器    |

        > 一个**域**可以拆分为多个 DNS 区域交由不同团队管理（区域的划分由区域管理者自行决定，通常与组织边界一致），比如 `sysu.edu.cn` 作为独立区域，由中山大学运维团队负责解析；上级 `edu.cn` 区域则由教育网机构管理，二者边界独立、互不重叠

    - 域名的层次结构：域名采用**从右到左**的层次化结构，用点 `.` 分隔不同级别，例如：`www.sysu.edu.cn`

        - `.cn` ：国家顶级域名
        - `.edu.cn` ：二级域名（中国教育机构）
        - `sysu.edu.cn` ：三级域名（中山大学）
        - `sse.sysu.edu.cn` ：四级域名（中山大学软件学院）
        - `www.sse.sysu.edu.cn` ：主机名

    - 域名管理原则

        1. **授权管理**：一个域管理其下的子域，创建新域需获得父域同意
            - 例：`.jp` 划分为 `ac.jp`（学术）、`co.jp`（商业）
            - 例：`.cn` 划分为 `edu.cn`、`com.cn` 等
        2. **逻辑独立性**：域的划分是**逻辑的**，与物理网络无关
            - 一个域的主机可以分布在不同物理网络
            - 一个物理网络的主机可以属于不同域

- `2.4.6` 域名的分布式解析

    - 区域 `Zone` 的含义

        - **定义**：DNS 命名空间被划分为**互不相交**的管理单元，每个区域是域名树的一部分
        - **关键特性**：区域的划分由**区域管理者自主决定**，可根据行政、地理或组织需求划分
        - **与"域"的区别**：域是逻辑概念，区域是管理边界；一个域可包含多个区域，一个区域也可跨多个子域

    - 域名服务器的分类

        | 服务器类型     | 功能                                                         | 管理机构                |
        | -------------- | ------------------------------------------------------------ | ----------------------- |
        | 根域名服务器   | 管理所有顶级域名，返回顶级域名服务器的地址                   | ICANN                   |
        | 顶级域名服务器 | 管理一个顶级域名，返回权威域名服务器的地址                   | 各顶级域名注册管理机构  |
        | 权威域名服务器 | 管理一个特定区域，提供该区域内域名记录的权威答案             | 组织或第三方 DNS 服务商 |
        | 本地域名服务器 | 用户访问 DNS 的第一入口<br/>缓存查询结果，代表用户进行递归查询 | ISP 或公共 DNS 服务商   |

        - 根域名服务器 `Root DNS Server` 

            - 核心职责
                - 负责**顶级域** `TLD` 的委托：不直接解析具体域名，只告知"哪个 TLD 服务器负责 .com/.org 等"
                - 是**全球 DNS 解析的起点**
            - 管理架构
                - **管理机构**：互联网名称与数字地址分配机构 `ICANN` 通过 IANA 职能管理根 DNS 域
                - **运营现状**：
                    - **13 个逻辑根服务器**（命名从 A 到 M：a.root-servers.net ~ m.root-servers.net）
                    - **数百个物理服务器实例**：通过任播 `Anycast` 技术在全球部署，美国约有 200 个物理节点
                    - 全球各大洲均有部署，确保高可用性

        - 顶级域名服务器 `Top-Level Domain (TLD) DNS Server`

            - **通用顶级域（gTLD）**：`.com`、`.org`、`.net`、`.edu`、`.aero`、`.jobs`、`.museums` 等
            - **国家代码顶级域（ccTLD）**：`.cn`（中国）、`.uk`（英国）、`.fr`（法国）、`.ca`（加拿大）、`.jp`（日本）等
            - **运营实例**：
                - Verisign Global Registry Services 维护 `.com` TLD 服务器
                - Educause 维护 `.edu` TLD 服务器

        - 权威域名服务器 `Authoritative DNS Server` 

            组织机构自己的DNS服务器，为组织内各主机提供 “**权威**域名-IP” 映射信息

            - **维护方式**：由组织自行维护，或委托第三方（如DNS服务商、云厂商）维护
            - **冗余设计**：通常配置主（Master）服务器和从（Slave）服务器，通过区域传输（AXFR）同步数据

        - 本地域名服务器 `Local DNS Server` 

            - **严格来说，本地 DNS 服务器不属于 DNS 层次结构**，它是客户端与 DNS 层次结构之间的**代理和缓存层**，通常由 ISP部署，也可由企业/组织自行搭建或使用公共 DNS
            - 本地 DNS 工作流程
                1. 主机发起DNS查询时，首先发送至本地DNS服务器
                2. 本地DNS服务器检查**本地缓存**：
                    - 若命中且未过期：直接返回缓存结果（**非权威应答**，可能过时）
                    - 若未命中：作为**递归解析器**，向 DNS 层次结构转发请求并返回最终结果

    - DNS 解析过程

        1. 本地客户端与本地 DNS 服务器交互

            - 本地解析器通常是操作系统内置的 DNS 客户端，作为客户向本地 DNS 服务器发出查询报文
            - 查询报文默认使用 UDP 协议，端口号 53；当响应报文超过 512 字节时，会使用 TCP 协议传输

        2. 本地 DNS 服务器的解析

            - **本地区域内解析**：查询的域名属本服务器负责区域（如中山大学 DNS 服务器解析 sse.sysu.edu.cn），直接返回结果

            - **缓存解析**：查询结果在本地缓存中且未过期，直接返回缓存的记录

            - **远程解析**：以上两种情况都不满足时，向其他 DNS 服务器发起查询（递归或迭代方式）

                - **递归查询** `Recursive Query` ：本地 DNS 服务器代表客户端进行完整的查询过程，最终将 IP 地址返回给客户端

                    - **特点**：解析负担完全集中在本地 DNS 服务器上，会导致根服务器负担过重
                    - 流程示例：

                    ```mermaid
                    sequenceDiagram
                        participant Host as 客户端主机
                        participant LocalDNS as 本地DNS服务器
                        participant RootDNS as 根DNS服务器
                        participant TLDDNS as .edu 顶级域DNS
                        participant AuthDNS as 目标权威DNS
                    
                        note over Host,LocalDNS: 客户端→本地DNS<br/>递归请求（要求返回最终IP）
                        Host->>LocalDNS: 1. 查询 gaia.cs.umass.edu IP
                        note over LocalDNS,RootDNS: 本地DNS无结果<br/>【主动代为查询】
                        LocalDNS->>RootDNS: 2. 递归查询（继续找答案）
                        note over RootDNS,TLDDNS: 根服务器无结果<br/>【继续代为查询】
                        RootDNS->>TLDDNS: 3. 递归查询
                        note over TLDDNS,AuthDNS: 顶级域无结果<br/>【继续代为查询】
                        TLDDNS->>AuthDNS: 4. 递归查询
                        AuthDNS-->>TLDDNS: 5. 返回【最终IP地址】
                        TLDDNS-->>RootDNS: 6. 转发最终IP
                        RootDNS-->>LocalDNS: 7. 转发最终IP
                        LocalDNS-->>Host: 8. 交付最终IP，查询结束
                    ```

                    1. 客户端只发 **1 次请求**，之后全程等待，不再主动发包
                    2. 本地 DNS 查不到结果，**没有把根服务器地址发给客户端**，而是自己主动向根服务器发起查询
                    3. 根服务器、顶级域服务器同理：查不到最终 IP，**不会返回 “下一跳地址”**，而是继续向下一级服务器**代为发起查询**
                    4. 权威服务器拿到最终 IP 后，结果**逐层向上转发**，整条链路是**连续的接力代查**

                    > **中间所有 DNS 服务器都在 “帮别人干活”**，负载集中在整条链路的服务器上

                - **迭代查询** `Iterated Query` ：被查询的服务器如果不知道答案，会返回下一个应该查询的服务器地址，由本地 DNS 服务器继续查询

                    - **特点**：解析负担分散在各级 DNS 服务器上，根服务器负担较轻
                    - 流程示例：

                    ```mermaid
                    sequenceDiagram
                        participant Host as 客户端主机
                        participant LocalDNS as 本地DNS服务器
                        participant RootDNS as 根DNS服务器
                        participant TLDDNS as .edu 顶级域DNS
                        participant AuthDNS as 目标权威DNS
                    
                        note over Host,LocalDNS: 客户端→本地DNS<br/>递归请求（正常固定搭配）
                        Host->>LocalDNS: 1. 查询 gaia.cs.umass.edu IP
                        note over LocalDNS,RootDNS: 本地DNS发起【迭代查询】
                        LocalDNS->>RootDNS: 2. 发起查询
                        note over RootDNS,LocalDNS: 根服务器：无IP<br/>【返回下一跳地址：.edu服务器】
                        RootDNS-->>LocalDNS: 3. 回复：请查询 .edu 服务器（本次会话结束）
                        note over LocalDNS,TLDDNS: 本地DNS拿到地址，【主动发起新一轮查询】
                        LocalDNS->>TLDDNS: 4. 第二次独立查询
                        note over TLDDNS,LocalDNS: 顶级域：无IP<br/>【返回下一跳地址：umass.edu权威服务器】
                        TLDDNS-->>LocalDNS: 5. 回复：请查询权威服务器（本次会话结束）
                        note over LocalDNS,AuthDNS: 本地DNS再次【主动发起新一轮查询】
                        LocalDNS->>AuthDNS: 6. 第三次独立查询
                        AuthDNS-->>LocalDNS: 7. 返回【最终IP地址】
                        LocalDNS-->>Host: 8. 交付最终IP，查询结束
                    ```

                    1. 客户端依旧只发 1 次请求（客户端→本地 DNS 永远是递归，行业惯例）
                    2. 本地 DNS 向**根服务器发起迭代查询**
                    3. 根服务器查不到 IP，**直接返回 “下一级服务器地址”**，本次和本地 DNS 的对话**彻底终止**
                    4. **本地 DNS 作为请求方，必须自己拿着新地址，主动发起第 2 轮、第 3 轮全新查询**
                    5. 每一级上级 DNS（根、顶级域）都只做一件事：**返回下一跳地址，不代为查询**
                    
                    > **只有本地 DNS 在主动干活**，上级 DNS 只负责 “指路”，不承接完整查询任务

                | 交互环节           | 递归查询（本地 DNS $\leftrightarrow$ 根服务器） | 迭代查询（本地 DNS $\leftrightarrow$ 根服务器） |
                | ------------------ | ----------------------------------------------- | ----------------------------------------------- |
                | 根服务器收到请求后 | 不知道最终 IP，**继续向下代为查询**             | 不知道最终 IP，**仅返回下一跳服务器地址**       |
                | 根服务器返回内容   | 最终 IP 地址（全程查完再回包）                  | 下一级 DNS 服务器域名 / IP（只指路）            |
                | 本次会话状态       | 会话保持，链路连续接力                          | 会话立即结束，等待请求方下次新连接              |
                | 谁发起下一次查询   | 根服务器主动发起（代为查询）                    | 本地 DNS 主动发起（自主查询）                   |

- `2.4.7` DNS 缓存

    一旦本地 DNS 服务器获得某个域名映射，就会将其**缓存**起来，以加速后续查询响应，显著提高了 DNS 解析的响应速度，减少了网络上的 DNS 查询流量

    - 关键特性
        - **TTL 过期**：缓存条目在 TTL (Time-To-Live) 到期后自动失效，需重新查询
        - **根 / TLD 服务器缓存**：通常缓存在本地域名服务器中，无需频繁访问上层
        - **尽力而为映射**：DNS 缓存可能返回过期信息，属于尽力而为 "Best-Effort" 机制，不能保证实时性
        - **更新延迟**：若目标主机 IP 已更改，可能需等待所有 TTL 过期后才能全局生效

    > 较短的 TTL 可以加快 DNS 记录更新的速度，但会增加 DNS 服务器的负载

- `2.4.8` DNS 资源记录

    DNS 本质上是一个存储资源记录 `Resource Record (RR)` 的分布式数据库，RR 是其中最基本的信息单元

    - 基本格式：`(Name, Value, Type, TTL)` 

        | 字段      | 含义                                      |
        | --------- | ----------------------------------------- |
        | **Name**  | 域名（Domain name）                       |
        | **Value** | 值（可以是 IP 地址、域名或 ASCII 字符串） |
        | **Type**  | 记录类型（决定 Name 与 Value 的语义关系） |
        | **TTL**   | 生存时间（秒），缓存有效期                |

        | Type 字段 | Name 字段                 | Value 字段                          | 作用说明                                                     |
        | --------- | ------------------------- | ----------------------------------- | ------------------------------------------------------------ |
        | **A**     | 主机名<br/>如 `www`       | **IPv4 地址**                       | 将主机名映射到 IPv4 地址，最基础记录                         |
        | **NS**    | 域名<br/>如 `foo.com`     | **权威 DNS 服务器域名**             | 指定该域名的权威服务器，用于委派                             |
        | **CNAME** | 主机别名<br/>`Alias name` | **规范主机名**<br/>`Canonical name` | 创建别名，如 `www.ibm.com` 是<br/> `servereast.backup2.ibm.com` 的别名 |
        | **MX**    | 域名                      | **邮件服务器域名**                  | 指定接收该域名邮件的服务器，Value 含优先级                   |
        | AAAA      | 主机名<br/>如 `www`       | **IPv6 地址**                       |                                                              |

    - 实际示例解析

        ```cmd
        # ping www.bilibili.com
        Pinging a.w.bilicdn1.com (157.148.134.12): 56 data bytes
        64 bytes from 157.148.134.12: icmp_seq=0 ttl=49 time=14.155 ms
        ```

        - 为什么 `ping www.bilibili.com` 显示的是 `a.w.bilibilicdn1.com` ？
        - 因为 `www.bilibili.com` 是一个**CNAME 记录**，指向 `a.w.bilibilicdn1.com`
        - 本地 DNS 服务器先查询到 `www.bilibili.com` 的 CNAME 记录，然后再查询 `a.w.bilibilicdn1.com` 的 A 记录，最终得到 IP 地址

- `2.4.9` DNS 协议与报文格式

    DNS 查询和响应使用**相同的报文格式**，通常通过 **UDP 端口 53 **传输，报文超过 512 字节时使用 TCP 传输

    - 报文整体结构

        ```
        +---------------------+
        | 报文头部 (12字节)  |
        +---------------------+
        | 问题部分 (可变长度) |（包含要查询的域名和查询类型（Name, Type））
        +---------------------+
        | 回答部分 (可变长度) |（包含查询结果的资源记录（RR的信息））
        +---------------------+
        | 权威部分 (可变长度) |（包含权威 DNS 服务器的 NS 记录）
        +---------------------+
        | 附加部分 (可变长度) |（包含一些附加的有用信息，如权威服务器的 A 记录）
        +---------------------+
        ```

    - 报文头部结构

        | 字段             | 长度  | 含义                                                   |
        | ---------------- | ----- | ------------------------------------------------------ |
        | **标识符 (ID)**  | 16 位 | 用于匹配查询和响应报文，同一个查询和响应的 ID 必须相同 |
        | **标志 (flags)** | 16 位 | 包含多个子标志位，详见下表                             |
        | 问题数 (QDCOUNT) | 16 位 | 问题部分的记录数                                       |
        | 回答数 (ANCOUNT) | 16 位 | 回答部分的记录数                                       |
        | 权威数 (NSCOUNT) | 16 位 | 权威部分的记录数                                       |
        | 附加数 (ARCOUNT) | 16 位 | 附加部分的记录数                                       |

        | 标志位    | 全称                 | 含义                                             |
        | --------- | -------------------- | ------------------------------------------------ |
        | **QR**    | Query/Response       | 0 = 查询，1 = 响应                               |
        | **RD**    | Recursion Desired    | 客户端期望递归查询（1 = 是）                     |
        | **RA**    | Recursion Available  | 服务器支持递归查询（1 = 支持）                   |
        | **AA**    | Authoritative Answer | 响应来自权威服务器（1 = 是）                     |
        | **TC**    | Truncated            | 报文被截断（UDP超限时使用）                      |
        | **RCODE** | Response Code        | 响应状态：0 = 无错误，3 = 域名不存在（NXDOMAIN） |

- `2.4.10` DNS 域名记录的插入

    - 在上级域 DNS 服务器添加记录

        在 DNS 注册商（如阿里云、腾讯云）处注册域名时，需要提供你的权威 DNS 服务器信息，注册商会在顶级域 DNS 服务器中添加两条记录：

        1. NS 记录：指向你的子域的权威 DNS 服务器域名
        2. A 记录：你的权威 DNS 服务器域名对应的 IP 地址

    - 在子域权威服务器添加记录

        在你自己的权威 DNS 服务器上，添加该域下所有需要的资源记录：

        - A 记录：将主机名映射到 IP 地址
        - MX 记录：指定邮件服务器
        - CNAME 记录：设置主机别名

- `2.4.11` DNS 安全问题

    DNS 协议在设计之初没有考虑安全性，存在多种安全漏洞。

    1. DDoS 攻击

        - **流量轰炸根服务器**：试图发送大量查询请求使根服务器过载，但由于缓存的存在，实际影响有限

        - **流量轰炸顶级域服务器**：比轰炸根服务器更危险，但同样由于缓存，实际影响有限

        - **反射放大攻击**：最常见的 DNS DDoS 攻击方式
            - 原理：DNS 响应报文通常比请求报文大得多（放大倍数可达 10-100 倍）
            - 攻击者伪造目标 IP 发送大量 DNS 查询请求，所有 DNS 服务器的响应都会发送到目标主机，造成目标主机带宽耗尽

    2. 欺骗攻击 `Spoofing` 与缓存中毒

        - **DNS 欺骗攻击**：攻击者拦截 DNS 查询请求，返回虚假的响应结果，将用户引导到恶意网站

        - **DNS 缓存中毒**：攻击者发送伪造的响应给 DNS 服务器，使服务器缓存虚假的记录

        - **危害**：一旦 DNS 服务器缓存了虚假记录，所有查询该域名的用户都会得到虚假的 IP 地址，直到缓存过期

## `2.5` P2P 应用

- `2.5.1` 纯 P2P 架构

    纯 P2P 架构具备三大核心特征，区别于传统的 Client-Server 架构

    - 核心特点
        - **无中心服务器**：没有（或极少）一直运行的中心服务器，避免了单点故障和性能瓶颈
        - **对等直接通信**：任意端系统（节点）都可以直接建立连接并传输数据，无需经过中心服务器转发
        - **双重身份**：每个节点 `Peer` 同时扮演客户端和服务器的角色，向其他节点请求服务时是客户端，向其他节点提供服务时是服务器
        - **自扩展性** `Self-Scalability` ：新节点的加入不仅带来新的业务需求，同时也贡献了新的上传带宽和存储资源，系统整体性能随节点数增加而提升
    - 主要缺点
        - **管理复杂**：节点通常间歇上网，且每次上网的 IP 地址都可能变化，导致节点发现、状态维护和管理难度大
        - **安全性较低**：缺乏中心服务器的统一管控，容易出现恶意节点传播病毒、伪造文件、窃取数据等问题
        - **服务质量不稳定**：节点的上传 / 下载带宽差异大，且可能随时离线，导致数据传输速度和可靠性难以保证
    - 典型应用
        - **文件分发**：BitTorrent（经典 P2P 文件共享协议）
        - **流媒体加速**：爱奇艺、优酷、腾讯视频等平台内嵌的 P2P 加速模块，利用用户带宽分担服务器压力
        - **下载工具**：迅雷（构建了全球最大的去中心化存储与传输网络）
        - **区块链**：比特币、以太坊等区块链网络本质上也是纯 P2P 架构

- `2.5.2` 文件分发：C/S Vs. P2P

    > 假设需要从一台服务器向N个节点分发一个大小为F的文件，网络带宽充足（网络本身不会成为瓶颈），定义以下参数
    >
    > - $u_s$：服务器的上传带宽
    > - $d_i$：第i个客户端的下载带宽，$d_{min} = \min\{d_1, d_2, ..., d_N\}$（客户端最小下载带宽）
    > - $u_i$：第i个客户端的上传带宽，$\sum u_i$：所有客户端的总上传带宽

    1. C/S 模式分发时间

        在 C/S 模式下，所有文件数据都必须由服务器发送给客户端，客户端之间不能互相传输数据

        - **服务器端限制**：服务器需要向 N 个客户端各发送一个完整的文件拷贝，总上传数据量为 $N \times F$，所需时间为$\frac{NF}{u_s}$
        - **客户端端限制**：每个客户端必须下载一个完整的文件拷贝，下载速度最慢的客户端决定了客户端端的最大耗时，即$\frac{F}{d_{min}}$

        $\rightarrow$ **C/S模式最小分发时间公式**：$D_{C-S}\geq\max\{\frac{NF}{u_s}, \frac{F}{d_{min}}\}$

        > C/S模式的最小分发时间随节点数 N **线性增长**
        >
        > 当 N 很大时，服务器上传带宽会成为系统的绝对瓶颈，分发时间会变得非常长

    2. P2P 模式分发时间

        在 P2P 模式下，不仅服务器可以上传文件，已经下载了部分或全部文件的客户端也可以向其他客户端上传文件。

        - **服务器端限制**：服务器最少需要上传一个完整的文件拷贝（否则系统中没有任何节点拥有完整文件），所需时间为 $\frac{F}{u_s}$
        - **客户端端限制**：与 C/S 模式相同，最慢客户端的下载时间为 $\frac{F}{d_{min}}$
        - **全局上传带宽限制**：所有 N 个客户端总共需要下载 $N \times F$ 的数据量，系统总上传带宽为 $u_s + \sum u_i$，因此全局限制时间为 $\frac{NF}{u_s + \sum u_i}$

        $\rightarrow$ **P2P 模式最小分发时间公式**：$D_{\text{P2P}}\geq\max\{\frac{F}{u_s},\frac{F}{d_{min}},\frac{NF}{u_s + \sum u_i}\}$

        > P2P 模式的最小分发时间增长远慢于 C/S 模式。
        >
        > 当 N 很大时，分子 $N\times F$ 随 N 线性增长，但分母 $u_s + \sum u_i$ 也随 N 线性增长，因此 $\frac{NF}{u_s + \sum u_i}$ 会**趋近于一个常数**，这说明系统具有极佳的自扩展性

        - `BitTorrent` 协议

            BitTorrent 是目前最流行的 P2P 文件分发协议，其核心思想是将大文件分割成小块，让节点之间互相交换这些小块，从而实现高效的大规模文件分发

            - 核心概念

                - **Torrent 文件**：一个小的元数据文件，包含待分发文件的信息（文件名、大小、分块信息）以及 Tracker 服务器的地址
                - **Tracker**：一个中心服务器，负责跟踪当前参与该 Torrent 的所有节点的 IP 地址和端口号
                - **Swarm（洪流）**：所有参与同一个 Torrent 文件分发的节点组成的群体
                - **Peer**：参与文件分发的节点，可以同时下载和上传文件块
                - **Seeder（种子）**：已经拥有完整文件的节点，只上传不下载
                - **Leecher（下载者）**：还没有拥有完整文件的节点，同时下载和上传

            - 文件分块与交换机制

                - **文件分块**：待分发的大文件被分割成多个固定大小的块（通常为 256KB~4MB），每个块都有一个唯一的哈希值用于校验完整性
                - **并行下载**：客户端同时从多个 Peer 下载不同的文件块，大大提高了下载速度
                - **激励机制**：采用以牙还牙 `Tit-for-Tat` 机制
                    - 每个节点同时向多个邻居上传，但**优先向"给自己传数据最快"的 4 个邻居**发送块（称为"疏通" `Unchoked` ）
                    - 其他 Peer 被"阻塞" `Choked` ，暂时不接收来自该节点的数据
                    - **乐观疏通** `Optimistic Unchoking` ：每 30 秒随机选择一个新 Peer （无条件）进行上传，给予其加入 Top-4 的机会
                    - **目的**：激励对等节点贡献上传带宽，防止"搭便车" `Free-Riding`

            - 节点加入流程

                ```mermaid
                sequenceDiagram
                    participant P as 新Peer (Alice)
                    participant T as Tracker
                    participant O as 其他Peers
                    
                    P->>T: 1. 注册加入Torrent
                    T-->>P: 2. 返回Peer子集列表
                    P->>O: 3. 尝试建立TCP连接<br/>（选择"邻居"）
                    loop 周期性交互
                        P->>O: 4. 请求对方拥有的块列表
                        O-->>P: 5. 返回bitfield（块拥有情况）
                        P->>O: 6. 按Rarest First请求稀缺块
                        O-->>P: 7. 传输文件块
                        P->>O: 8. 向邻居上传已拥有的块<br/>（Tit-for-Tat）
                    end
                ```

                1. 用户下载并打开一个 Torrent 文件
                2. 客户端连接到 Torrent 文件中指定的 Tracker 服务器
                3. Tracker 服务器向客户端返回当前参与该 Torrent 的 Peer 列表
                4. 客户端与列表中的 Peer 建立 TCP 连接
                5. 客户端开始从多个 Peer 同时下载不同的文件块
                6. 当客户端下载完所有块并校验通过后，就成为一个 Seeder，继续为其他节点提供上传服务

## `2.6` 视频流和内容分发网

- `2.6.1` 多媒体应用现状

    | 应用类型                  | 代表平台                                   | 核心特征                     |
    | ------------------------- | ------------------------------------------ | ---------------------------- |
    | **VOD** (Video on Demand) | 腾讯视频、爱奇艺、B站、优酷、Netflix、Hulu | 用户按需点播，非实时交互     |
    | **短视频**                | UGC、YouTube、抖音、快手                   | 时长短、传播快、用户生成内容 |
    | **直播**                  | 抖音、快手                                 | 实时传输、低延迟要求         |
    | **即时通信**              | QQ、微信、钉钉、飞书                       | 实时音视频通话、即时消息     |

    - 流量特征：视频流量占据互联网大部分带宽

        **具体数据**：Netflix、YouTube、Amazon Prime 在 2020 年占据了住宅 ISP 流量的 **80%**

        > 随着高清/超高清视频普及，视频流量占比持续攀升

    - 核心挑战

        1. **规模性挑战**：如何同时服务海量用户（亿级日活）和存储分发百万级视频内容。
        2. **异构性挑战**：不同用户的网络环境差异巨大
            - 接入方式：有线宽带 vs 移动网络
            - 带宽条件：千兆光纤 vs 4G/5G 受限带宽
            - 设备能力：高性能电脑 vs 低端手机

        $\rightarrow$ 采用**分布式的应用层基础设施**，即 CDN+DASH 技术组合，将计算和存储资源下沉到离用户更近的位置。

- `2.6.2` 流媒体传输

    - **视频 = 固定速度显示的图像序列**

        - 例如：24 images/sec（每秒24帧，电影标准）
        - 网络视频特点：像素的阵列，每个像素由若干比特表示

    - 视频编码原理

        | 冗余类型                   | 定义                     | 压缩原理                         |
        | -------------------------- | ------------------------ | -------------------------------- |
        | **空间冗余**（图像内）     | 单帧图像内部相邻像素相似 | 利用同一帧内像素的空间相关性压缩 |
        | **时间冗余**（相邻图像间） | 相邻帧画面内容变化小     | 只存储帧间差异，而非完整帧       |

        - **空间冗余（图像内）**：同一帧图像中相邻像素往往具有相似的颜色值。例如一张纯色背景的图片，不需要发送每个像素的完整信息，只需发送 "颜色值 + 重复个数"。
        - **时间冗余（图像间）**：相邻两帧图像的大部分内容是相同的。例如一个跑步的人，背景基本不变，只需发送第 1 帧的全部信息和后续帧与前一帧的差异部分。

    - 流媒体传输的核心挑战

        - 连续播放约束 `Continuous Playout Constraint`
            - **定义**：客户端视频播放时，播放时间必须匹配原始时间
            - **核心问题**：网络时延是可变的（抖动），导致数据到达不均匀
            - **解决方案**：客户端设置**播放缓冲区**，提前缓存数据以平滑抖动
        - 更复杂的用户需求：现代流媒体需支持：快进、快退、倍速播放、频跳转（seek）、自适应码率切换

- `2.6.3` 流式多媒体核心技术：DASH

    基于 HTTP 的动态自适应流 `Dynamic Adaptive Streaming over HTTP (DASH)` 是目前主流的流媒体传输协议。

    - **服务器端工作机制**

        - 将完整的视频文件分割成多个小的视频块（通常 2-10 秒一个块）
        - 每个视频块独立编码为 8-10 种不同的码率版本（从低清到 4K / 8K）
        - 所有码率版本的视频块都复制到各个 CDN 节点存储
        - 生成一个 **Manifest 文件（告示文件）**，包含所有视频块的 URL 和对应的码率信息

    - **客户端工作机制**

        - 首先向服务器请求并下载 Manifest 文件
        - 解析 Manifest 文件，了解所有可用的视频块和码率选项
        - 在一个时刻只请求一个视频块，通过 HTTP 头部的 `Range` 字段指定字节范围
        - **自适应码率选择**：
            - 如果当前带宽足够，选择最大码率的视频块以获得最佳画质
            - 如果带宽下降，自动切换到较低码率的视频块以避免卡顿
            - 在播放过程中可以随时无缝切换不同码率的块

    - 客户端的自适应决策

        客户端需要自适应决定三个关键问题：

        | 决策维度         | 具体内容                                             | 目标                     |
        | ---------------- | ---------------------------------------------------- | ------------------------ |
        | **何时请求**     | 不至于缓存挨饿或溢出                                 | 维持缓冲区在合理水位     |
        | **请求什么码率** | 带宽够用时请求高质量                                 | 最大化用户体验质量       |
        | **从哪请求**     | 向离自己近的服务器发送 URL，或向高可用带宽服务器请求 | 最小化延迟，最大化吞吐量 |

    > **Streaming Video = Encoding + DASH + Playout Buffering**
    >
    > 完整的流媒体体验由视频编码、自适应传输和客户端播放缓冲三个部分共同构成。

- `2.6.4` 内容分发网络

    内容分发网络 `Content Distribution Networks (CND)` 是解决大规模视频分发问题的核心基础设施，通过分布在不同地理位置的服务器群组，通过将内容缓存到靠近用户的位置来加速内容交付

    | 核心组件       | 功能           | 说明                                   |
    | -------------- | -------------- | -------------------------------------- |
    | **源服务器**   | 存储原始内容   | 内容的最终来源，负责内容更新           |
    | **边缘服务器** | 缓存并分发内容 | 部署在全球各地的 PoP（入网点）         |
    | **DNS 服务器** | 智能路由调度   | 基于用户地理位置、网络状况选择最优节点 |
    | **负载均衡器** | 流量分配       | 防止单点过载，确保高可用性             |

    - **传统超级服务器方案的缺陷**

        - 服务器到客户端的网络路径长，跳数多，容易出现瓶颈链路**导致卡顿**
        - 违反 "二八定律"：80% 的用户会访问 20% 的热门内容，超级服务器会导致大量重复传输
        - 效率低：付费高、带宽浪费、用户体验差，容易造成周边网络拥塞
        - 存在单点故障风险，一旦中心服务器宕机，所有用户都无法访问

    - **通过CDN部署缓存节点**

        - 全网部署缓存节点，存储服务内容，就近为用户提供服务
        - **深入部署** `Enter Deep`：将 CDN 服务器深入到许多接入网，更接近用户，数量多，离用户近
        - **邀请做客** `Bring Home`：部署在少数（10个左右）关键位置，如服务器簇安装于交换点 IXP，采用租用线路将服务器簇连接起来

    - 工作流程

        ```mermaid
        sequenceDiagram
            participant U as 用户
            participant D as 本地DNS
            participant C as CDN智能DNS
            participant E as 边缘节点
            participant O as 源服务器
            
            U->>D: 1. 请求视频URL
            D->>C: 2. CNAME解析到CDN
            C->>C: 3. 智能调度<br/>（地理位置/负载/网络状况）
            C->>U: 4. 返回最优边缘节点IP
            U->>E: 5. 请求视频内容
            alt 缓存命中
                E->>U: 6a. 直接返回缓存内容
            else 缓存未命中
                E->>O: 6b. 回源请求
                O->>E: 7. 返回原始内容
                E->>E: 8. 本地缓存
                E->>U: 9. 返回内容
            end
        ```

## `2.7` UDP TCP 套接字编程
