# 第 3 章 传输层

## `3.1` 概述和传输层服务

- `3.1.1` 传输层服务与协议

    传输层的核心职责是：**为运行在不同主机上的应用进程 `Process` 提供逻辑通信 `Logical Communication`**

    - **逻辑通信**：指应用进程之间看似直接相连，实际上数据经过了复杂的网络传输，传输层屏蔽了下层网络的细节

        - **发送方**：将应用层的报文 `Message` 分成**报文段 `Segment`**，添加头部信息后传递给网络层
        - **接收方**：从网络层接收报文段，重组为报文后传递给应用层

    - **运行位置**：传输层协议**运行在端系统**中，而非网络核心设备（路由器、交换机）上

    - Internet 协议栈提供两个主要传输层协议：

        - 传输控制协议 `Transmission Control Protocol (TCP)`：可靠、保序传输
        - 用户数据报协议 `User Datagram Protocol (UDP)`：不可靠、不保序传输

        | 特性              | TCP（传输控制协议）                        | UDP（用户数据报协议）                  |
        | ----------------- | ------------------------------------------ | -------------------------------------- |
        | 可靠性            | 可靠传输，保证数据无丢失、无重复、按序到达 | 不可靠传输，不保证数据到达，不保证顺序 |
        | 连接性            | 面向连接，“三次握手、四次挥手”             | 无连接，通信前不建立连接，直接发送数据 |
        | 流量控制          | 有，防止发送方发送过快导致接收方缓冲区溢出 | 无                                     |
        | 拥塞控制          | 有，防止网络出现拥塞                       | 无                                     |
        | 多路复用 / 解复用 | 支持                                       | 支持                                   |
        | 数据边界          | 字节流（无消息边界）                       | 数据报（有消息边界）                   |
        | 头部开销          | 20 字节                                    | 8 字节                                 |
        | 典型应用          | HTTP、FTP、SMTP、SSH                       | DNS、VoIP、视频直播、在线游戏          |
        | 延时保证          | 不支持                                     | 不支持                                 |
        | 带宽保证          | 不支持                                     | 不支持                                 |

- `3.1.2` 传输层与网络层

    | 层次       | 通信对象               | 类比                         |
    | ---------- | ---------------------- | ---------------------------- |
    | **网络层** | **主机之间**的逻辑通信 | 邮政服务（找到家庭地址）     |
    | **传输层** | **进程之间**的逻辑通信 | 家长（将信件分发给家中孩子） |

    > **网络层只负责把数据送到正确的主机，而传输层负责把数据送到主机上正确的应用进程**

    - **传输层依赖网络层**：利用网络层提供的主机间通信服务
    - **传输层增强网络层**：解决网络层无法处理的问题
        - ✅ **可以增强**：不可靠 $\rightarrow$ 可靠（如 TCP 通过确认、重传机制实现）
        - ❌ **不可增强**：带宽、延迟（由物理链路和网络架构决定，传输层无法突破物理极限）

- `3.1.3` 传输层的工作流程

    传输层的工作可以清晰地分为发送方和接收方两个独立的流程，核心是实现**多路复用**和**多路分解**

    - 发送方工作流程
        1. 接收来自应用层的完整消息（app.msg）
        2. 确定报文段的头部信息（包括源端口号、目的端口号等关键标识）
        3. 将应用层消息分割成合适大小的报文段，添加传输层头部 T~h~
        4. 将封装好的报文段传递给网络层，由网络层继续封装并发送
    - 接收方工作流程
        1. 从网络层接收传输层报文段
        2. 检测并解析报文段的头部信息
        3. 去除传输层头部，提取出原始的应用层消息
        4. 根据头部中的端口号信息，通过**套接字 Socket** 将消息准确地解复用到对应的应用程序

## `3.2` 多路复用与解复用

- `3.2.1` 基本概念

    多路复用与解复用是传输层最核心的功能之一，解决了 “**一台主机上多个应用进程如何共享同一个网络连接收发数据**” 的问题

    | 概念           | 定义                                                         |
    | -------------- | ------------------------------------------------------------ |
    | **多路复用**   | 发送端从多个套接字接收来自不同应用进程的报文，添加头部信息后封装为报文段，传递给网络层 |
    | **多路解复用** | 接收端根据报文段头部信息（IP 地址、端口号），将数据交付给正确的套接字及对应进程 |

    **传输层如何知道将消息传递给哪个进程？**

    > 通过**端口号** `Port Number` ，每个应用进程绑定不同的端口号，传输层根据报文段头部的**目的端口号**进行精确分发

- `3.2.2` UDP 与 TCP 中的多路解复用

    - 传输层解复用的核心是**通过唯一标识区分不同的应用进程**：

        - IP 地址只能标识互联网中的一台主机，无法区分主机上的多个进程
        - 端口号（16 位整数，范围 0-65535）用于标识主机上的特定应用进程
        - TCP / UDP 报文段头部包含**源端口号**和**目标端口号**两个关键字段（共 32 比特）

        主机收到 IP 数据报后，会联合使用 IP 地址和端口号，将报文段发送给合适的套接字

    - UDP 中的多路解复用

        - **解复用标识：**UDP Socket = ( 目的 IP，目的端口号 )

            - 仅使用**目的 IP 地址 + 目的端口号**唯一标识一个 UDP 套接字
            - 源 IP 地址和源端口号不参与 UDP 套接字的匹配

            - 具备相同目标 IP 地址和目标端口号的 IP 数据报，即使来自不同的源 IP 地址或源端口，都会被传送到同一个目标 UDP 套接字上

        - **工作流程**

            - 创建 UDP 套接字时，必须绑定一个本地端口号
            - 发送 UDP 报文时，需要指定目标 IP 地址和目标端口号
            - 接收 UDP 报文时，主机仅检查报文段的目标 IP 和目标端口
            - 将报文段交给对应端口号的 UDP 套接字，无论其源 IP 和源端口是什么

    - TCP 中的多路解复用

        - **解复用标识：**TCP Socket = ( 源 IP 地址，源端口号，目的 IP 地址，目的端口号 ) 
            - 使用**源 IP 地址 + 源端口号 + 目的 IP 地址 + 目的端口号**唯一标识一个 TCP 套接字
            - 四个字段中任何一个不同，都会被识别为不同的 TCP 连接
        - **工作流程**
            - 服务器创建一个监听套接字，绑定到特定端口（如 Web 服务器的 80 端口）
            - 客户端发起 TCP 连接请求，包含客户端的源 IP 和源端口
            - 服务器接受连接后，会为每个新连接创建一个**独立的新套接字**
            - 接收 TCP 报文时，主机根据四元组将报文段分发给对应的 TCP 套接字
        - **关键特性**
            - 服务器能够在**同一个 TCP 端口上同时支持多个 TCP 连接**，每个连接由不同的四元组标识（源 IP 和源端口不同）
            - Web 服务器对每个连接客户端都有不同的套接字，非持久连接对每个请求都有不同的套接字

    | 特性           | UDP 多路解复用                  | TCP 多路解复用                                |
    | -------------- | ------------------------------- | --------------------------------------------- |
    | 标识方式       | 二元组（目的 IP + 目的端口）    | 四元组（源 IP + 源端口 + 目的 IP + 目的端口） |
    | 源信息作用     | 不参与套接字匹配                | 参与套接字匹配，是区分连接的关键              |
    | 同一端口多连接 | 不支持，所有报文到同一个套接字  | 支持，不同连接对应不同套接字                  |
    | 适用场景       | DNS、视频直播、游戏等无连接应用 | Web、邮件、文件传输等面向连接应用             |

    - 关键区别：两个具有**不同源IP地址**和/或**不同源端口号**的报文段
        - **UDP**：若目的 IP 和目的端口相同，则通过**相同套接字**定向到**相同进程**
        - **TCP**：被定向到**两个不同的套接字**（除非报文段携带初始创建连接的请求，即 SYN 报文段）

    > 多路复用与解复用并非传输层独有，而是发生在计算机网络的所有层次

## `3.3` 无连接传输 UDP

- `3.3.1` UDP 协议概述

    用户数据报协议 `User Datagram Protocol (UDP)` 是互联网传输层的核心协议之一，由 **RFC 768**（1980 年 8 月发布）定义，是一种 “无装饰” `No Frills` 、“极简” `Bare Bones` 的传输协议

    | 特征             | 具体含义                                       | 深层影响                               |
    | ---------------- | ---------------------------------------------- | -------------------------------------- |
    | **无连接**       | 发送数据前无需建立连接，发送后无需释放连接     | 减少 RTT 延迟，但无连接状态可维护      |
    | **不可靠**       | 不保证数据到达、不保证按序到达、不重传丢失报文 | 报文段可能丢失、乱序，需应用层自行处理 |
    | **面向报文**     | 应用层给什么就发什么，不拆分、不合并           | 保留应用层消息边界，但受 MTU 限制      |
    | **首部开销极小** | 固定 **8 字节** 首部（对比 TCP 的 20~60 字节） | 协议处理速度快，网络带宽占用少         |
    | **无控制机制**   | 不具备 TCP 的拥塞控制、流量控制、差错恢复      | 网络拥塞时仍能发送，但可能加剧拥塞     |

    为什么需要 UDP ？

    1. **低延迟**：不建立连接，立即发送，适合实时性要求高的场景
    2. **简单性**：发送端和接收端无需维护连接状态表，资源消耗极低
    3. **低开销**：首部仅 8 字节，对包头带宽占用极小
    4. **无阻塞**：不受拥塞控制约束，应用层可自主决定发送速率；当网络服务受威胁时，UDP 仍能正常工作（不会因拥塞控制而完全停滞）

- `3.3.2` UDP 报文段格式

    UDP 报文段由 **8 字节首部**（固定） 和 **可变长数据部分** 组成，其中数据部分最大长度为 **65527 字节**

    | 字段           | 长度  | 作用与说明                                                   |
    | -------------- | ----- | ------------------------------------------------------------ |
    | **源端口号**   | 16 位 | 标识发送方应用进程端口，若不需要对方回信（如单向广播），可置为 0 |
    | **目的端口号** | 16 位 | 标识接收方应用进程端口，终点交付报文时必须使用，用于解复用   |
    | **长度**       | 16 位 | 表示 **UDP 首部 + 数据部分** 的总字节数，最小值为 8（仅首部），最大值为 65535 |
    | **校验和**     | 16 位 | 提供差错检测功能，在 IPv4 中为**可选**（可置 0 表示禁用），在 IPv6 中为**强制** |

- `3.3.3` UDP 传输层工作流程

    ```mermaid
    sequenceDiagram
        participant App as 应用层
        participant UDP as 传输层 (UDP)
        participant IP as 网络层 (IP)
        
        App->>UDP: 传递应用层消息 (如 SNMP msg)
        UDP->>UDP: 确定首部信息 (源/目的端口、长度)
        UDP->>UDP: 计算校验和 (含伪首部)
        UDP->>UDP: 生成 UDP 报文段
        UDP->>IP: 将报文段交付给 IP 层
        Note over UDP: 核心动作：封装 + 端口复用
        IP->>UDP: 交付 UDP 报文段
        UDP->>UDP: 检测校验和与首部信息
        UDP->>UDP: 提取应用层消息
        UDP->>App: 通过套接字解复用交付应用
        Note over UDP: 若端口无对应进程，丢弃并报 ICMP 端口不可达
    ```

    - **发送方**：
        1. **接收消息**：从应用层接收待发送数据
        2. **填充首部**：填入源端口、目的端口、长度；校验和字段初始置 0
        3. **计算校验和**：基于伪首部 + UDP 首部 + 数据计算
        4. **交付下层**：将完整报文段交给 IP 层封装成 IP 数据报
    - **接收方**：
        1. **从 IP 接收**：剥离 IP 首部后得到 UDP 报文段
        2. **差错检测**：重新计算校验和，与首部中的校验和字段比对
        3. **提取数据**：去除 8 字节首部，得到应用层消息
        4. **解复用** `Demultiplexing`：根据**目的端口号**将消息交付给对应的应用进程

- `3.3.4` UDP 校验和 `Checknum`

    这是 UDP 提供的唯一可靠性机制

    - 校验和的计算范围：伪首部 `Pseudo Header`

        - UDP 校验和的计算**不仅包含 UDP 首部和数据**，还临时引入一个 **12 字节的伪首部**

        - 伪首部本身不传输，仅用于计算，目的是防止 IP 出现误投递（如地址错误、协议错配）

        - **构造伪首部**：从 IP 首部提取源/目的 IP （各 4 字节）+ 填充位（1 字节）+ 协议号（17，1 字节）+ UDP 长度（2 字节）

    - 校验和的计算：反码求和
        1. 1**6 位求和**：将所有内容按 16 位（2 字节）分组，奇数时末尾补 1 字节 `0x00` 凑整，进行二进制反码加法
        2. **回卷** `Wraparound` ：若相加产生进位（超过 16 位），将进位加到低 16 位
        3. **按位取反**：对最终和按位取反（0 变 1，1 变 0），结果即为校验和
    - 接收方的验证
        1. 对收到的 UDP 报文段（包括伪首部、接收到的校验和）执行相同的二进制反码求和
        2. 如果结果不是全 1，说明传输过程中出现了差错，丢弃该报文段
        3. 如果结果是全 1，说明没有检测到差错，但也许还是有差错（校验和的保护是很弱的）

- `3.3.5` UDP 的典型应用与现代演进

    - 传统应用场景

        | 应用                    | 使用 UDP 的原因                            |
        | ----------------------- | ------------------------------------------ |
        | **DNS**                 | 查询响应小、速度快、单次请求无需连接开销   |
        | **SNMP**                | 网络管理需定期轮询，UDP 开销低             |
        | **流媒体（视频/音频）** | 容忍少量丢包，但对延迟极度敏感             |
        | **VoIP / 在线游戏**     | 实时性优先，重传造成的延迟比丢包更不可接受 |

    - 现代演进：HTTP/3 over QUIC

        **QUIC**（Quick UDP Internet Connections）是 Google 提出、IETF 标准化的协议，它在 **UDP 之上重新实现了类似 TCP 的可靠传输机制**

        ```mermaid
        graph LR
            A[HTTP/3] --> B[QUIC]
            B --> C[TCP-like 拥塞控制<br/>丢包恢复<br/>流量控制]
            B --> D[TLS 1.3 加密<br/>集成于协议内部]
            B --> E[UDP 底层传输]
        ```

        > **核心启示**：UDP 本身不可靠，但可以在其**之上**（应用层）构建可靠机制
        >
        > 这体现了网络协议设计的分层思想 —— UDP 提供极简传输能力，可靠性按需在上层增强

- `3.3.6` UDP 协议小结
    - UDP 是一种极简的无连接传输协议，提供 "尽力而为" 的服务
    - 优点：无握手延迟、头部开销小、无拥塞控制、实现简单
    - 缺点：不保证可靠交付、不保证顺序、无流量控制
    - 核心价值：为对实时性要求高、容忍少量丢失的应用提供高效的传输服务
    - 扩展能力：可以在应用层增加可靠性机制，实现基于 UDP 的可靠传输

## `3.4` 可靠数据传输的原理

- `3.4.1` RDT 概述

    可靠数据传输 `Reliable Data Transfer (RDT)` 是计算机网络中的核心问题之一，在应用层、传输层和数据链路层都非常重要，被认为是网络领域 Top-10 问题之一

    - **问题根源**：信道天然具有不可靠性，会出现三种典型问题

        - 比特差错：分组中的某些比特发生翻转
        - 分组丢失：分组在传输过程中完全丢失
        - 分组乱序：分组到达接收方的顺序与发送顺序不同

        同时，收发双方无法直接感知对方状态，必须通过特定控制消息（确认、重传请求）进行沟通

    - 问题抽象与建模

        - 只考虑单向数据传输（控制信息双向流动），双向传输可看作两个单向传输的组合
        - 接口定义
            - `rdt_send(data)`：上层调用，将数据交给发送方
            - `udt_send(packet)`：RDT调用，通过不可靠信道发送分组
            - `make_pkt(data)` ：将数据打包成分组
            - `rdt_rcv(packet)`：当分组到达时被调用
            - `deliver_data(data)`：将数据交付给上层

- `3.4.2` RDT 1.0 与可靠信道上的可靠数据传输

    **假设条件**：下层信道完全可靠 —— 没有比特出错，没有分组丢失

    **工作机制**：

    - **发送方**：只有一个状态 “等待上层调用”，收到 `rdt_send(data)` 后，封装数据为分组并发送
    - **接收方**：只有一个状态 “等待下层调用”，收到 `rdt_rcv(packet)` 后，提取数据并交付上层

    > RDT 1.0 只做**封装和解封装**，是最简单的理想模型，但完全不具备实际应用价值，仅作为后续协议的基础

- `3.4.3` RDT 2.0 与比特差错处理

    **假设条件**：下层信道可能出现比特翻转（0 变 1，1 变 0），需要**差错检测**和**恢复机制**

    | 引入的新机制           | 作用       | 说明                                                         |
    | ---------------------- | ---------- | ------------------------------------------------------------ |
    | **校验和**             | 差错检测   | 发送方计算校验和放入分组头部，接收方重新计算验证             |
    | `ACK` / `NAK` **反馈** | 接收方通知 | `ACK` = 确认正确接收 `Acknowledgement` <br/>`NAK` = 否定确认 `Negative Acknowledgement`（分组出错） |
    | **重传机制**           | 恢复差错   | 发送方收到 NAK 后重传该分组                                  |

    **工作流程**：

    - 发送方行为
        1. **等待上层调用**：收到上层数据 $\rightarrow$ 封装分组（附加校验和）$\rightarrow$ 发送 $\rightarrow$ 转入“等待 `ACK` / `NAK` ”状态
        2. **等待** `ACK` / `NAK`：
            - 收到正确的 `ACK` $\rightarrow$ 转入“等待上层调用”状态
            - 收到正确的 `NAK` $\rightarrow$ 重传当前分组 $\rightarrow$ 保持 “等待 `ACK` / `NAK` ” 状态
    - 接收方行为
        - 收到正确分组（校验和无误）\(\rightarrow\) 交付上层 \(\rightarrow\) 发送 `ACK` \(\rightarrow\) 保持 “等待分组” 状态
        - 收到受损分组（校验和错误）\(\rightarrow\) 发送 `NAK` \(\rightarrow\) 保持 “等待分组” 状态

    **重要缺陷**：如果 `ACK` / `NAK` **受损**怎么办？发送方不知道发生了什么，难以决策 —— 重传产生重复分组，不重传导致死锁

- `3.4.4` RDT 2.1 与序号机制

    **核心机制**：引入**序列号** `Sequence Number` 机制，发送方在每个分组中加入序号（0 和 1 交替）

    > **为什么只需要 0 和 1 两个序号？** 因为采用**停等协议**，一次只发送一个未经确认的分组，因此发送方**要么传新分组，要么重传旧分组**，两种状态足以区分

    **关键逻辑 —— 处理重复分组**： 当 `ACK` / `NAK` 受损时，发送方重传当前分组，接收方通过序号判断是否为重复分组：如果是已接收过的序号，则**丢弃**（不交付上层），但**仍然发送** `ACK`（告知发送方已收到）

    **工作流程**：

    - 发送方行为

        1. **等待发送 0 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 0） $\rightarrow$ 发送 $\rightarrow$ 转入“等待 `ACK` / `NAK` 0”
        2. **等待** `ACK` / `NAK` **0**：收到正确 `ACK` 且 Seq = 0 $\rightarrow$ 转入“等待发送 1 号分组”；收到 `NAK` 或 `ACK` 受损 $\rightarrow$ 重传 0 号分组
        3. **等待发送 1 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 1） $\rightarrow$ 发送 $\rightarrow$ 转入“等待 `ACK` / `NAK` 1”
        4. **等待** `ACK` / `NAK` **1**：收到正确 `ACK` 且 Seq = 1 $\rightarrow$ 转入“等待发送 0 号分组”；收到 `NAK` 或 `ACK` 受损 $\rightarrow$ 重传 1 号分组

    - 接收方行为

        1. **等待 0 号分组**：

            收到正确 Seq = 0 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` $\rightarrow$ 转入“等待 1 号”

            收到受损分组 $\rightarrow$ 发 `NAK`

            收到正确 Seq = 1 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK`（让发送方知道已收到）

        2. **等待1号分组**：

            收到正确 Seq = 1 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` $\rightarrow$ 转入“等待 0 号”

            收到受损分组 $\rightarrow$ 发 `NAK`

            收到正确 Seq = 0 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK`（让发送方知道已收到）

    ```mermaid
    sequenceDiagram
        participant S as 发送方(sender)
        participant R as 接收方(receiver)
        
        S->>R: 发送 pkt0（序号0）
        R->>R: 正确接收pkt0，期望序号变为1
        R->>S: 发送 ACK0（确认pkt0）
        Note over S,R: ACK0在传输中出错（ack error）
        S->>S: 收到错误ACK，无法确认pkt0是否被接收
        S->>R: 重传 pkt0
        R->>R: 收到重复pkt0（当前期望序号是1），丢弃重复分组
        R->>S: 重新发送 ACK0（告知发送方pkt0已收到）
        S->>S: 收到正确ACK0，确认pkt0传输成功
        S->>R: 发送 pkt1（序号1）
        R->>R: 正确接收pkt1，期望序号变为0
        R->>S: 发送 ACK1（确认pkt1）
    ```

- `3.4.5` RDT 2.2 与 `NAK` 的移除

    **核心机制**：利用带编号的 `ACK` （具体说是前一个数据单位的 `ACK`）代替 `NAK` 来实现协议的简化，减少确认信息的种类

    | 场景                                       | RDT 2.1 做法 | RDT 2.2 做法                              |
    | ------------------------------------------ | ------------ | ----------------------------------------- |
    | 分组正确接收                               | 发 `ACK`     | 发 `ACK[n]`（n 为刚收到的分组序号）       |
    | 分组出错/重复                              | 发 `NAK`     | 发 `ACK[n-1]`（对上一个正确分组的 `ACK`） |
    | 收到重复的 `ACK`<br>（`ACK` 在传输中出错） | 重传当前分组 | 重传当前分组（处理逻辑没有变化）          |

    **工作流程**：

    - 发送方行为

        1. **等待发送 0 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 0） $\rightarrow$ 发送 $\rightarrow$ 转入“等待 `ACK` 0 ”
        2. **等待** `ACK` **0**：收到正确 `ACK` 且 Seq = 0 $\rightarrow$ 转入“等待发送 1 号分组”；收到 `ACK` 1 或 `ACK` 受损 $\rightarrow$ 重传 0 号分组
        3. **等待发送 1 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 1） $\rightarrow$ 发送 $\rightarrow$ 转入“等待 `ACK` ”
        4. **等待** `ACK` **1**：收到正确 `ACK` 且 Seq = 1 $\rightarrow$ 转入“等待发送 0 号分组”；收到 `ACK` 0 或 `ACK` 受损 $\rightarrow$ 重传 1 号分组

    - 接收方行为

        1. **等待 0 号分组**：

            收到正确 Seq = 0 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` 0 $\rightarrow$ 转入“等待 1 号”

            收到受损分组 $\rightarrow$ 发 `ACK` 1

            收到正确 Seq = 1 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK` 0（让发送方知道已收到）

        2. **等待1号分组**：

            收到正确 Seq = 1 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` 1 $\rightarrow$ 转入“等待 0 号”

            收到受损分组 $\rightarrow$ 发 `ACK` 0

            收到正确 Seq = 0 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK` 1（让发送方知道已收到）

    ```mermaid
    sequenceDiagram
        participant S as 发送方
        participant R as 接收方
        S->>R: send pkt0
        R->>S: rcv pkt0, send ack0
        S->>R: send pkt1
        Note right of R: rcv pkt1, error!
        R->>S: send ack0 [重复 ACK，替代 NAK]
        Note left of S: 收到 ack0（期待 ack1），重传
        S->>R: resend pkt1
        R->>S: rcv pkt1, send ack1
    ```

- `3.4.6` RDT 3.0 与超时重传机制

    **核心机制**：考虑信道中可能存在的分组丢失的现象，引入**超时重传机制**，若超时认为分组丢失并进行重传

    具体来说：

    - 发送方发送每个分组后，启动一个**倒计时定时器**
    - 定时器超时前收到 `ACK`：停止定时器，发送下一个分组
    - 定时器超时仍未收到 `ACK`：认为分组（或 `ACK`）丢失，**重传当前分组并重启定时器**
    - 利用序号处理重复分组：接收方识别重复分组后丢弃，并重新发送对应的 `ACK`

    **工作流程**：

    - 发送方行为

        1.  **等待发送 0 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 0）$\rightarrow$ 发送 $\rightarrow$ **启动定时器** $\rightarrow$ 转入“等待 `ACK` 0”

        2.  **等待** `ACK` **0**：

            收到正确 `ACK` 且 Seq = 0 $\rightarrow$ **停止定时器** $\rightarrow$ 转入“等待发送 1 号分组”

            收到 `ACK` 1 或 `ACK` 受损 $\rightarrow$ **直接忽略**

            **定时器超时** $\rightarrow$ 重传 0 号分组 $\rightarrow$ **重启定时器**

        3.  **等待发送 1 号分组**：收到上层调用 $\rightarrow$ 封装（Seq = 1）$\rightarrow$ 发送 $\rightarrow$ **启动定时器** $\rightarrow$ 转入“等待 `ACK` 1”

        4.  **等待** `ACK` **1**：

            收到正确 `ACK` 且 Seq = 1 $\rightarrow$ **停止定时器** $\rightarrow$ 转入“等待发送 0 号分组”

            收到 `ACK` 0 或 `ACK` 受损 $\rightarrow$ **直接忽略**

            **定时器超时** $\rightarrow$ 重传 1 号分组 $\rightarrow$ **重启定时器**

    - 接收方行为（和 RDT 2.2 完全一致）
        1. **等待 0 号分组**：
            - 收到正确 Seq = 0 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` 0 $\rightarrow$ 转入“等待 1 号”
            - 收到受损分组 $\rightarrow$ 发 `ACK` 1
            - 收到正确 Seq = 1 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK` 1
        2. **等待 1 号分组**：
            - 收到正确 Seq = 1 分组 $\rightarrow$ 交付上层 $\rightarrow$ 发 `ACK` 1 $\rightarrow$ 转入“等待 0 号”
            - 收到受损分组 $\rightarrow$ 发 `ACK` 0
            - 收到正确 Seq = 0 分组（重复）$\rightarrow$ 丢弃 $\rightarrow$ 发 `ACK` 0

    ```mermaid
    sequenceDiagram
        participant S as 发送方
        participant R as 接收方
        S->>R: send pkt0
        R->>S: rcv pkt0, send ack0
        S->>R: send pkt1
        Note right of R: pkt1 丢失！
        Note left of S: ⏰ timeout!
        S->>R: resend pkt1
        R->>S: rcv pkt1, send ack1
        Note left of S: ack1 丢失！
        Note left of S: ⏰ timeout!
        S->>R: resend pkt1
        R->>S: rcv pkt1 (duplicate), send ack1
        S->>R: send pkt0
        R->>S: rcv pkt0, send ack0
    ```

- `3.4.7` RDT 1.0 - 3.0 小结

    | 协议版本 | 解决的信道问题                | 核心机制                  | 序号范围 | 定时器 | 信道利用率             |
    | -------- | ----------------------------- | ------------------------- | -------- | ------ | ---------------------- |
    | RDT 1.0  | 信道完全可靠                  | 无差错控制                | 无       | 无     | 100%（理想）           |
    | RDT 2.0  | 比特差错                      | `ACK` + `NAK`             | 无       | 无     | 低                     |
    | RDT 2.1  | 比特差错 + `ACK` / `NAK` 出错 | `ACK` + `NAK` + 序号      | $0,1$    | 无     | 低                     |
    | RDT 2.2  | 比特差错 + 简化协议           | 仅带编号的 `ACK`          | $0,1$    | 无     | 低                     |
    | RDT 3.0  | 比特差错 + 分组丢失           | 带编号的 `ACK` + 超时重传 | $0,1$    | 有     | 低（停等机制固有缺陷） |

- `3.4.8` RDT 3.0 的性能问题

    RDT 3.0 虽能实现可靠数据传输，但发送方**在收到前一分组的 `ACK` 之前，不能发送下一分组**，无法充分利用链路的传输能力

    - 信道利用率 `Sender Utilization`（表示发送方忙于发送比特的时间比例）的计算：$U_{sender} = \frac{L/R}{RTT + L/R}$

        | 参数        | 含义                                                 |
        | ----------- | ---------------------------------------------------- |
        | $L$         | 分组长度 / bit                                       |
        | $R$         | 链路传输速率 / bps                                   |
        | $L/R$       | 传输时延（发送一个分组所需时间）                     |
        | $RTT$       | 往返时间 `Round-Trip Time` = 2 $\times$ 单次传播延时 |
        | $RTT + L/R$ | 发送一个分组并收到确认的总周期                       |

    > 考虑这样的情形：1 Gbps （10, 7374, 1824 bps）链路，15 ms 端-端传播延时，分组大小 1 KB（8192 bit）
    >
    > 可以计算得 $U\approx\frac{8000\div10^9}{0.015\times2+8000\div10^9}\approx0.027\%$，绝大部分时间**信道处于空闲状态**！
    >
    > 这充分说明，RDT 3.0 的性能问题瓶颈不在于物理链路，而在于**协议本身限制了物理资源的利用**

- `3.4.9` 流水线机制 `Pipelining` 

    流水线机制允许发送方在**未收到对方确认的情况下，连续发送多个分组**，这样在等待第一个分组的 `ACK` 时，链路可以继续传输后续分组，从而大幅提高利用率

    ```mermaid
    sequenceDiagram
        participant S as 发送方
        participant R as 接收方
        
        Note over S,R: Stop-and-Wait（RDT 3.0）
        S->>R: 分组1
        activate S
        Note right of S: 等待ACK...
        R-->>S: ACK1
        deactivate S
        S->>R: 分组2
        activate S
        Note right of S: 等待ACK...
        R-->>S: ACK2
        deactivate S
        
        Note over S,R: Pipelining（流水线）
        S->>R: 分组1
        S->>R: 分组2
        S->>R: 分组3
        Note right of S: 连续发送，无需等待
        R-->>S: ACK1
        R-->>S: ACK2
        R-->>S: ACK3
    ```

    - 如果按上图所示发送 3 个分组，仍然按照上述链路计算利用率，$U\approx0.081\%$ 变为原来的三倍

        $\rightarrow$ 当发送的分组数足够多，使得 \(n \times (L/R) \geq RTT\) 时，利用率可以达到 100%，此时瓶颈转移为链路带宽本身

    - 流水线提出的新要求

        - 必须增加序号的范围（用更多比特表示分组序号）
        - 发送方和接收方都需要缓冲区
            - 发送方缓存：存放已发送但未确认的分组，用于可能的重传
            - 接收方缓存：处理乱序到达的分组，排序后按序交付给上层

- `3.4.10` 滑动窗口技术 `Sliding Window`

    滑动窗口是实现流水线协议的核心机制，通过控制发送方和接收方的窗口大小来调节数据传输速率和可靠性

    - 发送缓冲区：内存中专门划分的一块连续区域，是传输层所有待处理分组的存储容器

        - 核心功能
            - 暂存**上层应用交付但尚未发送**的分组
            - 备份**已发送但未收到接收方确认**的分组（用于重传）
        - **必要性**：当分组在网络中丢失或出错时，能够直接从缓冲区取出分组重传，无需等待上层重新生成数据

        - 发送缓冲区中的分组状态
            - **未发送分组**：落入缓冲区但尚未被发送到网络的分组，可以连续发送
            - **已发送未确认分组**：已经发出但还没有收到确认的分组，只有收到确认后才能从缓冲区删除（发送窗口）

    - 发送窗口 `Sending Window` 

        发送窗口是**发送缓冲区的子集**，代表**已发送但未经确认**的分组序号构成的空间（发送窗口的最大值 $\le$ 发送缓冲区的值）

        - 相关概念

            - 后沿 `base` ：已发送未确认分组的最小序号

            - 前沿 `NextSeqNum` ：下一个待发送分组的序号

            $\rightarrow$ 发送窗口大小 = 前沿 - 后沿

        - 发送窗口的移动规则

            | 移动类型 | 触发条件                                | 移动规则                                                     | 移动极限                          |
            | -------- | --------------------------------------- | ------------------------------------------------------------ | --------------------------------- |
            | 前沿移动 | 发送端每成功<br/>发送一个分组           | 前沿向前移动一个单位<br/>发送缓冲区中的这个单位进入发送窗口  | 前沿不能超过<br/>发送缓冲区的边界 |
            | 后沿移动 | 发送端收到接收方<br/>发来的有效确认分组 | 后沿向前移动到**连续已确认分组的下一个序号**<br/>发送缓冲区腾出空间，可以接收上层新的分组 | 后沿不能超过前沿                  |

    - 接收窗口 `Receiving Window`

        与发送端有区别的是，接收窗口等于**接收缓冲区**，表示**当前接收方允许接收的分组序号构成的连续空间**

        - 接收规则

            - 只有序号**落在接收窗口内的分组**，接收方才会接收；序号落在接收窗口外的分组，接收方直接丢弃

            - 接收窗口大小决定了接收方的接收能力：
                - 当 **Wr=1** 时：接收方只能**顺序接收**（必须先收到 n 号分组，才能接收 n+1 号分组，其他分组将被丢弃）
                - 当 **Wr>1** 时：接收方可以**乱序接收**（可以先缓存序号较大的分组，等待前面的分组到达后再按顺序交付给上层）

        - 接收窗口的移动规则

            - **低序号分组到达**：如果收到的是接收窗口最左端的分组（期望的下一个序号），则接收窗口向前滑动一个单位，并发送该分组的确认
            - **高序号分组到达**：如果收到的是接收窗口内但不是最左端的分组（乱序分组），则先缓存该分组，但**不滑动接收窗口**

        | 协议类型                             | 接收窗口大小 | 接收方式     | 确认方式                                         |
        | ------------------------------------ | ------------ | ------------ | ------------------------------------------------ |
        | 回退 N 步<br/>`Go-Back-to-N (GBN)`   | Wr = 1       | 只能顺序接收 | 累计确认（确认号 n 表示所有 < n 的分组都已接收） |
        | 选择重传<br/>`Selective Repeat (SR)` | Wr > 1       | 可以乱序接收 | 逐个确认（收到哪个分组就确认哪个分组）           |

    - 发送窗口与接收窗口的互动

        - 正常情况下：

            - 对于发送窗口，新分组落入发送缓冲区范围时，立即发送，**发送窗口前沿向前滑动**；收到老的低序号分组的确认时，**发送窗口后沿向前滑动**，允许新的分组进入发送缓冲区
            - 对于接收窗口，收到分组且落入接收窗口范围内时，接收该分组；对正确接收的**低序号分组**，向发送方发送确认

        - 异常情况下 GBN 的收发窗口互动

            GBN 协议的核心特点是**累计确认**和**回退重传**，异常处理围绕这两个特点展开

            - **发送窗口异常处理**：
                - **超时重传机制**：定时器超时后，**将发送窗口中的所有未确认分组全部重新发送**
                - 收到**老分组的重复确认**时：说明有分组在发送过程中丢失了，发送窗口后沿**不向前滑动**，新分组无法进入发送缓冲区（但缓冲区中已有新分组仍可发送）
            - **接收窗口异常处理**：
                - 收到**乱序分组**（未落入接收窗口范围）时：**直接抛弃**，不缓存，并**重复发送累计确认**
                - 对已正确接收的序号分组，**重复发送累计确认**

        - 异常情况下 SR 的收发窗口互动

            SR 协议针对 GBN 出错代价大的问题进行优化，核心是**单独确认**和**选择性重传**

            - **发送窗口异常处理**：
                - **超时重传机制**：定时器超时后，**只重传超时的那个分组**
                - 收到**老分组的重复确认**时：说明有分组在发送过程中丢失了，发送窗口后沿**不向前滑动**，新分组无法进入发送缓冲区（但缓冲区中已有新分组仍可发送）
            - **接收窗口异常处理**：
                - 收到**乱序分组但落入接收窗口范围**时：**接收并缓存**该分组
                - 对每个正确接收的分组，**单独发送确认**（非累计确认）

- `3.4.11` 流水线协议小结

    | 对比维度         | GBN 协议                                                     | SR 协议                                                      |
    | ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **相同点**       | 发送窗口大小 > 1，一次可发送多个未经确认的分组               | 同左                                                         |
    | **接收窗口大小** | =1                                                           | >1                                                           |
    | **接收方式**     | 只能顺序接收                                                 | 可以乱序接收                                                 |
    | **重传机制**     | 一个分组出错，回退重传该分组及之后所有已发送分组             | 一个分组出错，只重传该出错分组                               |
    | **确认方式**     | 累计确认                                                     | 单独确认                                                     |
    | **优点**         | 实现简单，所需资源少<br/>接收方只需 1 个缓存单元             | 一旦出错，回退 N 步重传，代价大                              |
    | **缺点**         | 出错时只重传一个分组，代价小                                 | 实现复杂，所需资源多<br/>接收方需要多个缓存单元              |
    | **适用场景**     | 1. 出错率非常低的链路<br/>2. 链路容量小（延迟小、带宽小）的场景 | 1. 出错率较高的链路<br/>2. 链路容量大（延迟大、带宽大）的场景 |

    - GBN 协议

        - 发送端最多在流水线中有 N 个未确认的分组
        - 接收端只发送**累计型确认**，若发现中间有分组丢失，不确认新到的分组
        - 发送端**只需设置一个定时器**（对最老的未确认分组）
        - 定时器到时，**重传所有未确认分组**

        ```mermaid
        sequenceDiagram
            participant S as 发送方
            participant R as 接收方
            S->>R: 发送pkt0
            S->>R: 发送pkt1
            S->>R: 发送pkt2 (丢失)
            S->>R: 发送pkt3
            R->>S: 接收pkt0, 发送ack0
            R->>S: 接收pkt1, 发送ack1
            R->>S: 接收pkt3 (乱序), 丢弃, 发送ack1
            S->>R: 发送pkt4
            R->>S: 接收pkt4 (乱序), 丢弃, 发送ack1
            S->>R: 发送pkt5
            R->>S: 接收pkt5 (乱序), 丢弃, 发送ack1
            Note over S: pkt2超时
            S->>R: 重传pkt2
            S->>R: 重传pkt3
            S->>R: 重传pkt4
            S->>R: 重传pkt5
            R->>S: 接收pkt2, 发送ack2
            R->>S: 接收pkt3, 发送ack3
            R->>S: 接收pkt4, 发送ack4
            R->>S: 接收pkt5, 发送ack5
        ```

    - SR 协议

        - 发送端最多在流水线中有 N 个未确认的分组
        - 接收方对每个到来的分组**单独确认**
        - 发送方为**每个未确认的分组保持一个定时器**
        - 定时器到时，**只重发超时的未确认分组**

        ```mermaid
        sequenceDiagram
            participant S as 发送方
            participant R as 接收方
            S->>R: 发送pkt0
            S->>R: 发送pkt1
            S->>R: 发送pkt2 (丢失)
            S->>R: 发送pkt3
            R->>S: 接收pkt0, 发送ack0
            R->>S: 接收pkt1, 发送ack1
            R->>S: 接收pkt3 (乱序), 缓存, 发送ack3
            S->>R: 发送pkt4
            R->>S: 接收pkt4 (乱序), 缓存, 发送ack4
            S->>R: 发送pkt5
            R->>S: 接收pkt5 (乱序), 缓存, 发送ack5
            Note over S: pkt2超时
            S->>R: 只重传pkt2
            R->>S: 接收pkt2, 按序交付pkt2、3、4、5, 发送ack5
        ```

- `3.4.12` SR 接收窗口困境

    考虑这样的情形：发送和接收窗口大小为 3，使用 2 位表示序号（合法序号有 $[0,1,2,3]$ ）

    ```mermaid
    sequenceDiagram
        participant S as 发送方
        participant R as 接收方
        Note over S: 发送窗口 [0,1,2]
        Note over R: 接收窗口 [0,1,2]
        S->>R: pkt0
        S->>R: pkt1
        S->>R: pkt2
        Note over R: 窗口滑动到 [3,0,1]
        R->>S: ack0
        R->>S: ack1
        R->>S: ack2
        Note over S: 所有 ack 全部丢失    
        Note over S: 超时，重传 pkt0
        S->>R: 重传pkt0
        Note over R: 序号0正好在当前接收窗口[3,0,1]范围内！
        Note over R: 以为收到总第 5 个分组，实际发送第 1 个分组
        R->>S: 错误地接收pkt0，当作新数据
    ```

    - 问题的本质：当**发送窗口和接收窗口的大小之和超过序号空间总长度** 2^n^ 时，接收方将**无法区分 "重传的旧分组" 和 "新的、序号相同的下一轮分组"**，从而导致数据错误

        $\rightarrow$ 需要限制发送窗口和接收窗口的大小，保证 **发送窗口 $+$ 接收窗口 $\le2^n$** 

        | 协议 | 最大发送窗口 | 最大接收窗口 |
        | ---- | ------------ | ------------ |
        | GBN  | $2^n - 1$    | 1（固定）    |
        | SR   | $2^{n-1}$    | $2^{n-1}$    |

## `3.5` 面向连接的传输 TCP

- `3.5.0` TCP 概述

    TCP（传输控制协议）是面向连接的、可靠的传输层协议，相关标准 RFC 包括：793（基础标准）、1122、2018、5681、7323

    1. **点对点**：TCP 是严格的一对一通信，一个发送方对应一个接收方，不支持广播和多播

        > 这是 TCP 与 UDP 的重要区别之一（UDP 支持广播 / 多播）

    2. **可靠的、按序的字节流**：TCP 将数据视为无结构字节流，不保留报文边界，保证数据**无丢失、无重复、按顺序**到达接收方

        关键参数：最大报文段大小 `Maximum Segment Size (MSS)`

        - TCP 报文段中数据的最大长度（不含 TCP 头部信息），默认 1460 字节
        - 与 MTU 的关系：以太网 MTU 为 1500 字节，减去 IP 首部和 TCP 首部（都是 20 字节），得到 MSS = 1460 字节
        - 作用：避免 IP 层分片，提高传输效率

    3. **全双工**：同一 TCP 连接上，数据可以双向同时传输，连接的两端都维护独立的发送缓冲区和接收缓冲区

    4. **累积确认**：接收方**只确认到连续收到的最后一个字节的序号**，对于乱序到达的数据，不会单独确认，等待缺失的数据到达后再累计确认，能有效减少确认报文的数量，提高信息传输效率

    5. **流水线传输**：发送方可以**连续发送多个报文段**，而不必等待前一个的确认，发送窗口的大小由**拥塞控制**和**流量控制**共同决定，相比停等协议，极大提高了信道利用率

    6. **面向连接**：数据传输前必须通过**三次握手**建立连接，数据传输结束后必须通过**四次挥手**释放连接，连接建立过程中，双方会初始化发送序号、接收窗口等状态变量

    7. **流量控制**：接收方通过 TCP 首部的 "接收窗口" 字段告知发送方自己的接收能力，能保证发送方发送的数据量不能超过接收方的接收窗口大小、防止发送方发送过快，导致接收方缓冲区溢出

- `3.5.1` 段结构

    TCP 报文段由**固定首部（20 字节）**、**可变选项部分**和**应用层数据**三部分组成

    | 字段名称     | 长度 / bit | 核心含义                                                     | 关键作用与备注                                               |
    | ------------ | ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | 源端口号     | 16         | 发送方应用进程的端口号                                       | 与源 IP 地址共同标识发送方的网络端点                         |
    | 目的端口号   | 16         | 接收方应用进程的端口号                                       | 与目的 IP 地址共同标识接收方的网络端点                       |
    | 序号         | 32         | 本报文段所携带数据的**第一个字节**<br/>在整个 TCP 字节流中的编号 | TCP 是面向字节流的协议，对字节而非<br />报文段编号，这是可靠传输的核心 |
    | 确认号       | 32         | 接收方**期望收到的下一个字节的序号**                         | 表示确认号之前的所有字节都已正确收到<br/>仅当 ACK 标志位为 1 时有效 |
    | 首部长度     | 4          | 以 4 字节为单位的 TCP 首部总长度                             | 取值范围 5-15<br/>最小值 5 表示首部仅含固定部分 20 字节<br/>最大值 15 表示首部总长度 60 字节 |
    | 保留位       | 4          | 预留用于未来协议扩展                                         | 目前所有位必须置为 0                                         |
    | CWR          | 1          | 拥塞窗口减少 `Congestion Window Reduced`                     | 发送方设置，表示已响应拥塞信号<br/>并降低了发送速率；ECN 机制的一部分 |
    | ECE          | 1          | ECN 回显 `ECN-Echo`                                          | 接收方设置，表示收到了 IP 层标记的<br/>拥塞数据包；ECN 机制的一部分 |
    | URG          | 1          | 紧急 `Urgent`                                                | 为 1 时表示紧急数据指针有效<br/>紧急数据优先传输             |
    | ACK          | 1          | 确认 `Acknowledgement`                                       | 为 1 时表示确认号字段有效<br/>TCP 连接建立后所有报文段必须置 1 |
    | PSH          | 1          | 推送 `Push`                                                  | 为 1 时要求接收方立即将数据<br/>交给应用层，不等待缓冲区填满 |
    | RST          | 1          | 复位 `Reset`                                                 | 为 1 时表示异常终止 TCP 连接<br/>用于处理错误或拒绝非法连接  |
    | SYN          | 1          | 同步 `Synchronize`                                           | 为 1 时表示连接建立请求或确认报文<br/>用于三次握手过程       |
    | FIN          | 1          | 终止 `Finish`                                                | 为 1 时表示发送方无数据要发送<br/>请求释放连接，用于四次挥手过程 |
    | 接收窗口     | 16         | 接收方当前缓冲区能够接收的最大字节数                         | TCP 流量控制的核心字段<br/>最大值 65535 字节<br />可通过窗口扩大选项扩展 |
    | 校验和       | 16         | 对 TCP 首部、数据和伪首部的校验结果                          | 强制校验，用于检测传输过程中的错误<br/>计算方式与 UDP 相同但为必选 |
    | 紧急数据指针 | 16         | 指向紧急数据最后一个字节的下一个位置                         | 仅当 URG 标志位为 1 时有效<br/>用于传输如中断命令等紧急数据  |
    | 可选内容     | 320        |                                                              | 用于扩展 TCP 的功能                                          |

    - 序号和确认号机制

        - 序号 `Sequence Number` ：本报文段所发送数据的**第一个字节**在整个字节流中的编号

        - 确认号 `Acknowledgement Number` ：接收方**期望收到的下一个字节的序号**，同时表示之前的所有字节都已正确收到

        - 简单 Telnet 场景示例

            ```mermaid
            sequenceDiagram
                participant A as Host A<br/>(用户)
                participant B as Host B<br/>(服务器)
                
                Note over A,B: 假设初始序号：<br/>A的seq=42, B的seq=79<br/>用户键入'C'
                
                A->>B: Seq=42, ACK=79, data='C'
                Note right of B: B收到'C'，回显并确认
                
                B->>A: Seq=79, ACK=43, data='C'
                Note left of A: A确认收到回显的'C'
                
                A->>B: Seq=43, ACK=80
                Note right of B: A确认已收到B的'C'
            ```

            1. A 发送字符 'C'：`Seq=42`，数据长度 1 字节，因此 B 期望下一个序号是 `42+1=43`
            2. B 回显 'C' 并确认：`ACK=43`（期望收到 A 的 43 号字节），同时携带数据 'C'（`Seq=79`）
            3. A 确认收到回显：`ACK=80`（期望收到 B 的 80 号字节），`Seq=43`（与上次发送的 `ACK=79` 对应的数据无关，这是 A 的数据流序号）

            > 捎带确认 `Piggybacking`：B 给 A 发送数据时，把对 A 的确认"捎带"在数据报文段中，提高效率

    - TCP 超时时间的估计

        超时重传是 TCP 实现可靠传输的重要手段，如果发送方一定时间内没有收到报文段确认，就认为该报文段丢失并重新发送

        - 超时时间需要合理的估计

            - **超时太短** $\rightarrow$ 过早重传，浪费带宽，造成不必要的重复报文
            - **超时太长** $\rightarrow$ 对报文段丢失反应迟钝，降低吞吐量

        - RTT 的估计

            超时时间需要根据 RTT 来设计，需要尽可能准确估计未来一段时间内随路由器拥塞、端系统负载等等原因波动的 RTT

            1. 测量样本 RTT `SampleRTT`

                - 从报文段发出（交给 IP）到收到该报文段确认之间的时间
                - **关键规则**：TCP **不为重传的报文段计算 SampleRTT**，仅测量一次传输就成功的报文段

            2. 估计 RTT `EstimatedRTT` ：指数加权平均算法 `Exponential Weighted Moving Average (EWMA)` 

                $EstimatedRTT = (1-\alpha) \times EstimatedRTT + \alpha \times SampleRTT$

                - **$\alpha = 0.125$** —— RFC 6298 推荐值，新的估计值由旧的估计值（占 87.5%）和新的样本值（占 12.5%）共同决定
                - 能够平滑网络波动的影响，同时反映最新的网络状况

        - 超时时间的估计

            1. 计算 RTT 偏差 `DevRTT`

                $DevRTT = (1-\beta) \times DevRTT + \beta \times |SampleRTT - EstimatedRTT|$

                - $\beta = 0.25$ —— RFC 6298 推荐值
                - 衡量 SampleRTT 偏离 EstimatedRTT 的程度，帮助一定程度上修正 EstimatedRTT 的估计

            2. 设置超时时间间隔 `TimeoutInterval`

                $$TimeoutInterval = EstimatedRTT + 4 \times DevRTT$$

                - **初始值**：RFC 6298 推荐 **1 秒**
                - **超时后的处理**：超时后 TimeoutInterval **加倍**（指数退避），避免即将被确认的报文段过早超时；一旦收到新 ACK 并更新 EstimatedRTT，重新按公式计算

- `3.5.2` 可靠数据传输

    - TCP 可靠数据传输基础

        TCP 在 IP 层提供的不可靠、无连接服务基础上，实现了可靠数据传输，核心技术包括：

        - **管道化报文段**：批量发送多个报文段（类似 GBN 和 SR 协议的结合），提高传输效率

            TCP 的确认是累积的，但许多 TCP 实现会**缓存乱序到达的报文段**（类似 SR），而不是直接丢弃，因此 TCP 类似 GBN 与 SR 的混合体

        - **单个重传定时器**：只维护一个定时器，与最早未确认的报文段关联（类似 GBN）

        - **累积确认**：ACK = n 表示所有序号小于 n 的字节都已被正确接收（类似 GBN）

        特别地，TCP 标准**没有规定**如何处理乱序到达的报文段，由具体实现者决定，可以选择缓存乱序报文段，也可以直接丢弃

    - TCP 发送方工作流程

        | 变量       | 含义                                         |
        | ---------- | -------------------------------------------- |
        | `NextSeq`  | 下一个要发送的字节序号（发送窗口前沿）       |
        | `SendBase` | 最早已发送但未确认的字节序号（发送窗口后沿） |
        | `y`        | ACK 报文中的确认号字段值                     |

        1. 从应用层接收数据并发送

            1. 从 `Nextseq` 开始创建报文段，序号 `Nextseq` 为报文段首字节的字节流编号，发送数据
            2. 如果定时器**还没有运行**，启动定时器，并与**最早未确认**的报文段关联，时间间隔 `TimeOutInterval` 由 RTT 估计值计算得出

        2. 超时：**重传**后沿最老的报文段（即 `SendBase` 对应的报文段） 并**重新启动**定时器

            > 注意：超时后会将超时间隔加倍（拥塞控制的一部分，避免网络拥塞时频繁重传）

        3. 收到确认 ACK

            1. 如果是对**尚未确认**的报文段确认（即 `y > SendBase`），更新 `SendBase = y`（窗口后沿向前滑动）
            2. 如果当前还有未被确认的报文段，重新启动定时器
            3. 如果所有报文段都已确认，停止定时器

    - TCP 重传机制

        1. ACK 丢失触发重传

            ```mermaid
            sequenceDiagram
                participant A as 主机A
                participant B as 主机B
                A->>B: Seq=92, 8字节数据
                B->>A: ACK=100 (丢失)
                Note over A: 重传定时器超时
                A->>B: Seq=92, 8字节数据 (重传)
                B->>A: ACK=100
            ```

            - 发送方发送的报文段到达接收方，但接收方返回的 ACK 在网络中丢失
            - 发送方超时后重传原报文段，接收方再次返回 ACK

        2. 过早超时触发重传

            ```mermaid
            sequenceDiagram
                participant A as 主机A
                participant B as 主机B
                A->>B: Seq=92, 8字节数据
                A->>B: Seq=100, 20字节数据
                B->>A: ACK=120
                Note over A: 重传定时器过早超时
                A->>B: Seq=92, 8字节数据 (重传)
                B->>A: ACK=100 (网络延迟)
                B->>A: ACK=120
            ```

            - 第一个 ACK 因网络延迟未及时到达，导致发送方过早超时重传
            - 发送方收到后续的 ACK=120 后，直接将发送窗口后沿滑动到 120，确认所有数据

        3. 累积回复触发重传

            ```mermaid
            sequenceDiagram
                participant A as 主机A
                participant B as 主机B
                A->>B: Seq=92, 8字节数据 (丢失)
                A->>B: Seq=100, 20字节数据
                B->>A: ACK=92 (重复1)
                B->>A: ACK=92 (重复2)
                Note over A: 收到重复ACK，触发快速重传
                A->>B: Seq=92, 8字节数据
                B->>A: ACK=120
            ```

            - 第一个报文段丢失，但后续报文段都到达接收方
            - 接收方发送重复 ACK，告知发送方丢失的报文段序号
            - 发送方收到重复 ACK 后，重传丢失的报文段

    - TCP 接收方工作流程

        - 产生 ACK 的建议

            | 接收方事件                                            | TCP 接收方动作                                               |
            | ----------------------------------------------------- | ------------------------------------------------------------ |
            | 按序到达的报文段<br/>且所有期望序号之前的数据都已确认 | 延迟 ACK，最多等待 500ms<br/>若下个按序报文段在 500ms 内到达，发送一个 ACK 确认两个报文到达<br/>否则 500ms 后发送 ACK |
            | 按序到达的报文段<br/>且有另一个按序报文段等待发送 ACK | 立即发送单个累积 ACK，确认两个按序报文段到达                 |
            | 比期望序号大的报文段乱序到达                          | 检测出数据流中的间隔<br/>立即发送重复的 ACK，指明下一个期望的字节序号 |
            | 填补间隔的报文段到达<br/>且报文起始于间隔的低端       | **立即发送** ACK，不受第一条延迟发送的约束                   |

            - **能拖就拖**：正常按序到达的数据，不急着确认，等 500ms 看看有没有下一个数据一起确认（减少 ACK 数量，节省带宽）
            - **凑齐两个**：如果已经有一个数据在等确认了，再来一个就立即一起确认（最多累积两个）
            - **立即抱怨**：收到乱序数据（说明中间有数据丢了），立刻发送重复 ACK 催促发送方重传
            - **补洞汇报**：收到能填补缺口的数据，立即确认让发送方知道可以继续发送

        - TCP 快速重传机制

            超时重传的超时周期通常设置得较长（为了避免误判），导致报文段丢失后的重传延迟很大，快速重传机制通过**重复  ACK **来提前检测报文段丢失，无需等待超时再重传

            > 如果发送方收到对**同一数据**的 **3 个冗余 ACK** `Triple Duplicate ACKs`，则重传具有**最小序号**的未确认报文段

            ```mermaid
            sequenceDiagram
                participant A as Host A (发送方)
                participant B as Host B (接收方)
                
                A->>B: Seq=92, 8 bytes
                A->>B: Seq=100, 20 bytes (丢失)
                A->>B: Seq=120, 15 bytes
                A->>B: Seq=135, 10 bytes
                A->>B: Seq=145, 12 bytes
                
                B->>A: ACK=100 (正常确认 92)
                B->>A: ACK=100 (重复 ACK，收到 120)
                B->>A: ACK=100 (重复 ACK，收到 135)
                B->>A: ACK=100 (重复 ACK，收到 145)
                
                Note over A: 收到 3 个重复 ACK<br/>触发快速重传<br/>不用等待超时
                A->>B: Seq=100, 20 bytes (快速重传)
                
                B->>A: ACK=165 (累积确认所有数据)
            ```

            

- `3.5.3` 流量控制

    TCP 流量控制机制能够避免由于 TCP 套接字缓冲区满导致的数据丢弃与额外重传问题

    - 流量控制的基本概念

        流量控制是**接收方控制发送方**的端到端机制，目的是不让发送方发送得太多、太快，以至于接收方的缓冲区溢出

        > 流量控制是**端到端**的控制机制，解决的是**发送方与接收方速率不匹配**的问题，而非网络拥塞问题

    - 实现机制：接收窗口

        接收方在其向发送方的 TCP 段头部的**接收窗口** `Receive Window (Rwnd)` **字段**中 “通告” 其空闲缓冲区大小，发送方根据该值限制未确认字节的个数，确保不超过接收方通告的 rwnd 值

        | 关键变量       | 含义                                                         |
        | -------------- | ------------------------------------------------------------ |
        | `RcvBuffer`    | 接收缓冲区总大小（典型默认值 4096 字节，可通过 Socket 选项设置） |
        | `LastByteRcvd` | 已从网络收到并放入缓冲区的最后一个字节的编号                 |
        | `LastByteRead` | 应用进程已从缓冲区读走的最后一个字节的编号                   |
        | `rwnd`         | 接收窗口 = 缓冲区剩余空闲空间                                |

        - 缓冲区不溢出约束：`LastByteRcvd` $-$ `LastByteRead` $\le$ `RcvBuffer`

        - 接收窗口计算公式：`rwnd` $=$ `RcvBuffer` $- ($`LastByteRcvd` $-$ `LastByteRead`$)$

- `3.5.4` 连接管理

    - **三次握手连接**

        TCP 是**面向连接**的传输层协议，在正式交换数据之前，必须通过握手过程在发送方和接收方之间建立可靠的通信关系

        - **应用层接口对应**：

            - 客户端：`Socket clientSocket = new Socket("hostname", port)` 底层触发 TCP 三次握手
            - 服务器：`Socket connectionSocket = welcomeSocket.accept()` 底层完成三次握手并返回连接套接字

        - 两次握手的缺陷分析

            - 在真实的网络环境中，报文传输延迟不确定、报文可能丢失并触发重传、报文可能乱序到达、通信双方可能无法感知对方的状态变化，两次握手带来了很多问题

            - 半连接问题 `Half-open Connection` 

                ```mermaid
                sequenceDiagram
                    participant C as 客户端
                    participant S as 服务器
                    
                    Note over C,S: 场景1：半连接问题
                    C->>S: req_conn(x)
                    Note over C: 超时重传
                    C->>S: req_conn(x')
                    S->>C: acc_conn(x')(第一次连接返回)
                    Note over C,S: 建立连接x'，传输数据后关闭
                    Note over S: 延迟的req_conn(x)到达
                    S->>C: acc_conn(x)
                    Note over S: 进入ESTAB状态（半连接）
                    Note over C: 已关闭，忽略该报文
                    Note over S: 一直维护无用连接，浪费资源
                ```

                - 服务器在第二次握手后就认为连接已建立（ESTAB），但客户端可能由于崩溃、重启或根本没收到ACK而**并不认为连接存在**

                - 服务器端维护了一个"僵尸连接"，占用端口和内存资源，客户端却毫不知情

            - 冗余数据被接受 `Duplicate Data Accepted` 

                ``` mermaid
                sequenceDiagram
                    participant C as 客户端
                    participant S as 服务器
                    
                    Note over C,S: 场景2：旧数据被误接收
                    C->>S: req_conn(x) (延迟)
                    Note over C: 超时重传
                    C->>S: req_conn(x')
                    C->>S: data(x'+1)
                    Note over C: 超时重传
                    C->>S: data(x'+1)
                    S->>C: acc_conn(x')
                    Note over C,S: 建立连接x'，传输数据后关闭
                    Note over S: 延迟的req_conn(x)到达
                    S->>C: acc_conn(x)
                    Note over S: 进入ESTAB状态
                    C->>S: data(x'+1) (延迟的数据到达)
                    Note over S: 误将旧数据当作新连接数据接收
                ```

                - 旧连接的延迟报文被新连接误接收
                - 由于两次握手没有**变化的初始序列号**机制，服务器无法区分这是旧连接的残留数据还是新连接的有效数据

        - TCP 三次握手的流程

            ```mermaid
            sequenceDiagram
                participant C as 客户端
                participant S as 服务器
                
                Note over C: CLOSED
                Note over S: LISTEN
                
                Note over C: 调用connect()
                C->>S: SYN(seq=x)
                Note over C: SYN_SENT
                
                Note over S: 收到SYN
                S->>C: SYN(seq=y), ACK(ack=x+1)
                Note over S: SYN_RCVD
                
                Note over C: 收到SYN+ACK
                C->>S: ACK(ack=y+1)
                Note over C: ESTABLISHED
                
                Note over S: 收到ACK
                Note over S: ESTABLISHED
            ```

            | 握手次数   | 发送方 | 关键标志                       | 核心作用                                                     |
            | ---------- | ------ | ------------------------------ | ------------------------------------------------------------ |
            | **第一次** | 客户端 | `SYN=1, seq=x`                 | 客户端证明"我能发送"<br/>告知初始序列号 x                    |
            | **第二次** | 服务器 | `SYN=1, ACK=1, seq=y, ack=x+1` | 服务器证明"我能接收也能发送"<br/>告知初始序列号 y，确认收到 x |
            | **第三次** | 客户端 | `ACK=1, seq=x+1, ack=y+1`      | 客户端证明"我能接收"<br/>确认收到 y，**双方状态达成一致**    |

            1. 三次握手解决了半连接问题：
                - 当延迟的旧 SYN 报文到达服务器时，服务器会回复 SYN+ACK
                - 客户端收到后发现该报文的序列号不属于当前任何活跃连接，会立即发送 RST（复位）报文
                - 服务器收到 RST 后会释放该半连接，不会一直维护无用资源

            2. 三次握手解决了旧数据误接收问题：TCP 使用**随机变化的初始序列号**，每个新连接的初始序列号都不同；旧连接的报文序列号不会落在新连接的有效序列号范围内，因此会被 TCP 协议栈自动丢弃

        - 四次握手的冗余分析

            - 对于连接请求而言，服务器上 “确认客户端 SYN ” 和 “发送自己的 SYN” 可以合并进行（客户端发送了连接请求，服务器可以立马响应，无需等待）
            - 四次握手将这两个动作拆分成两个独立报文，没有任何技术上的必要性，而且会带来两个明显的缺点：
                - **增加了一个完整的往返时间**，连接建立延迟翻倍
                - **增加了网络流量和服务器处理开销**，每个连接多处理一个报文

        - 总结：三次挥手的必要性

            1. **确认双方的收发能力**：前两次握手只能让客户端确认双方的收发能力均正常，而服务端需要通过第三次握手才能确定自己的发送能力和客户端的接收能力 —— 三次是完成双向能力确认的最小必要握手次数
            2. **防止失效连接请求**： 如果只有两次握手，过期的 SYN 报文可能导致服务端错误地建立历史连接，浪费资源 —— 三次握手通过第三次 ACK 报文让客户端有机会判断并终止历史连接
            3. **同步双方的初始序列号**：序列号是 TCP 实现可靠传输的基础，三次握手确保了双方都能将自己的序列号告知对方并获得确认；两次握手只能确认一方，另一方无法得到确认，双向可靠性无法建立

            4. **节省网络资源和保证传输效率的设计**：第二次握手中，服务器收到连接请求后可以立即响应、将 SYN 和 ACK 合并在同一个报文中发送，无需将这两个信息拆分为两次通信

                综上， TCP 设计为三次握手，是兼顾了可靠性与传输效率的经典设计

    - **四次挥手释放**

        TCP 连接是**全双工**的，每个方向的数据流都需要单独关闭，因此连接关闭需要四次挥手过程

        - **客户端 → 服务器 方向**：客户端发送完数据，发送 `FIN` 关闭
        - **服务器 → 客户端 方向**：服务器可能还有数据要发，需等待服务器也发送 `FIN` 关闭

        > 这与建立连接不同：建立连接时双方**同时**同意建立双向通道，可以合并 `SYN` 和 `ACK`
        >
        > 关闭时，一方的关闭意愿**不意味着另一方也立即准备好关闭**，因此 `ACK`（确认对方的关闭）和 `FIN`（宣告自己的关闭）通常**无法合并**

        ```mermaid
        sequenceDiagram
            participant C as 主动关闭方（客户端）
            participant S as 被动关闭方（服务器）
            
            Note over C,S: ESTABLISHED
            
            Note over C: 调用close()
            C->>S: FIN(seq=x)
            Note over C: FIN_WAIT_1
            
            Note over S: 收到FIN
            S->>C: ACK(ack=x+1)
            Note over S: CLOSE_WAIT
            Note over C: 收到ACK
            Note over C: FIN_WAIT_2
            
            Note over S: 处理完剩余数据，调用close()
            S->>C: FIN(seq=y)
            Note over S: LAST_ACK
            
            Note over C: 收到FIN
            C->>S: ACK(ack=y+1)
            Note over C: TIME_WAIT (等待2MSL)
            Note over C: CLOSED
            
            Note over S: 收到ACK
            Note over S: CLOSED
        ```

        | 状态             | 所在方     | 含义                                                         |
        | ---------------- | ---------- | ------------------------------------------------------------ |
        | **FIN\_WAIT\_1** | 主动关闭方 | 已发送 `FIN`，等待对方的 `ACK` 或对方的 `FIN`                |
        | **FIN\_WAIT\_2** | 主动关闭方 | 已收到对方对 `FIN` 的 `ACK`，等待对方的 `FIN`                |
        | **CLOSE\_WAIT**  | 被动关闭方 | 已收到对方的 `FIN` 并回复 `ACK`，等待本地应用调用 `close()`  |
        | **LAST\_ACK**    | 被动关闭方 | 已发送自己的 `FIN`，等待最后的 `ACK`                         |
        | **TIME\_WAIT**   | 主动关闭方 | 已发送最后的 `ACK`，等待 **2 倍最大报文段寿命 (2MSL)** 时间确保对方收到 |
        | **CLOSED**       | 双方       | 连接彻底释放                                                 |

        - TCP 连接关闭并不完美，可能产生半连接问题：

            - 主动关闭方发送 FIN 后，被动关闭方未回复 ACK
            - 被动关闭方发送 FIN 后，主动关闭方未回复 ACK
            - 一方主机崩溃，未发送 FIN 报文

            这些情况都会导致一方维护着已经失效的连接，浪费系统资源，TCP 通过保活计时器 `Keepalive Timer` 来检测并释放长时间无数据传输的半连接

## `3.6` 拥塞控制原理

- `3.6.1` 拥塞概述

    **拥塞** `Congestion` 是指 “太多的数据需要网络传输，超过了网络的处理能力”，这是一个**全局性问题**，涉及网络中所有主机、路由器以及链路资源的整体负载状况，和流量控制不同：

    | 对比维度   | 拥塞控制                                 | 流量控制                               |
    | ---------- | ---------------------------------------- | -------------------------------------- |
    | 解决的问题 | 发送者太多，整体发送速度超过网络处理能力 | 单个发送者速度太快，超过接收方处理能力 |
    | 关注范围   | 全局性问题，涉及网络中所有主机和路由器   | 端到端问题，只涉及单个发送方和接收方   |
    | 核心目标   | 防止网络出现全局性性能下降甚至崩溃       | 防止接收方缓冲区溢出                   |

    - 拥塞的表现
        - **分组丢失**：**路由器缓冲区满**，无法容纳新到达的分组，只能主动丢弃
        - **分组延迟增加**：分组在路由器的输出队列中长时间排队等待转发

- `3.6.2` 拥塞的原因与代价

    - 当链路中进入的数据接近链路带宽时，数据来不及即时转发，多余数据包在路由器缓存排队等候，链路的延迟会不断增大

        同时，路由的缓存是有限的，多余的数据在缓存满后会被丢弃，需要重传，进一步加剧的链路的负担

        $\rightarrow$ 不考虑其他因素时，有效吞吐量随输入速率增加逐渐逼近链路物理上限，链路延迟会不断加剧、并趋于无穷

    - 发送端无法区分 “分组丢失” 与 “分组延时”，只能通过超时判断，对于分组只是延迟到达的情况，发送方超时后重传，导致网络中出现两个相同的分组副本，这一现象在有效吞吐量趋近链路上限时被放大

        $\rightarrow$ 有效吞吐量几乎不可能到达链路物理上限，甚至可能随着链路的压力增加，由于大量的非必要重传而导致传输速率下降

    - 考虑网络传输链路上的大量节点，如果某一段线路上由于压力过大导致路由器缓存满，经过这条线路上的数据会大量丢失，进而导致了上游链路带宽的浪费

        $\rightarrow$ 下游分组丢失时，所有上游链路的传输能力都被浪费

    > **核心结论：**
    >
    > 1. 网络吞吐量永远无法超过其物理最大容量
    > 2. 吞吐量在接近最大容量时会开始下降
    > 3. 丢包和必要重传会降低有效吞吐量
    > 4. 非必要重传会进一步降低有效吞吐量
    > 5. 下游分组丢失时，所有上游链路的传输能力都被浪费

- `3.6.3` 拥塞控制方法

    - 端到端拥塞控制

        网络不提供任何内部状态信息，端系统完全依靠自身观察到的现象（延迟增加、分组丢失）来推断拥塞是否发生，并调整发送速率

        ```mermaid
        sequenceDiagram
            participant S as 发送端
            participant N as 网络
            participant R as 接收端
            
            S->>N: 发送数据
            N->>R: 转发数据
            R->>S: ACK确认
            Note over S: 观察：ACK延迟？<br/>丢包事件？<br/>推断：网络拥塞？
            S->>S: 调整发送速率
        ```

        - 不需要路由器支持，实现简单，兼容性极好

        - 反应滞后，必须等拥塞已经发生（出现丢包）后才能做出反应

    - 网络辅助的拥塞控制

        路由器主动参与拥塞控制，向端系统提供显式的拥塞反馈信息，端系统根据这些信息提前调整发送速率

        ```mermaid
        sequenceDiagram
            participant S as 发送端
            participant R1 as 路由器
            participant R as 接收端
            
            S->>R1: 发送数据
            Note over R1: 检测到拥塞！
            R1->>R: 设置拥塞指示位
            R->>S: 返回带拥塞信息的ACK
            Note over S: 根据显式反馈<br/>调整发送速率
        ```

        - 反应更快，能够在拥塞初期甚至发生前进行干预
        - 需要路由器硬件和软件的支持，实现复杂，部署难度大

## `3.7` TCP 拥塞控制

- `3.7.1` TCP 端到端的拥塞控制

    TCP 采用**端到端的拥塞控制**，网络本身不提供拥塞反馈，由发送方通过观察网络行为（丢包、延迟）来推断拥塞程度并调整发送速率

    > 这样有助于减轻路由器的负担，符合网络核心简单的 TCP/IP 架构原则

- `3.7.2` TCP 拥塞感知

    | 拥塞信号     | 含义                    | 拥塞程度 | 网络状况                             |
    | ------------ | ----------------------- | -------- | ------------------------------------ |
    | 超时重传     | 某个段超时未收到确认    | 严重拥塞 | 网络可能已经瘫痪，丢包率高           |
    | 3 次重复 ACK | 连续收到 3 个相同的 ACK | 轻度拥塞 | 网络出现个别丢包，但整体仍能正常工作 |

    > 3 次重复 ACK 表明**个别报文段的丢失**而不是网络严重拥塞导致的大量数据丢失，因此 TCP 采取相对温和的调整策略

- `3.7.3` TCP 发送速率控制

    - 拥塞窗口 `Cwnd` ：发送方根据拥塞状况自行维护的窗口，表示发送方在未收到确认的情况下可以连续发送的最大字节数
    - 发送速率估算：`发送速率 ≈ Cwnd / RTT`（字节 / 秒），RTT 为往返时间

    $\rightarrow$ **发送窗口上限**：`LastByteSent - LastByteAcked ≤ min(Cwnd, rwnd)`，其中 rwnd 是接收方通告的接收窗口

    > `Cwnd` 结合拥塞感知的方法，能根据网络拥塞程度动态调整，从而粗略地控制发送方的往网络中注入的速率

- `3.7.4` TCP 拥塞控制策略

    | 机制                                     | 作用                                   |
    | ---------------------------------------- | -------------------------------------- |
    | **慢启动** `Slow Start (SS)`             | 连接初始阶段指数级探测可用带宽         |
    | **拥塞避免** `Congestion Avoidance (CA)` | 超过阈值后线性增长，谨慎探测           |
    | **快速重传** `Fast Retransmit`           | 收到 3 dupACKs 立即重传，不等超时      |
    | **快速恢复** `Fast Recovery`             | 快速重传后保持较高窗口，避免退回慢启动 |

    1. 慢启动

        - **初始状态**：TCP 连接建立时，`Cwnd = 1 MSS`（MSS 为最大分段大小，通常为 1460 字节）
        - **增长规则**：**每收到一个 ACK，Cwnd 增加 1 MSS**，因此每个 RTT 内 Cwnd 翻倍（指数增长）
        - **特点**："慢启动" 指初始发送速率慢，但增长速度极快，能迅速探测网络可用带宽

    2. 拥塞避免与 AIMD

        发送方可以提高发送速率直到发生丢包（拥塞），然后在发生丢包（拥塞）事件时降低发送速率

        - **从慢启动到拥塞避免的切换**：引入慢启动阈值 `Slow-start Threshold (Ssthresh)` 

            - 当 `Cwnd < Ssthresh`：处于**慢启动阶段**，指数增长
            - 当 `Cwnd > Ssthresh`：进入**拥塞避免阶段**，线性增长
            - 当 `Cwnd = Ssthresh`：通常进入拥塞避免（实现可略有差异）
            - `Ssthresh` 的设置：若出现丢失，`Ssthresh` 设置成 Cwnd 的 1/2

        - AIMD 原理

            - 加性增加 `Additive Increase` ：拥塞避免阶段，**每个 RTT 内 Cwnd 增加 1 MSS**（线性增长）

            - 乘性减少 `Multiplicative Decrease` ：每次丢失事件（3 个冗余 ACK），将 Ssthresh 设置为当前 Cwnd 的一半
            - Why AIMD ？
                - **分布式协作**：无需集中式控制，各 TCP 连接独立调整
                - **异步适应**：不需要全局时钟同步
                - **稳定性**：已被数学证明能收敛到公平且高效的平衡点
                - **网络友好**：避免拥塞崩溃

        - 不同拥塞情况的不同处理

            - TCP Tahoe 协议

                | 丢包检测方式  | 响应动作                                                |
                | ------------- | ------------------------------------------------------- |
                | **超时**      | `Ssthresh = Cwnd/2`, `Cwnd = 1 MSS`，重新进入**慢启动** |
                | **3 dupACKs** | `Ssthresh = Cwnd/2`, `Cwnd = 1 MSS`，重新进入**慢启动** |

                > 无论何种丢包，一律退回慢启动，过于保守

            - TCP Reno 协议（现在采用）

                | 丢包检测方式  | 响应动作                                                     |
                | ------------- | ------------------------------------------------------------ |
                | **超时**      | `Ssthresh = Cwnd/2` , `Cwnd = 1 MSS`，进入**慢启动**         |
                | **3 dupACKs** | `Ssthresh = Cwnd/2` , `Cwnd = Ssthresh + 3MSS` ，进入**快速恢复** |

                > Reno 在收到 3 dupACKs 时**不回到慢启动**，而是将窗口设为 `Ssthresh + 3MSS` 并进入快速恢复，避免了窗口骤降导致的吞吐量断崖

    3. 快速恢复与快速重传

        1. 收到第 3 个重复 ACK 时，`Ssthresh = Cwnd / 2` ，`Cwnd = Ssthresh + 3MSS`
        2. 立刻**重传**丢失的报文段
        3. 每收到一个额外的重复 ACK ，Cwnd += 1 MSS（继续膨胀）
        4. 当收到**确认新数据**的 ACK 时：Cwnd = Ssthresh（收缩回阈值），回到**拥塞避免**阶段

- `3.7.5` TCP 吞吐量分析

    - 使用拥塞窗口尺寸 W 和 RTT 来描述，假设发送端总有数据在传输，和忽略慢启动阶段
    - **平均吞吐量**：对于经典 AIMD 算法，平均吞吐量约为 $0.75\times W_{max}/\text{RTT}$ bits，其中 W~max~ 为拥塞发生前最大窗口大小

- `3.7.6` 现代 TCP 拥塞控制改进

    - `TCP CUBIC` 算法：使用三次函数来调整 Cwnd 的增长速度，在窗口接近上次拥塞点时增长变慢，远离时增长变快

        > `TCP Cubic` 算法更适合高速网络，是现代 Linux 系统的默认 TCP 拥塞控制算法

    - 显式拥塞通知

        显式拥塞通知 `Explicit Congestion Notification (ECN)` 是一种**网络辅助**的拥塞控制机制，路由器在即将发生拥塞时，在 IP 首部标记拥塞位，无需等到丢包就能通知拥塞

        - 路由器检测到拥塞，将 IP 首部的 ECN 位设置为 "拥塞经历"
        - 接收方收到标记的报文后，在 ACK 中设置 ECE 位
        - 发送方收到 ECE 位后，将 Cwnd 减半，如同收到 3 次重复 ACK

        > 避免了丢包带来的性能损失，能够更早地响应拥塞

    - 基于延迟的拥塞控制

        通过测量 RTT 变化判断拥塞：RTT 增加 → 网络排队增加 → 即将拥塞，而不是等待丢包（拥塞已经发生后）再处理

        - **管道原理**：保持发送端管道 “**仅足够满，但不满**”，在即将发生拥塞时**提前减速**，在丢包发生前调整速率
        - 认为具有拥塞窗口 Cwnd 的**非拥塞吞吐量为 Cwnd/RTT~min~**
            - 如果测量的吞吐量“非常接近”非拥塞吞吐量，线性增加 Cwnd（因为路径不拥塞）
            -  否则，如果测量的吞吐量“远低于”非拥塞吞吐量，线性减少 Cwnd（因为多半发生了路径拥塞）

        - 代表算法
            - **TCP Vegas**：比较期望吞吐量与实际吞吐量，差值过大则减窗
            - **TCP BBR（Bottleneck Bandwidth and RTT）**：Google 提出，测量瓶颈带宽和最小 RTT，直接计算最优发送速率

## `3.8` 传输层功能的演化

- `3.8.1` 传输层协议需要演化

    传输层是互联网协议栈中负责**端到端应用进程通信**的核心层，在过去 40 多年里，所有互联网应用只能在 TCP 和 UDP 之间二选一

    - TCP 协议：面向连接，提供可靠的字节流传输，内置拥塞控制和流量控制机制

        但是，其可靠性恢复代价大、效率低，其拥塞控制机制假设 "所有丢包都是网络拥塞引起的"，这在无线链路（丢包多由信号干扰导致）中会严重降低性能

        应用一旦选择 TCP，就必须接受其 "一刀切" 的服务方式

    - UDP 协议：无连接，仅提供应用进程的区分功能，不保证可靠性，不进行拥塞控制

        但是，其仅提供最基本的进程区分功能，所有可靠性保证、拥塞控制、流量控制都需要应用层自己实现，极大增加了开发者的工作量

    - 新型应用与网络环境的驱动

        - 应用需求多样化：实时视频、在线游戏、物联网等应用对低延迟、高吞吐量有不同要求
        - 高速链路、数据中心网络和无线链路的大量采用：这些环境的特性与 TCP/UDP 设计时的假设（低速、有线、低丢包）相差甚远

- `3.8.2` QUIC 协议

    快速 UDP 互联网连接 `Quick UDP Internet Connections (QUIC)` 是由谷歌主导开发的新一代传输协议，其运行在 UDP 之上，重新实现了 TCP 的所有核心功能，并集成了 TLS 1.3 加密，大幅提升了 Web 性能，是 HTTP/3 的底层传输标准

    - QUIC 的核心特性

        - **高效的连接建立**：将 TCP 的可靠性状态（初识序号、拥塞窗口）和 TLS 的安全状态（身份认证、加密密钥）合并，**在一个 RTT（往返时间）内完成所有握手过程**

        - **无队头阻塞的多路复用**：多个应用级别的 "流" 可以复用于一个 QUIC 连接，每个流独立进行可靠传输和安全加密，一个流的丢包不会影响其他流，彻底解决了 TCP 的队头阻塞问题

        - **可插拔的拥塞控制**：所有流服从公共的拥塞控制策略，但算法可根据网络环境和应用需求灵活替换

        - **连接迁移**：当客户端 IP 地址或端口变化时（如手机从 WiFi 切换到 4G），QUIC 连接可以无缝迁移，无需重新建立

    - QUIC **的连接建立机制**

        - **QUIC 1-RTT**：首次连接时，客户端发送的第一个包即携带加密握手信息，**1 个 RTT** 后即可发送应用数据
        - **QUIC 0-RTT**：若客户端之前与服务器通信过并缓存了会话票据，则**无需 RTT** 即可直接发送数据（存在前向安全性的权衡）

        ```mermaid

            C->>S: SYN (seq=x)
        ```

    - QUIC 的可靠传输与拥塞控制

        QUIC 在应用层**重新实现了 TCP 的核心功能**，且更加高效：

        - **差错控制**：采用类似 TCP 的确认、重传机制，但使用**包号** `Packet Number` **单调递增**替代 TCP 的序列号，解决重传歧义问题
        - **拥塞控制**：框架内置，但算法可插拔（如 Cubic、BBR），所有流共享同一拥塞控制窗口
        - **流独立**：每个流拥有独立的可靠传输状态与流量控制，但共享底层加密与拥塞控制
